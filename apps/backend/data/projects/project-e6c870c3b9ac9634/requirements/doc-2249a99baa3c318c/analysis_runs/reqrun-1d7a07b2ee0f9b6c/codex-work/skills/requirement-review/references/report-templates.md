### 2. 清晰度和可理解性评估

**评级**：[优秀 / 良好 / 一般 / 较差]（[分数]%）

**优势**：
- ✅ [写得好的需求示例]

**发现的问题**：

#### 有歧义的需求
- ⚠️ **[REQ-ID]**：“[原始歧义需求文本]”
  - **问题**：[为什么有歧义，可能存在多个解释]
  - **解释 A**：[可能含义 1]
  - **解释 B**：[可能含义 2]
  - **建议**：“[更清晰的需求文本]”

#### 发现的模糊词
使用不清晰语言的需求：
- “用户友好”出现在：[REQ-023, REQ-034, REQ-056]
- “性能很快”出现在：[REQ-045, REQ-078]
- “易用”出现在：[REQ-067, REQ-089, REQ-091]
- “直观”出现在：[REQ-102, REQ-115]

**建议**：替换为具体、可度量标准。例如：
- “用户友好” → “新用户无需帮助即可在 < 5 分钟完成首个任务”
- “快速” → “95% 请求响应时间 < 2 秒”

### 3. 一致性和冲突分析

**评级**：[优秀 / 良好 / 一般 / 较差]（[分数]%）

#### 冲突需求
- 🔴 **冲突 #1**：需求 [REQ-012] vs [REQ-089]
  - **REQ-012**：“[完整需求文本]”
  - **REQ-089**：“[冲突需求文本]”
  - **冲突性质**：[冲突说明]
  - **业务影响**：[不解决时的影响]
  - **建议解决方式**：[具体处理方案]

#### 术语不一致
| 不一致术语 | 出现次数 | 建议标准术语 |
| ---------- | -------- | ------------ |
| User / Customer / Client / End-user | 45 / 23 / 12 / 8 | “User”（出现最多） |
| Login / Sign-in / Log-in / Sign in | 15 / 8 / 7 / 4 | “Login”（与系统一致） |
| Order / Purchase / Transaction | 34 / 12 / 8 | “Order”（业务术语） |

**建议**：创建术语表定义标准术语，并更新所有需求。

#### 优先级冲突
- [REQ-045] 标为 Critical，但依赖标为 Medium 的 [REQ-078]
- 太多需求（120 个中的 35 个）被标为 Critical
- [REQ-089] 和 [REQ-091] 都标为 Priority 1，但彼此互斥

### 4. 可测试性评估

**评级**：[优秀 / 良好 / 一般 / 较差]（[分数]%）

#### 不可测试需求
- ❌ **[REQ-034]**：“系统应当安全”
  - **问题**：没有可度量标准判断“安全”
  - **建议**：拆成可测试需求：
    - “系统应强制密码复杂度（8+ 字符、1 个大写字母、1 个数字、1 个特殊字符）”
    - “系统应在 15 分钟内 5 次登录失败后锁定账户”
    - “系统应使用 TLS 1.3 加密所有传输中数据”
    - “系统应使用 AES-256 加密静态敏感 PII”
    - “系统应记录所有认证尝试，包含时间戳和 IP”

#### 验收标准缺失
缺少验收标准的用户故事：
- [US-045]：“作为用户，我想搜索商品...”
- [US-056]：“作为客户，我想追踪订单...”
- [US-078]：“作为管理员，我想管理用户...”
- [US-089]：“作为用户，我想保存收藏...”

**总计**：87 个用户故事中有 23 个缺少验收标准

**建议**：在 sprint 计划前为所有故事补充 Given-When-Then 验收标准。

#### 缺少验证方法的需求
- [REQ-023, REQ-034, REQ-056, REQ-078, REQ-091]：未定义测试方法
- 第 4.3 节非功能需求没有指定验证方法

### 5. 可追踪性评估

**评级**：[优秀 / 良好 / 一般 / 较差]（[分数]%）

#### 缺少向后追踪

- [REQ-145]：实时仪表盘功能（谁提出？为什么需要？）
- [REQ-167]：高级报表模块（业务价值不清楚）
- [REQ-189]：移动 App 支持（是否属于原始范围？）

**建议**：将每条需求关联到业务目标、提出干系人和商业论证元素。

#### 缺少向前追踪
**没有设计覆盖的需求**：[45 条需求]
- 第 3.2 节（用户管理）：无架构/设计记录
- 第 3.5 节（报表）：无 UI 原型或数据模型

**没有测试用例的需求**：[78 条需求]
- 第 3.1-3.4 节功能需求没有映射测试用例
- 非功能需求（第 4 节）没有测试策略

**未追踪的业务需要**：
- “支持现场工作人员移动访问” - 没有移动端需求
- “集成支付网关” - 没有支付处理需求

**建议**：创建或更新需求追踪矩阵：业务需要 → 需求 → 设计 → 实现 → 测试用例。

## 建议

### Critical（批准前必须修复）

1. **补充缺失安全需求（REQ-SEC-*）**
   - **优先级**：Critical
   - **工作量**：2-3 天
   - **行动**：
     - 定义认证机制（OAuth2、JWT）
     - 指定授权规则（RBAC 模型）
     - 记录数据保护要求（静态/传输加密）
     - 定义审计日志要求（记录什么、何时记录、保留多久）
     - 指定会话管理（超时、并发会话）
   - **负责人**：[安全架构师 + 业务分析师]
   - **截止日期**：[日期]

2. **解决需求冲突（冲突 #1、#3、#5）**
   - **优先级**：Critical
   - **工作量**：1 周
   - **行动**：
     - 冲突 #1（REQ-012 vs REQ-089）：明确手机号是否必填
     - 冲突 #3（REQ-034 vs REQ-078）：统一实时处理 vs 批处理
     - 冲突 #5（REQ-091 vs REQ-102）：解决移动优先 vs 桌面优先
   - **负责人**：[产品负责人 + 业务分析师]
   - **截止日期**：[日期]

3. **为所有用户故事补充验收标准（23 个故事）**
   - **优先级**：Critical
   - **工作量**：1-2 周
   - **行动**：
     - 每个故事使用 Given-When-Then 格式
     - 包含正向场景（happy path）
     - 包含负向场景（错误情况）
     - 包含边界场景
     - 定义清晰通过/失败标准
   - **负责人**：[业务分析师 + 开发团队]
   - **截止日期**：[日期]

### Major（为提升质量应修复）

4. **提升性能需求清晰度**

   - **工作量**：3-5 天

     - 记录性能测量方法
   - **负责人**：[业务分析师 + 性能工程师]
   - **截止日期**：[日期]

5. **增强需求追踪性**

   - **行动**：

     - 将需求映射到测试用例
     - 记录需求来源（干系人、法规等）
   - **负责人**：[业务分析师]
   - **截止日期**：[日期]
