# 需求评审

在设计和开发开始前，系统化评审需求，验证需求质量并识别问题。确保需求完整、清晰、一致、可测试、可追踪。

## 评审流程

## 1. 准备

收集所有相关文档：

- 需求文档（BRD、SRS、用户故事）
- 非功能需求和约束
- 需求追踪矩阵（如有）
- 项目背景（章程、目标）
- 现有验收标准

### 2. 质量评估

使用 **六个质量属性** 评估每条需求：

1. **完整性**：所有需求已捕获，没有缺失细节或 TBD，依赖已识别
2. **清晰度**：无歧义、具体，不使用模糊词（“用户友好”“快速”“简单”）
3. **一致性**：无冲突，术语和优先级一致
4. **可测试性**：可通过可度量验收标准验证，具备明确通过/失败条件
5. **可追踪性**：能关联业务目标、设计和测试
6. **可行性**：在约束内（预算、时间、能力）技术上可实现

> 详细评估标准和不同文档类型的检查清单见 [quality-checklists.md](references/quality-checklists.md)

### 3. 问题识别

识别常见需求问题：

**有歧义**：“系统应当很快” → 指定可度量标准：“95% 请求响应时间 < 2 秒”

**不可测试**：“系统应当安全” → 定义具体控制项：密码复杂度、加密标准、审计日志

**不完整**：“系统应发送通知” → 指定渠道、时机、内容、接收人

**相互冲突**：REQ-012 “手机号必填” vs REQ-089 “手机号可选” → 标记给干系人裁决

> 更多前后对比例子见 [examples.md](references/examples.md)

### 4. 质量评分

为每个质量属性计算分数（0-100%）：

- **90-100%**：优秀 - 问题极少
- **75-89%**：良好 - 需要少量改进
- **60-74%**：一般 - 存在明显缺口
- **低于 60%**：较差 - 需要大幅返工

**总体质量** = 六个属性的平均值
**目标**：生产就绪需达到 ≥ 90%

### 5. 报告生成

创建结构化评审报告，包含：

**执行摘要**：质量评级、建议、关键优势（2-3 条）、关键问题（2-3 条）、优先行动

**详细发现**：质量分数、按严重程度分类的问题（Critical/Major/Minor）、带需求 ID 的具体例子

**行动项**：带负责人、截止日期、工作量估算和批准条件的优先级列表

> 完整报告结构和模板见 [report-templates.md](references/report-templates.md)

### 6. 建议

给出清晰决策：

- **批准**：需求达到 ≥ 90% 质量阈值
- **有条件批准**：进入设计前必须解决关键问题
- **重大修订**：质量 60-74%，需要大量返工
- **拒绝**：质量 < 60% 或存在根本性问题，需要完整重设

## 按文档类型关注重点

### 商业需求文档（BRD）

关注业务目标、干系人诉求、范围定义、商业论证、约束。

### 软件需求规格说明（SRS）

关注功能需求、非功能需求（性能、安全、可扩展性）、系统行为、集成点、IEEE 830 符合性。

### 用户故事待办列表

关注 INVEST 准则（独立、可协商、有价值、可估算、小、可测试）、验收标准格式（Given-When-Then）、故事格式、优先级。

> 按文档类型的评估标准见 [quality-checklists.md](references/quality-checklists.md)

## 严重程度定义

- **Critical**：阻塞进展，必须立即修复（安全缺口、根本冲突、范围缺失）
- **Major**：显著影响质量，应在批准前修复（标准模糊、验收标准缺失）
- **Minor**：质量改进项，最好修复（格式、示例、增强说明）

## 需要标记的常见反模式

- **镀金**：加入未被要求的功能
- **偏解决方案**：说明“如何做”而不是“做什么”（需求应尽量与技术无关）
- **范围蔓延**：没有变更控制就接受变更
- **分析瘫痪**：无限追求需求完美
- **弱验收标准**：测试条件模糊或缺失
- **无追踪性**：需求与业务目标断开

## 需要替换的模糊词

始终替换为可度量标准：

- “用户友好”“直观”“简单” → 定义可用性指标
- “快速”“很快”“响应快” → 指定响应时间目标
- “安全” → 定义具体安全控制项
- “可扩展” → 定义容量和负载目标
- “可靠” → 定义可用率和恢复时间

## 标准符合性

- **IEEE 830**：SRS 结构和内容标准
- **INVEST**：用户故事质量准则（独立、可协商、有价值、可估算、小、可测试）
- **ISO/IEC 25010**：系统与软件质量模型
- **行业标准**：HIPAA（医疗）、PCI-DSS（支付）、SOC 2（SaaS）、FDA（医疗器械）

> 标准符合性细节见 [quality-checklists.md](references/quality-checklists.md)

## 报告格式

按以下结构生成评审报告：

1. **执行摘要**（1 页）：整体评估、关键发现、建议
2. **质量指标**（0.5 页）：按属性列出分数和目标
3. **详细发现**（2-5 页）：按属性分组的问题、例子和建议
4. **行动项**（1 页）：带负责人和截止日期的优先级列表
5. **批准决策**（0.5 页）：建议、理由和下一步

报告应事实清楚、具体、可执行。识别问题时始终引用具体需求 ID。

> 完整报告模板见 [report-templates.md](references/report-templates.md)
