## 歧义需求示例

## 示例 1：性能需求

**❌ 差（有歧义）**：

```text
REQ-045: 系统应当快速且响应灵敏。
```

**问题**：

- “快速”是主观词，对不同用户含义不同
- “响应灵敏”模糊，没有可度量标准
- 没有上下文，哪些操作要快
- 没有基线，怎样才算可接受

**✅ 好（清晰）**：

```text
REQ-045: 在正常负载（最多 1,000 个并发用户）下，系统应在 2 秒内响应 95% 的用户搜索请求。

验收标准：
- 第 95 百分位搜索结果在 2 秒内展示
- 第 99 百分位搜索结果在 5 秒内展示
- 使用 1,000 个并发用户执行搜索进行测量
- 使用持续 1 小时的负载测试进行测量
- 基准测试数据：100 万条商品记录
```

### 示例 2：用户界面需求

**❌ 差（有歧义）**：

```text
REQ-067: 应用应具备用户友好、直观且易用的界面。
```

**问题**：

- “用户友好”“直观”“易用”都是主观词
- 没有可度量成功标准
- 不能客观测试
- 不同用户的技能水平不同

**✅ 好（清晰）**：

```text
REQ-067: 应用应支持新用户在无需培训的情况下完成核心任务。

可度量标准：
- 80% 的首次使用用户可在无人协助情况下 5 分钟内完成账户注册
- 70% 的新用户可在不查看帮助文档的情况下 10 分钟内完成首次下单
- 通过至少 20 名参与者的可用性测试测量任务完成情况
- 用户在任务后问卷中对易用性的评分 ≥ 4.0/5.0
- 关键流程从开始到完成最多 3 步
```

### 示例 3：安全需求

**❌ 差（有歧义）**：

```text
REQ-089: 系统应当安全并保护用户数据。
```

**问题**：

- “安全”过于宽泛，未说明安全的哪些方面
- “保护”模糊，未说明防护哪些威胁
- 没有定义具体机制
- 按当前写法不可测试

**✅ 好（清晰）**：

```text
REQ-089: 系统应通过以下安全控制项保护用户数据：

1. 认证：
   - 支持 OAuth 2.0 和 SAML 2.0 认证
   - 强制密码复杂度：至少 12 位，包含 1 个大写字母、1 个小写字母、1 个数字、1 个特殊字符
   - 15 分钟内 5 次登录失败后锁定账户
   - 每 90 天要求修改密码

2. 数据保护：
   - 使用 TLS 1.3 加密所有传输中数据
   - 使用 AES-256 加密静态敏感 PII
   - 使用 bcrypt 哈希密码，work factor ≥ 12
   - 掩码信用卡号（仅显示后 4 位）

3. 审计与监控：
   - 记录所有认证尝试（成功和失败），包含时间戳、用户名、IP
   - 记录所有敏感字段访问，包含用户 ID 和时间戳
   - 审计日志保留 2 年
   - 同一 IP 5 分钟内失败登录 > 10 次时告警安全团队
```

## 不可测试需求示例

### 示例 4：可扩展性需求

**❌ 差（不可测试）**：

```text
REQ-102: 系统应具备高可扩展性，以支持未来增长。
```

**问题**：

- “高可扩展性”没有可度量定义
- “未来增长”未定义，增长多少
- 没有清晰通过/失败标准
- 无法验证“应具备可扩展性”

**✅ 好（可测试）**：

```text
REQ-102: 系统架构应支持水平扩展以处理增长负载。

可测试标准：
- 在不改代码的情况下，通过增加应用服务器将系统从 1,000 并发用户扩展到 10,000 并发用户
- 负载从 1,000 增至 5,000 并发用户时（基础设施按比例扩展），响应时间退化 < 10%
- 数据库支持只读副本，复制延迟 < 100ms
- 无状态应用设计允许增删服务器而不丢失会话
- 负载均衡器将流量分发到 N 台应用服务器，偏差 < 5%

验证方法：
- 使用 JMeter 在 1K、5K、10K 并发用户下做负载测试并测量响应时间
- 基础设施测试：增加服务器并验证自动扩缩容触发
- 监控数据库复制延迟 24 小时
```

### 示例 5：可维护性需求

**❌ 差（不可测试）**：

```text
REQ-115: 应用代码应可维护并遵循最佳实践。
```

**问题**：

- “可维护”是主观词
- “最佳实践”随团队/组织变化
- 没有客观度量
- 无法判断通过/失败

**✅ 好（可测试）**：

```text
REQ-115: 应用代码应满足以下可维护性标准：

代码质量指标：
- 保持 ≥ 80% 单元测试覆盖率（由覆盖率工具测量）
- 每个函数圈复杂度 ≤ 10（由 SonarQube 测量）
- 不存在超过 10 行的重复代码块（由 SonarQube 检测）
- 所有函数/方法均有 JSDoc/XML 文档和参数说明

代码标准：
- 遵循 .eslintrc 中定义的 ESLint 规则（生产构建零错误）
- 通过 Prettier 格式检查（在 pre-commit hook 中自动执行）
- 所有公开 API 均记录在 OpenAPI 3.0 规范中
- 合并前必须经过代码评审批准（至少 1 名批准人）

验证方法：
- 自动：每次提交执行 SonarQube 分析，未达阈值则构建失败
- 自动：CI 流水线执行 ESLint/Prettier 检查
- 手工：代码评审清单包含文档检查
```

## 冲突示例

### 示例 6：优先级冲突

**❌ 冲突需求**：

```text
REQ-125: 用户注册时应提供手机号。[优先级：Critical]
REQ-187: 为降低注册阻力，手机号应为可选。[优先级：Critical]
```

**问题**：

- 直接矛盾：必填 vs 可选
- 两者都标为 Critical，不能同时都是必要项
- 不同干系人可能有不同目标
- 开发无法同时实现两者

**✅ 已解决需求**：

```text
REQ-125: 用户注册时应提供邮箱地址（必填）。

REQ-125a: 用户可在注册时选择性提供手机号，用于：
- 短信通知（用户选择加入）
- 双因素认证（用户选择加入）
- 通过短信接收订单状态（用户选择加入）

REQ-125b: 系统应发送验证邮件，在账户激活前确认邮箱地址。

REQ-125c: 如果用户提供手机号，系统应在启用短信功能前发送短信验证码。

优先级：Critical（邮箱）、Medium（手机号）
理由：邮箱对账户恢复和通信至关重要；手机号是给希望使用短信功能用户的增值项。
解决日期：2024-01-15
参与干系人：产品负责人（Sarah）、UX 负责人（Mike）、安全负责人（Tom）
```

### 示例 7：技术冲突

**❌ 冲突需求**：

```text
REQ-145: 系统应在所有设备间提供 < 1 秒延迟的实时同步。
REQ-167: 系统应支持离线工作，并在连接恢复后同步变更。
```

**问题**：

- 实时同步需要持续连接
- 离线模式意味着无连接
- 架构方案存在冲突
- 需要澄清期望行为

**✅ 已解决需求**：

```text
REQ-145: 当设备在线时，系统应提供近实时同步。

标准：
- 当所有设备均有活跃网络连接时，变更应在 5 秒内跨设备同步
- WebSocket 连接维护同步状态
- 同步期间用户看到“同步中...”提示
- 同步完成后用户看到“已同步”确认

REQ-167: 系统应支持离线模式和延迟同步。

标准：
- 用户离线时可查看和编辑本地缓存数据
- 离线期间系统在本地排队变更
- UI 清晰显示“离线模式”提示
- 连接恢复后，系统自动同步排队变更
- 冲突解决：Last Write Wins（LWW），按时间戳处理，并向用户提示冲突
- 用户可查看同步历史，了解哪个设备做了哪些变更

优先级：REQ-145（High）、REQ-167（Medium）
架构：事件溯源 + local-first 方案，使用 CRDT 实现无冲突合并
```

## 用户故事示例

### 示例 8：验收标准较差的用户故事

**❌ 差的用户故事**：

```text
US-045: 作为用户，我想搜索商品，以便找到我需要的东西。

验收标准：
- 搜索可用
- 展示结果
- 用户可以点击结果
```

**问题**：

- 标准模糊（“搜索可用”是怎样可用）
- 没有定义具体场景
- 没有处理错误情况
- 没有性能标准
- 没有边界场景

**✅ 好的用户故事**：

```text
US-045: 作为客户，我想按关键词搜索商品，以便快速找到感兴趣并想购买的商品。

验收标准：

Given 我在网站任意页面
When 我在搜索框输入“laptop”并按 Enter 或点击搜索
Then 我应在 2 秒内看到匹配“laptop”的商品列表

Given 我搜索“laptop”
When 搜索完成
Then 结果应按相关性排序（最佳匹配优先）
And 每个结果展示：商品图片、标题、价格、评分、库存状态
And 我能看到结果数量（例如“找到 1,247 个 laptop 相关结果”）

Given 我搜索“xyzabc123nonsense”
When 没有商品匹配搜索
Then 我看到“未找到 xyzabc123nonsense 的结果”消息
And 我看到搜索建议或热门分类

Given 我搜索某个商品
When 我点击搜索结果
Then 我进入该商品详情页

Given 我正在查看搜索结果
When 结果超过 20 条
Then 结果分页展示（每页 20 条）
And 我可以跳到上一页/下一页
And 我能看到总页数（例如“第 1 页，共 63 页”）

Given 我使用搜索功能
When 我输入 SQL 注入尝试 "'; DROP TABLE products--"
Then 系统清理输入并将其当作普通搜索字符串处理
And 不出现数据库错误

非功能：
- 搜索响应时间：95% 查询 < 2 秒
- 搜索支持最多 1,000 个并发搜索请求
- 商品变更后搜索索引在 5 分钟内更新
- 搜索支持常见拼写错误（例如“labtop” → “laptop”）

完成定义：
- 代码已评审并批准
- 单元测试：覆盖率 80%+
- 集成测试通过
- 性能测试：验证响应 < 2s
- 安全测试：验证 SQL 注入防护
- 已部署到 staging 并由 PO 验证
```

### 示例 9：符合 INVEST 的用户故事

**✅ 好的用户故事（INVEST）**：

```text
US-078: 作为回访客户，我想一键从订单历史中再次购买商品，以便快速购买我经常购买的商品。

故事点：5

验收标准：

Given 我已登录并正在查看订单历史
When 我点击历史订单上的“再次购买”按钮
Then 该订单的所有商品都被加入购物车
And 我进入购物车页面
And 我看到确认消息“12 件商品已加入购物车”

Given 我点击订单 #12345 的“再次购买”
When 部分商品不再可售
Then 可售商品加入购物车
And 我看到列出不可售商品的消息：“注意：2 件商品不再可售：[商品 A]、[商品 B]”
And 我可继续购买可售商品

Given 我点击订单 #12345 的“再次购买”
When 我的购物车中已有商品
Then 再次购买的商品加入现有购物车
And 购物车展示更新后的商品总数

Given 我点击订单 #12345 的“再次购买”
When 商品价格自原订单以来发生变化
Then 商品按当前价格加入购物车
And 我看到消息“价格可能已较原订单发生变化”

完成定义：
- 订单历史页展示 UI 按钮
- 后端 API 端点：POST /api/orders/{orderId}/reorder
- 单元测试覆盖：可售商品、不可售商品、价格变化
- E2E 测试：完整再次购买流程
- 触发分析事件：“reorder_clicked”
- 性能：再次购买在 < 1 秒内完成

依赖：
- 需要已完成：US-034（订单历史页）
- 需要：商品可用性 API

备注：
- 产品团队优先级：High（最高频客户请求）
- 数据显示 35% 客户会在 30 天内再次购买
- 预计转化率提升 8%（基于 A/B 测试）

INVEST 检查：
✅ Independent：可不依赖其他故事开发
✅ Negotiable：如有需要，可简化为“单商品”再次购买
✅ Valuable：直接提升客户便利性和转化率
✅ Estimable：团队可估算为 5 点
✅ Small：适合一个 sprint
✅ Testable：验收标准清楚且包含具体场景
```

## 非功能需求示例

### 示例 10：性能需求

**❌ 差的 NFR**：

```text
NFR-001: 系统应具备良好性能。
```

**✅ 好的 NFR**：

```text
NFR-001: 性能 - 响应时间

系统应满足以下从用户浏览器测得的响应时间目标：

页面加载时间（冷加载）：
- 首页：第 95 百分位 < 3 秒
- 商品列表页：第 95 百分位 < 3 秒
- 商品详情页：第 95 百分位 < 2 秒
- 结账页：第 95 百分位 < 2 秒

API 响应时间：
- 搜索 API：第 95 百分位 < 500ms
- 商品 API：第 95 百分位 < 300ms
- 购物车操作：第 95 百分位 < 200ms
- 结账 API：第 95 百分位 < 1 秒

测量条件：
- 用户位置：与服务器同地理区域（网络延迟 < 50ms）
- 设备：桌面端现代浏览器（Chrome、Firefox、Safari 最新版本）
- 网络：宽带连接（10+ Mbps）
- 负载：最多 5,000 个并发用户

验证：
- 使用 Apache JMeter 模拟 5,000 个并发用户进行负载测试
- 使用真实用户监控（RUM）追踪实际用户体验
- 通过生产 RUM 数据生成周度性能报告
- 在 CI/CD 流水线中执行性能回归测试

优先级：Critical
验收：生产发布前必须满足所有目标
```

### 示例 11：可用性需求

**❌ 差的 NFR**：

```text
NFR-015: 系统应具备高可用性。
```

**✅ 好的 NFR**：

```text
NFR-015: 可用性和正常运行时间

系统应保持按月测量的 99.9% 正常运行时间（每月允许 43.2 分钟停机）。

正常运行时间测量：
- 通过外部监控服务（如 Pingdom）从 3 个地理位置测量
- 如果 30 秒内未收到 HTTP 200 响应，则服务视为“不可用”
- 计划维护窗口不计入正常运行时间

计划维护：
- 每月最多 4 小时计划维护
- 计划维护必须提前 7 天公告
- 维护窗口：周日 2:00 AM - 6:00 AM EST（最低流量时段）
- 维护期间展示维护页和预计恢复时间

高可用架构：
- 负载均衡器至少分发到 3 台应用服务器
- 数据库：主从架构并支持自动故障转移
- 数据库故障转移时间：< 60 秒
- 应用服务器：基于 CPU 自动扩缩容（>70% 时增加服务器）
- 每 30 秒健康检查，自动替换不健康实例

灾备：
- 恢复时间目标（RTO）：4 小时
- 恢复点目标（RPO）：15 分钟
- 数据库备份：每 15 分钟增量，每日全量
- 备份存储在异地地域
- 灾备站点可承载 100% 生产负载

监控和告警：
- 通过 PagerDuty 7x24 监控
- 24 小时滚动窗口可用性低于 99.5% 时告警
- 任意服务停机 > 5 分钟时告警
- 5 分钟内升级到值班工程师

验证：
- 监控服务提供月度正常运行时间报告
- 每季度灾备演练（完整故障转移测试）
- 每月负载均衡器故障转移测试

优先级：Critical
处罚：正常运行时间 < 99.9% 时按合同条款提供 SLA 补偿
```

## 完整评审示例

### 示例 12：BRD 章节评审

**原始 BRD 章节**：

```markdown
## 3.2 用户管理

系统需要用户管理能力。用户应该能够注册、登录并管理个人资料。系统应该安全并保护用户信息。管理员需要能够管理用户。
```

**评审发现**：

**识别的问题**：

1. **完整性（Critical）**：缺少关键需求
   - 未指定密码要求
   - 未定义用户角色（普通用户 vs 管理员）
   - 没有账户激活/验证流程
   - 没有密码重置流程
   - 没有会话管理要求
   - 没有多因素认证要求

2. **清晰度（Major）**：表述模糊
   - “安全”未定义，具体哪些安全控制
   - “管理个人资料”模糊，用户可以编辑哪些内容
   - “管理用户”模糊，管理员有哪些能力

3. **可测试性（Major）**：按当前写法不可测试
   - 所有需求均缺少验收标准
   - 没有可度量安全标准

**改进后的 BRD 章节**：

```markdown
## 3.2 用户管理

### 3.2.1 用户注册

REQ-201: 系统应允许新用户通过以下信息注册：
- 邮箱地址（必填，唯一，格式校验）
- 密码（必填，满足 REQ-202 密码复杂度要求）
- 名（必填，2-50 个字符）
- 姓（必填，2-50 个字符）
- 手机号（可选，如提供则校验格式）

REQ-202: 系统应强制密码复杂度要求：
- 至少 12 个字符
- 至少 1 个大写字母
- 至少 1 个小写字母
- 至少 1 个数字
- 至少 1 个特殊字符（!@#$%^&*）
- 不能与前 5 次密码相同
- 不能包含用户姓名或邮箱

REQ-203: 系统应在注册时发送邮件验证：
- 注册后立即发送验证邮件
- 邮件包含安全验证链接（24 小时后过期）
- 邮箱验证前用户不能登录

### 3.2.2 用户认证

REQ-210: 系统应支持用户名/密码认证：

REQ-211: 系统应在 15 分钟内 5 次登录失败后锁定账户：
- 显示消息：“由于多次登录失败，账户已锁定。请 15 分钟后重试或重置密码。”

REQ-212: 系统应支持“记住我”功能：
- 登录页提供可选复选框
- 勾选后会话持续 30 天
- 未勾选时，会话在 30 分钟不活动后过期
- 用户可随时手动登出

REQ-213: 系统应支持可选双因素认证（2FA）：
- 用户可在账户设置中启用 2FA
- 支持基于 TOTP 的 2FA（兼容 Google Authenticator、Authy）

- 启用 2FA 时提供备份码（10 个一次性码）

### 3.2.3 密码重置
```

## 关键要点

评审需求时，重点检查：

1. **具体性**：用可度量标准替换模糊词
2. **可测试性**：每条需求都应有清晰通过/失败标准
3. **完整性**：覆盖正向路径、错误、边界场景
4. **一致性**：需求之间没有冲突
5. **可追踪性**：关联业务目标和下游产物

高质量需求才能支撑高质量软件。
