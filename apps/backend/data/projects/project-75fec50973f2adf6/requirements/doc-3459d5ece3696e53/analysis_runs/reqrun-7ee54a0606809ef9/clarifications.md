# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 方案选择 | Plan A 和 Plan B 两个方案最终选择哪个方案实施？还是两个方案都需要实现？ | 仅实现 Plan A（修改文件解析节点和收集用户上传文件节点） | 仅实现 Plan B（修改大模型回复和大模型变量赋值节点） | 阻塞开发，两个方案涉及不同的节点修改，决定了整个开发范围和架构设计 |
| P0 | 多图解析-异常处理 | 多图解析时，如果部分图片解析成功、部分解析失败，整体如何处理？ | 整体失败，所有图片都不提交，提示用户哪些图片解析失败需要重新上传 | 部分成功，仅提交解析成功的图片，失败的图片跳过并提示用户 | 影响核心流程的异常处理逻辑和用户体验 |
| P0 | URL上传-校验规则 | URL 上传时，文件大小、格式的具体限制值是多少？ | 单张图片不超过 10MB，支持 jpg/png/gif/webp 格式 | 单张图片不超过 20MB，支持 jpg/png/gif/bmp/webp 格式 | 影响前端校验逻辑和后端处理，不明确无法实现校验功能 |
| P1 | 多图解析-模型选择 | 兜底多图解析模型如何确定？是系统配置的默认模型还是用户自行选择？ | 系统在后台配置一个默认的兜底多图解析模型，用户未选择特定模型时使用该模型 | 没有兜底模型，用户必须手动选择一个支持多图解析的模型，否则无法开启多图解析 | 影响用户配置流程和模型选择逻辑 |
| P1 | URL上传-文件状态 | URL 上传时，如果用户输入的 URL 指向的资源无法访问（404/403/超时），状态如何流转？ | 标记为传输失败，展示失败状态，允许用户重新输入 URL | 标记为解析失败，展示失败状态，允许用户重新输入 URL | 影响 URL 上传的异常处理逻辑和用户交互 |
| P1 | 多图解析-并发与重复 | 用户在短时间内连续点击多次解析按钮，是否会触发多次重复解析请求？ | 解析按钮点击后立即置灰/禁用，防止重复点击，解析完成后恢复 | 不限制点击，但后端做幂等处理，同一批图片只解析一次 | 涉及并发控制和资源消耗，防止重复调用大模型API造成浪费 |
| P1 | 多图解析-工作流 | 工作流（Plan A）中勾选多图解析后，'除图片外先进行解析'具体指什么？非图片文件如何处理？ | 非图片文件（如文档）先单独解析，图片文件等待多图合并后统一解析 | 所有文件（包括非图片）都等待多图合并后统一解析 | 影响工作流中文件解析的执行顺序和逻辑 |
| P2 | 复制导入导出 | 复制导入导出时，多图合并解析的配置（开关状态、选择的模型）是否需要完整保留？ | 完整保留所有多图解析配置，导入后直接可用 | 仅保留开关状态，模型配置需要重新选择 | 影响数据迁移和兼容性实现 |
| P2 | trace日志 | trace 日志需要记录多图解析的哪些信息？ | 记录上传的图片数量、解析结果（成功/失败）、调用的模型名称、请求的 messages 数组 | 记录上传的图片数量、解析结果（成功/失败）、调用的模型名称，不记录具体图片 URL | 影响日志系统的实现和调试能力 |
| P2 | 文件存储 | 上传的图片文件在平台文件服务中保留多久？是否有自动清理策略？ | 保留 7 天，过期后自动清理 | 永久保留，不自动清理 | 影响存储成本和数据生命周期管理 |
