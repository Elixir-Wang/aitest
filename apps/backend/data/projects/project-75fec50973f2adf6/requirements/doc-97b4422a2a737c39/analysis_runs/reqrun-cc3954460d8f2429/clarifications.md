# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 测试影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 灰度迁移流程 | A 类平台按机器人灰度迁移时，同一个机器人下的所有 webhook 事件是否必须整体迁移，还是可以按事件类型（如消息、回调）拆分迁移？ | 机器人维度整体迁移，该机器人的所有 webhook 事件全部走 Go 链路 | 可以按事件类型拆分，部分事件类型走 Go 链路，部分仍走 Python 链路 | 影响灰度迁移的测试用例设计：如果按事件类型拆分，需要测试不同事件类型在不同链路的处理；如果整体迁移，则只需验证机器人级切换的完整性 |
| P0 | 灰度迁移流程 | A 类平台灰度迁移时，同一个机器人下的 webhook URL 在第三方平台修改后，是否存在新旧 URL 同时生效的过渡期（即第三方平台同时向新旧两个 URL 发送请求）？ | 不存在过渡期，修改后所有新请求立即发往新 URL | 存在过渡期，第三方平台可能同时向新旧 URL 发送请求一段时间 | 影响消息去重和幂等性测试设计：如果存在过渡期，需要验证双写场景下消息不重复处理 |
| P0 | 消息处理 | Go gateway 收到 webhook 请求后写入 Go 队列失败（如 RabbitMQ 不可用）时，Go gateway 如何处理？是否向第三方平台返回错误响应？ | Go gateway 返回 5xx 错误给第三方平台，由第三方平台重试 | Go gateway 本地缓存或重试写入，不立即返回错误 | 影响消息丢失场景的测试用例设计和异常处理断言 |
| P0 | 消息处理 | Go worker 消费 Go 队列消息处理失败时，重试机制和最终失败处理策略是什么？ | 消息进入 retry queue 重试若干次，最终进入 Go DLQ | 消息直接进入 Go DLQ，不重试 | 影响异常处理场景的测试用例设计，无法验证重试逻辑和 DLQ 消息的最终处理 |
| P1 | 回退方案 | A 类平台回退时，Go worker 继续处理 Go queue 中已入队消息，但该机器人的 webhook 已切回 Python gateway。如果 Go worker 处理完消息后需要向第三方平台回复（如发送消息状态回调），此时回复应该走 Go 链路还是 Python 链路？ | Go worker 处理完存量消息后，通过 Go 链路直接回复第三方平台 | Go worker 处理完存量消息后，将回复结果写入 Python 队列，由 Python worker 回复 | 影响回退场景的测试用例设计，无法验证存量消息处理完成后的回复是否正确路由 |
| P1 | 回退方案 | B 类平台回退时，Go worker 处理 Go queue 存量消息期间，Python gateway 已恢复接收新流量。如果 Go worker 处理的消息与 Python worker 处理的新消息涉及同一业务对象（如同一客户会话），是否存在数据一致性问题？ | 存在一致性问题，需要设计补偿机制或等待 Go queue 清空后再恢复 Python 链路 | 不存在一致性问题，Go 和 Python 处理的消息在业务上完全独立 | 影响回退场景的数据一致性测试设计，无法验证并发处理同一业务对象时的正确性 |
| P1 | 监控与可观测性 | 灰度迁移期间，如何判断迁移是否正常？具体的可观测指标和成功标准是什么？ | Go 链路消息处理成功率 >= 99.9%，且无消息积压增长，持续观察 15 分钟 | Go 链路无报错日志，Go queue ready 数量稳定或下降，即可认为正常 | 影响灰度迁移验收判断，无法确定何时可以继续下一批迁移或判定迁移成功 |
| P1 | 配置管理 | Go gateway 的路由配置（CHANNEL_GATEWAY_ENABLED_PLATFORMS）修改后，是否需要重启 Go gateway 服务才能生效？ | 需要重启 Go gateway 服务 | 支持热加载，无需重启 | 影响灰度迁移操作的测试设计：如需重启，需验证重启期间请求是否丢失；如支持热加载，需验证配置切换的实时性 |
| P2 | 消息处理 | Go gateway 收到 webhook 请求后，是否向第三方平台返回与 Python gateway 完全相同的响应格式和状态码？ | 响应格式和状态码完全一致，第三方平台无感知 | 响应格式可能不同，但状态码语义一致 | 影响第三方平台兼容性测试：如响应格式不同，部分第三方平台可能根据响应做后续处理，导致行为差异 |
