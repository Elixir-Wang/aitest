# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 测试影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 外置存储触发条件 | 当节点输出字段文本长度刚好等于 10000 字符时（例如边界值 9999、10000、10001），是否触发外置存储？10000 是闭区间还是开区间？ | 采用严格大于：文本长度 > 10000 时外置；等于 10000 仍按原结构保留完整文本 | 采用大于等于：文本长度 ≥ 10000 时外置；9999 仍按原结构 | 无法设计 9999/10000/10001 边界用例，无法断言外置引用态与原结构的切换断言点，影响回归边界测试覆盖。 |
| P0 | 单字段 20000 字上限 | 单个字段长度超过 20000 字时（例如知识检索结果、文件解析结果）系统应如何处理？ | 写入侧拒绝：超过 20000 字直接写入失败，提示“字段超过最大长度限制” | 写入侧自动截断：保留前 20000 字并继续流程，日志记录被截断 | 无法设计 19999/20000/20001 边界用例，无法对超长知识检索结果、文件解析结果断言系统反应，影响异常流与兼容性测试验收。 |
| P0 | 下游节点读取判定 | “下游节点仅做判断、展示、传递则不读取完整内容”的判定口径是什么？ | 由节点类型静态判定：节点本身标识为“消费型/传递型”，消费型始终读取完整内容，传递型保持引用 | 由节点运行时行为自适应：节点按是否调用完整读取 API 自动决定是否触发读取，节点无统一策略 | 无法为代码执行、语义判断、条件判断、大模型回复、文本回复等节点分别设计“是否读取完整内容”的断言用例，会出现“外置后下游莫名拉全量”或“需要全量的下游却拿到引用”的覆盖空白。 |
| P0 | 外置存储异常处理 | 外置存储失败（数据库写入/读取异常）时，对话流引擎应如何处理？ | 失败即报错：任一环节失败则将整段对话流标记为失败并抛出异常，不允许降级继续 | 降级继续：数据库不可用时将完整文本回退到运行态按原结构透传，牺牲性能保可用性 | 无法设计数据库故障注入用例，无法断言引擎在 DB 不可用时的回退路径，影响高可用与异常流测试覆盖。 |
| P0 | 历史会话超长文本 | 历史会话中已存储的字段长度超过 10000 字符的旧数据，本次升级后如何处理？ | 保持原状：历史会话中已存储的旧文本（无论是否 >10000）均按原逻辑读取，不做外置迁移 | 惰性迁移：历史会话读取时若检测到旧字段 >10000，首次访问自动迁移到外置存储并切换为 chunk 引用 | 无法设计历史会话回归用例，无法断言升级后老会话是否会因旧超长字段再次触发引擎崩溃，影响兼容性验收。 |
| P1 | 写入节点覆盖判定 | “大模型变量赋值、普通变量赋值、知识检索变量赋值、文件检索变量赋值、文件解析”等节点的“输出字段”超长时，是否也按 10000 阈值外置处理，还是仅作用于输出展示环节？ | 全节点统一外置：所有涉及变量读写/赋值的节点输出字段统一按 10000 阈值外置运行态 | 仅输出节点外置：内部赋值环节保留原结构，仅在最终输出（调试/回复）环节外置或分区展示 | 无法确认中间变量（如知识检索结果赋给变量、代码执行结果赋给变量）是否仍可能因超长击穿引擎，影响 P0 的崩溃问题是否真正解决。 |
| P1 | chunk 切分与展示 | 超长文本在调试/预览/发布/接口调试页面按 chunk 分区展示时，chunk 切分粒度是多少？是否支持复制全文、加载更多、搜索等交互？ | 固定粒度切片：按统一 chunk 大小（如 2000 字）切分，前端逐片渲染，支持全部展开与复制全文 | 按节点输出原结构切片：沿用上游外置时的 chunk 划分，前端只做对应渲染与翻页，不提供额外加工 | 无法对前端超长文本展示编写 UI 断言与交互用例，无法验证“调试页面输出分区展示完整超长文本”的兼容性承诺。 |
| P1 | 并发与幂等性 | 同一变量被多个下游节点同时消费、或同一变量被多次写入并发覆盖时，chunk 引用与外置存储如何保证一致性？ | 引用每次独占生成：每次写入生成新 chunk 引用，旧引用失效；并发读取仅读取本次写入对应副本 | 引用复用共享：多次写入复用同一 chunk，外置存储按最新内容覆盖；并发读取共享同一份内容 | 无法设计并发读写场景的回归用例，存在并发覆盖、内容错乱、引用指向旧内容等隐藏缺陷无法被验证。 |
| P2 | 对话流日志口径 | “对话流日志展示变量的所有字段”中的“所有字段”是指所有变量字段，还是特指超长文本字段也要完整写入日志？ | 展示所有变量条目：日志按字段名展示所有变量值，超长文本字段也以 chunk 分区或引用形式完整记录 | 仅展示关键/常用变量：日志展示变量名清单与代表值，超长文本以引用或摘要形式记录，避免日志爆炸 | 无法断言日志写入的字段范围与体积边界，可能因日志过大影响检索/落盘，需补充日志回归断言。 |
| P2 | Go 版本改造边界 | Python 版本改造范围内的“所有涉及变量读写/解析的节点”与未来 Go 版本改造的边界如何划分？本次是否需要为 Go 版本预留接口契约或抽象层？ | 本次仅实现 Python 版本：Go 版本独立设计，接口/存储格式不强约束，未来兼容风险由 Go 版本重构承担 | 面向 Go 版本预留抽象：本次 Python 实现的统一变量读取方法、chunk 引用结构对外暴露稳定契约，方便 Go 版本复用 | 无法判断本次 Python 实现的接口契约在 Go 版本切换时的复用性，影响跨语言回归与一致性验证范围。 |
