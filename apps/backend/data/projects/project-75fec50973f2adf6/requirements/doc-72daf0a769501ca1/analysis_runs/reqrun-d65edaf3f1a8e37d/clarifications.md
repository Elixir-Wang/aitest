# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 测试影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 外置存储与 chunk 引用 | 节点输出字段超过 10000 字符时，chunk 引用信息包含哪些字段（如引用 ID、chunk 数量、总长度、偏移量等），以及 chunk 的切分粒度是多少？ | 引用信息包含完整内容 ID、chunk 总数与每 chunk 长度，下游按需按 chunk 顺序读取并拼接 | 引用信息仅包含完整内容 ID，下游一次性读取完整内容并在节点侧自行切分处理 | 无法为外置存储写入、引用信息读取、按 chunk 展示等场景设计等价类与边界用例，也无法断言下游节点消费时的内容完整性。 |
| P0 | 下游消费判定 | “仅判断/展示/传递”与“真正消费变量”在不同节点类型上的判定口径是什么？哪些节点类型被归为仅判断/展示/传递，从而不读取完整内容？ | 明确列举属于“仅判断/展示/传递”的节点类型清单（如条件判断、语义判断等），其余节点默认按“真正消费变量”读取完整内容 | 由节点自身声明消费模式（仅判断/展示/传递 vs 真正消费），引擎按声明决定是否读取完整内容 | 无法判断条件判断、语义判断、代码执行、文本回复等节点是否读取完整内容，导致分支用例与兼容性用例无法设计。 |
| P0 | 单字段长度限制 | 单个字段长度限制 20000 字，是对外置前/外置后文本的总长度限制吗？触发限制后是截断、报错还是写入失败？ | 对任意字段最终写入文本做 20000 字上限校验，超出则按业务既定策略处理（如报错并提示用户） | 仅对未触发外置存储的短文本路径生效 20000 字上限，外置存储路径只受 10000 字符外置阈值影响、不再校验 20000 字 | 无法对 10000–20000 字符区间以及 >20000 字符两个边界设计测试断言，也无法判断是否会产生“刚超 10000 字符却被 20000 字限制拒绝”的矛盾场景。 |
| P1 | 异常与恢复 | 外置存储数据库写入失败、读取失败或引用失效时，节点应如何处理？是否重试？是否回滚上游输出？ | 数据库写入失败时节点报错并中断对话流，提示用户稍后重试；读取失败时按节点类型决定报错或降级 | 数据库写入失败时退化为短文本路径继续运行（仅适用于不会触发引擎崩溃的体积），读取失败时上游重试一次后再报错 | 无法设计数据库故障、引用失效、读取超时的异常分支用例，也无法对引擎稳定性这一核心目标进行风险验证。 |
| P1 | 前端分区展示 | 超长文本在 debug、预览、对话流测试、单节点调试、发布后页面、API 接口调试中的分区展示交互是怎样的？分页/懒加载/失败提示如何处理？ | 前端按 chunk 顺序分页加载，提供翻页与单 chunk 重试入口，单 chunk 加载失败时仅该块显示重试按钮 | 前端一次性按 chunk 顺序渲染完整内容（不分页），整体加载失败时统一提示并支持重新加载 | 无法对前端分区展示进行可用性、加载失败、滚动/翻页等交互断言，也无法验收“超长文本输出可被完整查看”这一目标。 |
| P1 | 日志展示 | 对话流日志中“展示变量的所有字段”对于外置存储的超长文本，是展示完整内容、还是仅展示 chunk 引用信息？是否会对日志体积与性能造成影响？ | 日志中按需读取并展示超长文本的完整内容，并接受因此带来的日志体积增大 | 日志中仅展示 chunk 引用信息（外置存储 ID、chunk 数等），不展开完整内容，避免日志体积膨胀 | 无法判断日志场景下超长文本的可观察结果，可能造成日志用例设计与线上回归范围不一致。 |
| P2 | 历史会话兼容 | 历史会话中已存的普通文本按原逻辑读取，但若同一字段在历史会话中存在“外置前/外置后”混合版本，应如何处理？ | 历史会话中的字段统一按写入时的存储形态读取，原短文本路径保持原样读取，不再重新外置 | 历史会话中的字段在读取时统一转换为新的引用形态（必要时回填外置存储），保证存储一致性 | 无法为历史会话回归场景设计存储形态断言，也无法评估跨版本历史数据对下游消费的影响。 |
| P2 | Go 版本范围 | Go 版本对话流的改造范围与本次 Python 版改造是否保持一致？是否在同一次发布内提供改造？ | 本次仅发布 Python 版改造，Go 版本在后续切流完成后再独立发布同等改造 | 本次同时发布 Python 与 Go 版本的同等改造，回归覆盖两套实现 | 无法判断本次需求验收是否需要覆盖 Go 版本，无法规划回归范围与多版本一致性测试。 |
