# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 测试影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 超长文本判定与存储阈值 | 字段文本长度为 10000 字符至 20000 字之间时，是统一启用外置存储并透传 chunk 引用，还是先尝试整段传递、再由运行态做长度兜底？以及单字段长度上限 20000 字的具体执行时点和超限处理方式是什么？ | 写入时一次性判定：长度>10000 字符即外置存储并透传引用；单字段>20000 字时按截断/拒绝策略明确禁止写入 | 运行态每节点判定：下游消费时才决定是否读取完整内容；20000 字为单节点输出字段硬上限，超出报错 | 无法设计长度边界用例，无法断言 10000/20000 临界处的存储路径与对外提示，也无法定位超限字段在不同节点的异常来源 |
| P0 | 下游消费节点读取策略 | 下游节点类型中，哪些属于"仅判断/展示/传递"仅用 chunk 引用，哪些属于"需要内容计算/输出"必须读取完整内容？该判定标准如何在节点实现中固定？ | 按本次改造方案中列出的节点类型显式区分：判断类（语义/条件）、传递类直接用引用；计算类（代码执行）、输出类（大模型回复、文本回复）触发完整读取 | 由下游节点按需自行决定是否读取，统一读取方法始终返回完整内容以避免隐式行为 | 无法对每个被改造的节点类型设计消费断言，无法定位引用与完整内容混用导致的回归问题 |
| P0 | 外置存储失败与引用失效 | 外置存储数据库写入失败或后续 chunk 引用失效时，超长文本是否回退到原结构直接传递、抛错终止运行，还是仅记录错误并使用空内容？ | 写入失败时立即报错，阻断当前节点或整条对话流；引用失效时下游报错并提示重新执行 | 写入失败时降级为原结构完整传递，引用失效时下游使用空内容并打日志 | 无法设计外置存储不可用场景下的异常恢复用例，无法断言对话流引擎在该场景下是否仍崩溃（原始痛点） |
| P1 | 历史会话兼容性 | 历史会话中已经按原结构存储的普通文本（≤10000 字符）迁移方案是什么？是否需要在历史会话中回填外置存储引用或保持原状仅按原逻辑读取？ | 保持原状：历史会话中已存普通文本按原逻辑读取，不生成外置存储引用 | 读取时按需重写：历史文本在新一轮执行时若超过 10000 字符再触发外置存储 | 无法覆盖历史会话跨升级运行时的兼容性测试，无法断言改造上线后旧会话执行不会触发引擎崩溃 |
| P1 | 对话流日志字段展示 | 对话流日志"展示变量的所有字段"是指完整展示原始文本（含 >10000 字符未截断内容），还是仅展示 chunk 引用详情（chunk 数、首块大小等元信息）？展示完整内容时是否同样走外置存储反查？ | 日志展示完整原始文本，>10000 字符时按 chunk 分区或完整回填 | 日志仅展示 chunk 引用元信息与摘要，正文按需通过引用按需拉取 | 无法设计日志相关测试用例，无法断言超长变量在日志中的可观测性与体积边界 |
| P1 | 调试页面 chunk 分区展示 | 调试页面（debug、预览、对话流测试、单节点调试、发布后页面、API 接口调试）按 chunk 分区展示时，单个 chunk 的展示粒度如何划分？是固定大小还是与外置存储切分粒度保持一致？ | 与外置存储切分粒度一致，使用相同的 chunk 块大小和顺序展示 | 按调试页面独立切分粒度（如每页固定字节/字符数），与存储切分粒度解耦 | 无法在调试页面对照存储侧切分设计断言，也无法覆盖跨页边界文本的完整性 |
| P2 | 字段长度计量口径 | 判定 10000 字符与 20000 字时使用的是字符数、字节数还是 Unicode 码点计数？中文、emoji、多字节字符如何统计？ | 统一按 Unicode 码点（code point）计数，对所有语言和 emoji 一视同仁 | 按字符（UTF-16 code unit）计数，emoji 可能按 2 个单位计入 | 无法设计含中文/emoji 的边界用例，无法准确给出超过阈值时的触发断言 |
| P2 | Go 版本改造时点 | Go 版本改造是否纳入本次验收范围？若在 Python 版本上线期间 Go 版本仍处于原状态，跨版本切换是否会因引用结构不一致导致历史会话执行异常？ | Go 版本暂不纳入本次验收，上线期间 Go 版本继续按原逻辑处理 | Go 版本同步改造，本次需同时验证 Python 与 Go 版本的一致性 | 无法判断本次上线跨语言版本的覆盖范围，无法设计 Go 版本回归用例 |
