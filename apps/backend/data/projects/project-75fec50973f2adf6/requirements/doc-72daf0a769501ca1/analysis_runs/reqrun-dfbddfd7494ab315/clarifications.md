# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 超长文本存储 | 单个字段长度超过20000字符时如何处理？是截断、拒绝写入还是分多个字段存储？ | 超过20000字符时拒绝写入并提示用户文本超长 | 超过20000字符时自动截断至20000字符 | 影响超长文本的边界处理逻辑，阻塞开发 |
| P0 | 超长文本存储 | chunk引用信息的具体数据结构是什么？包含哪些字段？ | 包含 chunk_id（唯一标识）、存储位置（表名/集合名）、文本长度、分片序号 | 仅包含 chunk_id（唯一标识），通过统一查询接口获取完整内容 | 影响数据库表结构设计和运行态数据传输格式，阻塞开发 |
| P0 | 超长文本存储 | 超长文本存入数据库的表结构是什么？是否需要分片存储？ | 单表存储，每条记录存储一个完整超长文本，字段包括 id、文本内容、创建时间等 | 分片存储，超长文本按固定大小切分为多个chunk分别存储，每条记录存储一个chunk | 影响数据库设计和读写性能，阻塞开发 |
| P1 | 消费节点还原 | 如何判断下游节点是否需要读取完整内容？判断规则是什么？ | 按节点类型硬编码判断：大模型回复、文本回复等消费类节点需要读取；条件判断、语义判断等判断类节点不读取 | 由节点配置决定：每个节点增加一个'是否需要完整内容'的配置开关 | 影响下游节点读取逻辑的实现方式 |
| P1 | 超长文本存储 | 外置存储的超长文本是否有生命周期？是否需要定期清理？ | 随会话生命周期管理，会话结束后清理对应的超长文本数据 | 永久保留，不主动清理 | 影响数据库存储容量和数据清理策略 |
| P1 | 异常处理 | 下游节点根据引用信息读取完整内容时，如果引用信息失效或数据库中的数据被删除，如何处理？ | 抛出明确异常，提示'超长文本数据已丢失，请重新处理' | 静默降级，返回空字符串或部分可用数据，不影响对话流继续运行 | 影响系统稳定性和用户体验 |
| P1 | 并发与一致性 | 多个下游节点并发读取同一个超长文本时，是否需要考虑并发控制和数据一致性？ | 不需要特殊处理，数据库读取天然支持并发 | 需要加锁或使用事务，防止读取过程中数据被修改或删除 | 影响高并发场景下的系统稳定性 |
| P2 | 前端展示 | 超长文本按chunk分区展示时，前端的交互方式是什么？ | 分页展示，每页显示一个chunk，用户点击翻页查看 | 滚动加载，用户向下滚动时自动加载下一个chunk | 影响前端UI设计和用户体验 |
| P2 | 对话流日志 | 对话流日志中展示变量的所有字段，对于超长文本是展示完整内容还是引用信息？ | 展示完整文本内容（从数据库读取后展示） | 展示引用信息（chunk_id等），并提供查看完整内容的入口 | 影响日志系统的存储和展示设计 |
