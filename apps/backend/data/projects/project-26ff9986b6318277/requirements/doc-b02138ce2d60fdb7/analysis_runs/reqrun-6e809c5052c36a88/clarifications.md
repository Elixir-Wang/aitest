# 待澄清问题

| 优先级 | 模块/对象 | 澄清问题 | 选项 A | 选项 B | 影响 |
|-------|----------|---------|--------|--------|------|
| P0 | 模型配置管理 | 模型配置管理的具体功能和操作流程是什么？原文该章节只有标题，无任何描述。 | 提供 CRUD 接口（增删改查模型配置），包括模型名称、目标模型、端点、API_KEY、协议类型、代理、分类等字段的维护 | 仅在初始化时从数据库加载，不提供运行时变更接口，所有变更通过 DBA 手工执行 SQL | 影响模型配置模块的接口设计和开发工作量，关系到是否需要管理后台或 API |
| P0 | 架构设计 | SDK（llm-gateway-g-sdk）与 Web 服务（llm-gateway-g）之间的关系是什么？SDK 是直接调用 LLM 还是经过 Web 服务转发？ | SDK 内部直接通过数据库配置调用 LLM，不经过 Web 服务，避免任何 HTTP 损耗 | SDK 内部还是通过 HTTP 调用 Web 服务，由 Web 服务统一对外提供 OpenAI 协议和鉴权 | 决定 SDK 的实现复杂度、性能和部署形态，影响整体架构 |
| P0 | 切流策略 | Cybertron 的"按照模型进行逐渐切流"具体如何实现？`UseLLMGatewaySDK` 是配置中心热加载还是发布时确定？ | 配置中心热加载，运行时动态生效，新增模型无需重启服务即可切流 | 服务启动时一次性加载，变更后需要重启服务才能生效 | 影响配置变更的响应速度和运维方式，决定是否需要监听配置变更事件 |
| P0 | API_KEY 鉴权 | 业务方调用 llm-gateway-g 时，API_KEY 的传递和校验机制是什么？ | 通过 HTTP Header（如 Authorization: Bearer xxx）传递，Web 服务校验 api_keys 表中的 source 字段对应的 api_key | 调用方在请求 body 中通过 source_model_api_key 表映射，将 source_api_key 转换为对应厂商的 provider_api_key | 影响 Web 服务的鉴权实现和 source_model_api_key 表的使用方式 |
| P0 | API_KEY 存储安全 | 数据库中 api_key、provider_api_key 等敏感字段是否需要加密存储？ | 需要加密存储（如 AES），应用层解密后使用，避免数据库泄漏导致凭证外泄 | 明文存储即可，依赖数据库本身的访问控制和网络隔离 | 影响数据安全等级和实现复杂度，关系到是否符合公司安全规范 |
| P0 | 协议兼容 | llm-gateway-g 对外提供 OpenAI 协议时，如何处理非 OpenAI 协议的厂商（如公司内自研模型）？ | 通过 llm_model_config 中的 interface_protocol 字段标识，Web 服务内部做协议转换，对外统一暴露 OpenAI 格式 | 仅透传 OpenAI 协议，非 OpenAI 协议的模型由调用方自行适配，网关不做转换 | 决定网关的协议适配范围和工作量，影响公司内模型的接入方式 |
| P1 | 容错降级 | 当某个 LLM 模型调用失败时，网关是否有重试或降级策略？ | 支持配置重试次数和备用模型（fallback），主模型失败后自动切换到备用模型 | 直接透传错误给调用方，不做重试和降级，由业务方自行处理 | 影响网关的可用性和业务连续性，关系到是否需要在 llm_model_config 中增加 fallback 字段 |
| P1 | 代理配置 | proxy_config 表中 proxy_url 的使用场景是什么？是用于调用 LLM 时的网络代理还是其他用途？ | 用于访问外网 LLM（如 OpenAI）时的 HTTP 代理，解决内网访问限制问题 | 用于内网 LLM 服务的反向代理或负载均衡 | 决定 llm_model_config 中 proxy_id 字段的关联逻辑和代理的实现方式 |
| P1 | 日志监控 | 网关调用 LLM 时是否需要记录请求/响应日志和调用链路？本次是否包含？ | 需要记录完整的请求/响应日志和耗时，用于问题排查和后续 Token 计量基础 | 仅记录关键信息（模型、调用方、耗时、是否成功），不记录请求/响应内容 | 影响可观测性和后续 Token 计量功能的实现基础 |
| P1 | protocol_options | llm_model_config 表中 protocol_options（JSON 字段）的用途和结构是什么？ | 存储各厂商特有的协议参数（如 temperature、top_p、max_tokens 等），网关透传给对应厂商 | 存储协议转换规则，用于非 OpenAI 协议到 OpenAI 协议的映射配置 | 影响协议适配的灵活性和配置复杂度 |
| P1 | SDK 接口 | llm-gateway-g-sdk 暴露给 Go 服务的接口形态是什么？是函数式 API 还是封装了完整 Client 对象？ | 提供高层封装的 Client 对象（如 gatewayClient.Chat()），屏蔽底层 HTTP/协议细节，对业务友好 | 提供底层函数调用，保留与 OpenAI SDK 类似的灵活度，由业务方自行组装请求 | 决定 SDK 的易用性和灵活性，影响业务方接入成本 |
| P1 | 自动初始化 | 自动初始化流程触发的时机和频率是什么？是否支持运行时配置变更热更新？ | 仅服务启动时执行一次，运行时变更需重启服务 | 启动时执行 + 定时（如每分钟）刷新配置 + 监听配置中心变更事件实现热更新 | 决定配置变更的响应实时性和运维复杂度 |
| P2 | 多租户隔离 | 不同业务方（source）调用同一个模型时，是否需要隔离或区分？ | 同一模型对所有 source 共享，API_KEY 通过 source_model_api_key 表按调用方分配各自凭证 | 同一模型对所有 source 完全共享 provider_api_key，不区分调用方 | 影响 source_model_api_key 表的业务语义和后续计费/限粒度 |
| P2 | 流式响应 | 是否需要支持 SSE 流式响应（OpenAI 的 stream 模式）？ | 需要支持，Web 服务和 SDK 都需实现 SSE 流式透传 | 仅支持非流式一次性响应，流式功能后续迭代 | 影响 Web 服务的响应处理和 SDK 的实现方式，对话体验差异显著 |
| P2 | 超时控制 | 调用 LLM 的超时时间如何配置？是固定值还是按模型可配置？ | 在 llm_model_config 中新增 timeout 字段，按模型灵活配置 | 使用统一的全局默认超时（如 60s），所有模型共用 | 影响大模型调用的响应控制和用户体验 |
