# 单接口自动化用例生成

针对输入中的指定 endpoint 生成结构化接口自动化用例。用例数量只由接口事实和适用测试点决定，不设固定数量、不追求奇偶、不按比例凑数，也不因优先级较低而省略有效测试点。

## 范围

生成单接口的成功、参数、契约、鉴权、安全、查询、业务规则、数据影响、重复操作、上传和下载用例。

不生成：

- 多接口调用链、上游输出传递或跨接口业务流程；
- 并发、压测、限流、超时、重试、熔断、依赖故障等稳定性专项；
- 异步任务、回调、Webhook、流式协议专项。

## 事实边界

1. 只使用接口定义、环境摘要、历史用例和用户目标提供的事实。
2. 不得编造路径、方法、字段、枚举、状态码、角色、资源状态、文件限制或业务规则。
3. 字段名称只能辅助识别分页、排序、搜索和成对范围等通用语义，不能据此创造业务规则。
4. 已声明错误响应但触发条件或数据未知时，生成待补充数据用例，并在 `test_data` 明确缺少什么；不得虚构触发条件。
5. 环境变量和敏感数据使用 `${VARIABLE_NAME}`，不得输出 token、cookie、密码或机器绝对路径。
6. `include_security_cases=false` 时只覆盖鉴权缺失、空值等契约负向；为 `true` 时才增加错误凭据、过期凭据、无权限、越权和输入安全场景。

## 强制工作流

在内部完成以下步骤，只输出最终结构化结果：

1. 提取 endpoint 方法、路径、参数位置、请求体、响应、鉴权和 schema。
2. 建立全部字段清单，递归展开嵌套对象、数组元素和组合 schema。
3. 为每个字段建立适用测试点，区分 required、optional、nullable、default、example 和约束。
4. 建立接口级测试点：成功响应、请求契约、鉴权、查询语义、业务规则、数据影响、重复操作、上传或下载。
5. 识别明确的字段关系：条件必填、互斥、依赖、起止、上下限和组合 schema。
6. 每个适用测试点至少生成一条能独立验证该目标的用例。
7. 对无明确关系的独立字段使用“合法基线 + 单变量变化”；不要生成字段笛卡尔积。
8. 补齐遗漏后删除真重复，并逐条校验标题、请求、预期和断言一致。

## 测试点全集

### 1. 成功路径

- 最小合法请求；
- 包含全部可选字段的完整合法请求；
- 每个明确合法枚举或具有不同业务含义的合法分支；
- 每个文档明确的主要成功响应形态。

只有当完整请求相对最小请求增加了真实覆盖点时，才分别生成。

### 2. 字段存在性和可空性

- 每个 required 字段缺失；
- optional 字段不传和传合法值；
- 空字符串、纯空白、`null`、空对象、空数组，仅在字段类型和 nullable 语义适用时生成；
- requestBody 必填时区分请求体不发送与空对象/空内容。

“缺失”“空字符串”“null”和“空容器”是不同测试点，不得混用。

### 3. 类型、格式和约束

- 字段类型错误；
- `format`、`pattern` 的合法值与非法值；
- `minLength/maxLength`：边界内、边界值、边界外；
- `minimum/maximum`、exclusive 边界：边界内、边界值、边界外；
- 数值的 0、负数、小数和精度，仅在类型或约束适用时生成；
- enum 的每个合法值和至少一个非法值；
- array 的空、单元素、数量边界、越界、重复元素和元素非法，仅在相应约束适用时生成；
- `oneOf/anyOf/allOf/discriminator` 的合法分支、缺失分支和冲突分支。

不得为没有对应约束的字段虚构最大长度、数值范围或文件大小。

### 4. 字符与序列化

仅对字符串和相应参数位置生成适用项：

- 前后空格、纯空白、中文、Unicode、特殊字符、换行；
- query/path 的 URL 编码；
- 数组 query 的 OpenAPI style/explode 表达；
- 重复 query key、布尔和数字序列化，仅在契约或框架语义明确时生成；
- 未声明字段：验证拒绝或忽略行为，预期必须有 schema 或历史事实支持。

### 5. 日期、时间和字段关系

- 合法与非法日期时间格式、时区、闰年、月末和精度；
- start/end、from/to、begin/end、min/max、lower/upper：小于、等于、大于；
- 文档明确的条件必填、互斥、依赖和组合约束；
- 不明确最大跨度、未来时间或历史时间规则时，不得自行设定预期。

### 6. 鉴权与安全

- 已声明鉴权信息缺失和空值；
- 开启安全用例时，覆盖有事实支持的错误、过期、无权限、越权或资源归属不匹配；
- 开启安全用例时，对适用文本字段覆盖注入、脚本和路径穿越输入，但只断言契约已声明的拒绝或安全处理结果；
- 检查明确响应 schema 不应返回的敏感字段时，不得使用当前执行器不支持的断言伪装可执行性。

### 7. 查询语义

存在相应 query 参数时覆盖：

- 默认分页、第一页、边界页、非法页码或页大小；
- 合法和非法排序字段/顺序；
- 过滤、搜索的匹配、无匹配、空值和非法值；
- 多个查询条件的明确关系；无关系字段只做必要的 pairwise 组合，不做全排列。

### 8. 业务规则、数据影响和重复操作

只依据描述、历史用例或用户目标中的明确事实覆盖：

- 资源存在/不存在、允许/禁止状态、已删除资源；
- 创建、更新、删除、绑定、发布等操作成功后的数据变化；
- 失败请求不产生副作用，更新时未修改字段保持不变；
- 重复创建、重复更新、重复删除、重复提交和幂等键语义。

这些仍是同一 endpoint 的独立重复调用，不扩展成多接口场景。

### 9. 请求和响应契约

- 保持 `request.method` 和 `request.path` 与输入 endpoint 完全一致；当前流水线不生成错误 Method 或错误 Path 用例；
- Content-Type 缺失或错误只在请求明确声明 Content-Type 且执行器能够表达时生成；
- 每个文档声明的 4xx/5xx 响应至少有对应测试点；触发条件未知时标记待补充数据；
- JSON 响应覆盖关键字段存在和文档明确的固定值；
- 下载响应覆盖状态码、Content-Type、Content-Disposition、响应体非空，以及文档提供哈希时的 SHA-256。

## 上传接口

OpenAPI 声明 `multipart/form-data` 或文件字段时，使用 `request.files`，不得把文件写进 JSON body：

```json
{
  "method": "POST",
  "path": "/files",
  "body": {"description": "sample"},
  "files": {
    "file": {
      "path": "${API_UPLOAD_FILE_PATH}",
      "filename": "sample.txt",
      "content_type": "text/plain"
    }
  }
}
```

- `body` 作为 multipart 普通表单字段发送；
- `files` 的 key 必须等于 OpenAPI 文件字段名；
- 多文件字段使用文件描述对象数组；
- 成功上传使用环境变量提供真实文件路径；
- 文件缺失用例省略对应 `files` 字段；
- 文件类型、扩展名、大小和数量只按文档声明的限制生成；需要特定文件而环境未提供时，在 `test_data` 写明变量和准备要求。

## 下载接口

下载接口保持普通 `request`，断言使用当前执行器支持的类型：

- `status_code`；
- `content_type`，expected 为 Content-Type 的完整值或稳定子串；
- `header_exists`，path 为响应头名称；
- `header_equals`，path 为响应头名称；
- `body_not_empty`；
- `body_sha256`，仅在文档提供固定 SHA-256 时使用。

资源不存在、鉴权失败等仍按普通负向用例生成，不对错误响应执行下载正文断言。

## 组合与去重

1. 单字段约束逐字段完整覆盖。
2. 明确字段关系完整覆盖有效、边界和无效关系。
3. 无关系字段使用合法基线加单变量变化；可选字段只做必要 pairwise。
4. 不合并不同字段、不同边界方向、不同合法枚举或不同预期结果。
5. 只有测试目标、变化字段、输入等价类、预期状态码和断言全部相同时才删除重复。

## 优先级与覆盖类型

- `P0`：核心成功、认证授权、关键写入/删除/发布、资金或高风险数据影响；
- `P1`：普通成功、关键必填、主要错误响应、关键边界；
- `P2`：常见空值、类型、格式、业务异常；
- `P3`：低频字符、兼容性和非核心边界。

优先级只用于排序，不得用于截断测试点。

- `positive`：成功请求和成功响应契约；
- `negative`：缺失、类型/格式错误、普通鉴权、业务拒绝和错误响应；
- `boundary`：长度、数值、日期、分页、数组数量和范围关系边界；
- `security`：仅安全开关启用时的错误凭据、权限和安全输入；
- 不生成 `scenario`。

## 请求和断言规则

1. `endpoint_id`、`request.method`、`request.path` 必须与输入 endpoint 一致。
2. path 保持 OpenAPI 模板；具体 path 参数值记录在 `test_data`，避免与当前落库校验冲突。
3. query/body/files 只能使用接口定义中存在的字段。
4. 除目标变量外，其余请求字段保持合法基线，确保失败原因唯一。
5. 每条用例至少包含一个 `status_code` 断言。
6. JSON 只使用 `jsonpath_exists` 和有明确固定预期时的 `jsonpath_equals`。
7. 二进制下载不得使用 JSONPath 断言。
8. 不输出标签、状态、`notes`、`preconditions`、`variables` 或 `data_origin`。

## 输出前检查

逐项检查，发现遗漏直接补充，不输出检查过程：

1. 是否递归分析了每个字段和每个声明约束；
2. 是否为每个适用测试点生成了用例；
3. 是否遗漏字段关系、查询语义、鉴权、数据影响、上传或下载；
4. 是否生成了无事实依据的字段、限制、状态码或业务规则；
5. 标题中的缺失、空值、非法值或边界是否真实体现在请求；
6. 非目标字段是否保持合法，预期是否能归因于目标变化；
7. 上传是否使用 `files` 和环境变量路径，下载是否避免 JSONPath；
8. 是否存在真重复；
9. `summary` 数量是否等于 `cases` 数量。

## 输出格式

只返回符合 `ApiAutomationGenerationResult` 的结构化结果：

```json
{
  "summary": "生成 3 条接口自动化用例，覆盖最小成功请求、必填字段缺失和下载内容校验。",
  "cases": [
    {
      "title": "下载文件 - 成功返回非空文件",
      "priority": "P1",
      "endpoint_id": "apiend-1",
      "coverage": "positive",
      "source": "ai_generated",
      "request": {"method": "GET", "path": "/files/{file_id}", "query": {}, "headers": {}},
      "test_data": {"file_id": {"value": "${API_FILE_ID}"}},
      "expected": {"status_code": 200, "content_type": "application/octet-stream"},
      "assertions": [
        {"type": "status_code", "path": "", "expected": 200},
        {"type": "content_type", "path": "", "expected": "application/octet-stream"},
        {"type": "body_not_empty", "path": "", "expected": true}
      ]
    }
  ]
}
```

不得输出 Markdown 或额外解释。
