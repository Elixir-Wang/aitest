# 测试设计方法

## 覆盖维度

对每个功能点至少考虑以下维度：

1. 功能测试：主流程、正向路径、核心规则。
2. 异常测试：输入错误、状态不满足、依赖失败、超时或中断。
3. 边界测试：空值、最小值、最大值、临界值、数量限制、时间限制。
4. 安全测试：未登录、无权限、越权访问、敏感操作。
5. 性能测试：仅当需求明确性能要求时生成。
6. 兼容测试：仅当需求明确终端、浏览器或版本要求时生成。

## 六维扫描法

对每个功能点检查：

1. 触发条件与前置：谁可以触发，什么时候可以，需要什么数据。
2. 边界与约束：格式、长度、数量、时间、范围。
3. 异常与恢复：失败提示、重试、回滚、补偿。
4. 状态与时序：可操作状态、目标状态、并发或重复提交。
5. 权限与隔离：角色权限、项目隔离、数据归属。
6. 数据生命周期：创建、修改、删除、归档、审计。

## 优先级

- P0：核心主流程、阻断业务使用的场景。
- P1：重要分支、常见异常、高风险规则。
- P2：边界条件、辅助流程、低频异常。
- P3：体验优化、兼容性补充、非关键建议。

高风险场景优先级不低于 P1：

- 额度消耗、权限变更、不可逆操作。
- 权限控制和数据隔离。
- 并发、幂等、事务一致性。
- 第三方系统调用。
- 数据删除、归档、不可逆操作。

## 待确认处理

需求未说明的业务规则不能被写成确定预期。

可以生成测试用例，但必须在 `notes` 中标记：

```text
待确认：需求未说明连续输错密码后的锁定规则。
```

预期结果也应保持可验证但不编造细节，例如：

```text
系统按已确认的密码错误处理规则给出提示或限制。
```
