# 可测试性检查清单

用于发现 QA 和验收缺口。

## 可测试性问题

对每个模块或能力检查：

- 测试目标是什么？
- 谁执行动作？
- 需要什么角色、权限、租户或账号状态？
- 需要哪些前置条件和配置？
- 需要哪些测试数据？
- 哪条操作路径触发行为？
- 哪个结果可以被观察？
- 哪些状态或数据会变化？
- 期望出现什么错误信息、通知、日志或审计记录？
- 边界值是什么？
- 必须处理哪些非法输入？
- 有哪些异常路径和恢复路径？
- 哪些时间、并发或一致性规则重要？
- 集成失败时预期行为是什么？

## 测试覆盖缺口检查

需求分析阶段不生成完整 QA 测试用例，只识别会影响后续测试设计和验收判断的缺口：

- 功能是否有明确通过/失败标准。
- 用户角色、权限、租户、账号状态是否足以执行测试。
- 前置条件、系统状态、配置和依赖服务是否明确。
- 测试数据是否可准备，数据字段含义是否清楚。
- 操作路径、状态流转、分支流程和触发条件是否可复现。
- 预期结果是否可观察，包括页面提示、接口响应、数据变化、日志、通知和审计记录。
- 边界值、无效输入、异常路径、错误提示和恢复策略是否覆盖。
- 性能、安全、权限、兼容性等非功能验收是否有可度量标准。

## 验收标准格式

优先识别来源是否能支持类似下面的验收标准。若不能支持，判断是进入待澄清还是覆盖审计。

```gherkin
Given 用户已使用有效账户登录
  And 用户购物车中已有商品
When 用户点击“提交订单”按钮
Then 系统创建带唯一订单 ID 的订单
  And 用户在 5 分钟内收到确认邮件
  And 库存立即扣减
```

检查清单格式也可以接受：

```markdown
- 用户可以输入邮箱和密码
- 系统在提交前校验邮箱格式
- 无效凭据显示清晰错误
- 5 次失败后锁定账户
```

## 何时创建待澄清问题

当来源没有定义 QA 必须知道的值或规则时，创建问题，例如：

- 重试次数、锁定时长、过期时间
- 允许的状态流转
- 必填和选填字段行为
- 权限归属
- 精确错误信息或用户可见结果
- 数据同步或一致性规则
- 超时、重试或补偿行为

典型待澄清问题：

- 验证码连续输错达到多少次后锁定登录尝试，锁定多久？
- 管理员是否可以代用户重置 MFA，还是只能引导用户自助重置？
- 订单取消后库存何时释放，支付已完成时如何退款？
- 审计日志需要保留多久，哪些字段必须脱敏？

## 何时只使用覆盖审计

以下情况只使用 `coverage_audit`，不创建待澄清问题：

- 缺口是一般验证风险，不是业务决策
- 需求已足够清晰，但需要下游测试设计
- 来源已经隐含答案，只需要证据映射

典型覆盖审计记录：

- 主流程已清楚，但缺少自动化测试数据准备说明。
- 来源明确说明短信通知，但没有列出通知模板，需在测试设计阶段补模板断言。
- 非功能目标已给出，但需要性能测试环境和压测数据集。

## 非功能可测试性

非功能需求只有包含可度量标准时才可测试：

- 性能：响应时间、吞吐量、并发量、数据量
- 可用性：可用率、RTO、RPO、故障切换行为
- 安全：认证、授权、加密、审计、留存
- 兼容性：浏览器、设备、操作系统、API 版本
- 可访问性：标准和等级，例如 WCAG 等级
- 可维护性：相关时使用可观察的工程质量指标

## 质量评分参考

`quality_gate.testability_score` 可参考：

- 90-100：测试目标、角色、数据、路径、预期结果、边界、异常和非功能指标都清晰。
- 70-89：主体可测试，存在少量不会阻断测试设计的缺口。
- 50-69：只能覆盖主流程，关键规则、异常或数据缺口明显。
- 0-49：缺少可观察结果或核心业务规则，无法可靠设计测试。
