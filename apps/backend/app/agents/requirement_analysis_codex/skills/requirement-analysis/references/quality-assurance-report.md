# 质量保证报告

用于描述需求是否可测试，以及还剩哪些验证风险。

## 目的

回答：QA 是否能基于该需求设计可靠测试，仍有哪些覆盖缺口。

## 运行时去向

填充：

- `quality_assurance_report_markdown`
- `coverage_audit`
- `quality_gate`
- 相关 `key_gaps`
- `next_actions`

质量保证视图直接展示 `output/quality.md` / `quality_assurance_report_markdown`。不要假设前端会把质量门禁、覆盖审计拆成额外卡片或表格；报告本身必须自足、可读。

除非调用方明确要求，否则不要把独立质量保证报告写入 `analysis.md`。

## 质量保证 Markdown 结构

```markdown
# 质量保证

## 质量摘要
- 当前需求是否足以支撑可靠测试设计
- 最主要的阻塞或风险
- 推荐优先处理顺序

## 质量门禁
- 结果：warning
- 可测试性评分：70

## 阻塞问题
- ...

## 风险警告
- ...

## 已通过检查
- ...

## 覆盖审计
| 模块 | 状态 | 原因 |
| --- | --- | --- |
| 登录 | pending_clarification | 缺少验证码错误次数 |

## 可测试性维度
| 维度 | 判断 | 说明 |
| --- | --- | --- |
| 测试目标 | 通过 | 主流程目标明确 |
| 异常路径 | 警告 | 缺少验证码错误次数 |

## 下一步建议
- ...
```

## 质量门禁

使用：

- `passed`：没有未解决的重要澄清项或可测试性问题。
- `warning`：测试可以继续，但存在已知缺口或假设。
- `blocked`：缺失或冲突信息阻断有意义的验证。

`testability_score` 取 0 到 100：

- 90-100：场景、规则、数据、预期结果和可度量非功能标准清晰
- 70-89：大体可测试，只有有限缺口
- 50-69：部分可测试，但缺少重要规则或路径
- 0-49：不足以支撑可靠下游工作

## 报告内容

质量保证报告至少覆盖：

- 质量门禁结果：`passed`、`warning` 或 `blocked`
- 可测试性评分及评分理由
- 阻塞问题：会阻止可靠设计、开发、测试或验收的事项
- 风险警告：可以推进但需要显式假设或后续补充的事项
- 已通过检查：来源已经足够支撑的验证点
- 覆盖审计：每个模块或关键能力的分析状态和原因
- 下一步建议：优先处理顺序和补充方向

报告可以使用表格，但必须是 Markdown 表格，不依赖前端专用组件。

## 质量指标写法

可以在 Markdown 中用表格表达质量指标：

```markdown
| 质量属性 | 判断 | 影响 |
| --- | --- | --- |
| 完整性 | warning | 缺少异常路径规则 |
| 清晰度 | passed | 主流程表达清楚 |
| 一致性 | passed | 未发现冲突 |
| 可测试性 | warning | 关键边界值待补充 |
```

但不要输出“前端应渲染三张卡片”“生成覆盖审计表格组件”等 UI 指令。

## 覆盖审计

每个 `coverage_audit` 条目应包含：

- `module_key`
- `module_name`
- `source_excerpt`
- `analysis_status`
- `reason`

`analysis_status` 使用：

- `analyzed`：来源足够清晰，可以完成分析
- `pending_clarification`：需要人工回答
- `not_testable`：缺少可观察的通过/失败标准
- `missing_detail`：已有部分描述，但细节不足

## QA 维度

检查：

- 测试目标
- 用户角色和权限
- 前置条件和系统状态
- 测试数据和数据准备
- 用户或 API 操作路径
- 预期 UI、API、数据、通知、日志或审计结果
- 边界值
- 非法输入
- 异常路径和恢复行为
- 状态流转
- 并发和时间相关规则
- 集成失败行为
- 可度量的非功能目标

## 问题严重程度

在报告中解释严重程度时使用：

- `blocker`：阻止可靠测试设计或阻断核心验收。
- `major`：测试可继续，但会造成明显覆盖缺口或高返工风险。
- `minor`：不阻断测试，只影响表达精度或补充断言。

## 示例

好：

```markdown
## 阻塞问题
- 登录验证码错误次数和锁定时长未定义，无法设计认证异常路径测试。

## 覆盖审计
| 模块 | 状态 | 原因 |
| --- | --- | --- |
| 登录 | pending_clarification | 缺少验证码错误次数、锁定时长和错误提示 |
```

差：

```text
质量保证 tab 应展示三个卡片：质量门禁、可测试性评分、覆盖审计数量。
```

## 写作规则

- QA 发现应说明验证影响，不要改写业务决策。
- 如果缺失测试输入只能由人工决定，应转成待澄清问题。
- 质量门禁理由要使用可度量、可验证的表达。
- 不要输出只适合前端框架消费的结构说明；质量保证报告就是一份普通 Markdown 文件。
- 不要在报告里复制完整待澄清问题清单，只说明这些问题对测试覆盖和质量门禁的影响。
