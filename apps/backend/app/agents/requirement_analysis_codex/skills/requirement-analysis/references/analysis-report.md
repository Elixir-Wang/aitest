# 需求分析报告

用于描述从主需求来源中已经理解和确认的内容。

## 目的

回答：当前需求说了什么、成熟度如何、哪些已确认缺口会影响后续工作。

## 内容

应包含：

- 文档目标和分析范围
- 来源中明确出现的业务背景和目标
- 已确认的范围和非范围边界
- 用户、角色、权限和参与方
- 模块清单、模块能力和职责
- 业务对象、字段、状态流转和业务规则
- 已知依赖和集成点
- 来源中明确出现的非功能需求
- 成熟度评估及证据
- 关键缺口分类和影响
- 测试覆盖影响摘要，但不要列出具体待澄清问题
- 质量门禁摘要和下一步建议

不应包含：

- 可由人工答复的问题清单
- 推荐答案选项
- 完整测试用例清单
- 通用教材式解释
- `approved`、`rejected`、`conditional approval` 等审批结论

## 建议 Markdown 结构

```markdown
# 需求分析报告

## 分析摘要
- 文档目标
- 当前可确认的业务目标
- 总体成熟度判断
- 关键风险摘要

## 需求成熟度
- 成熟度等级：RA0-RA5
- 判断依据
- 当前最影响下游工作的缺口类别

## 范围与边界
- 范围内
- 范围外
- 假设和约束
- 依赖系统或外部角色

## 模块与能力
- 模块清单
- 每个模块的职责
- 关键能力和业务对象
- 角色和权限

## 业务规则与数据
- 业务规则
- 校验规则
- 字段含义
- 状态流转
- 通知、日志、审计规则

## 关键缺口分类
- 按 `key_gaps` 类别分组
- 每个缺口说明影响
- 需要人工回答的具体问题不要写在这里

## 测试覆盖影响
- 哪些模块可直接进入测试设计
- 哪些模块存在覆盖风险
- 只写影响摘要，不复制待澄清问题清单

## 质量门禁摘要
- 质量门禁结果
- 可测试性评分
- 阻塞/警告原因摘要

## 下一步建议
- 优先补充项
- 推荐处理顺序
- 进入设计、开发或测试前的前置条件
```

## 写作规则

- 只陈述来源支持的内容。
- 不确定点先作为缺口分类说明，真正需要人工回答的问题放入 `clarification_questions`。
- 缺口描述按影响归类，不要写成问题清单。
- 使用短句和具体表达，避免宽泛咨询话术。
- 不输出“批准”“拒绝”“有条件批准”等传统评审决策。
- 不写完整测试用例，只写会影响测试覆盖的需求层面事实。
- 不要把 `output/quality.md` 的完整质量保证报告复制进来，只保留摘要。

## 缺口写法

好：

```text
登录异常路径缺少错误次数和锁定时长，影响认证异常流和自动化断言。
```

差：

```text
验证码连续输错达到多少次后应锁定登录尝试？
```

问题句应进入待澄清报告，不进入需求分析报告。
