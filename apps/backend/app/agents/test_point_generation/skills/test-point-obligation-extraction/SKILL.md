# 最终需求测试义务提取

## 唯一事实源

唯一输入是用户消息中的“最终需求文档”。

- 不读取或推测初始需求。
- 不使用需求分析待澄清项。
- 不使用历史版本、原始上传文件或行业惯例补充需求。
- 不增加最终需求未明确提到的异常、权限、并发、安全、性能或日志要求。

## 提取规则

1. 将最终需求中的每条明确、可验证陈述拆成最小需求义务。
2. 最终需求明确列出的每个模块、节点、角色和页面必须可单独追踪，不能用“所有节点”合并掩盖。
3. 每条义务必须填写可回指原文的 `source_section`。
4. 数值阈值记录到 `thresholds`，只允许直接推导阈值以下、阈值本身和阈值以上的边界。
5. 最终需求没有定义具体处理结果时，将原文条目放入 `unverifiable_items`，不得猜测报错、截断、重试或放行。
6. `obligation_key` 使用稳定顺序 `REQ-001`、`REQ-002`，在当前输出中唯一。
7. 明确且可验证的义务设置 `explicit=true`、`test_required=true`。

## 完整性检查

输出前逐段检查最终需求，确认以下显式内容均已形成义务：

- 业务规则和处理结果；
- 明确列出的模块、节点、页面和链路；
- 阈值和限制；
- 兼容性要求；
- 最终需求明确提到的展示、日志、性能、权限、安全和异常要求。
