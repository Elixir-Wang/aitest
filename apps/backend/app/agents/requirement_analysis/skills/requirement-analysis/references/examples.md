# 需求分析示例

这些示例用于判断信息应进入哪份产物：已确认内容进入 `analysis.md`，需要人工回答的事项进入 `clarification.md` 和结构化字段，测试影响进入 `quality.md`。

## 模糊性能需求

原文：

```text
系统应当快速且响应灵敏。
```

问题：

- “快速”“响应灵敏”不可度量。
- 未说明哪些操作需要快。
- 未给并发量、数据量、百分位或测量条件。

需求分析报告写法：

```markdown
## 关键缺口分类
- 性能指标缺口：来源只要求“快速且响应灵敏”，没有给出操作范围、响应时间、并发量或数据量，影响性能设计和验收标准。
```

待澄清报告写法：

```markdown
## CQ-001 性能
- 模块Key：performance
- 类型：clarification
- 维度：boundary_value
- 严重级别：major
- 问题：哪些关键操作需要满足响应时间指标，各自的目标响应时间、并发量和数据量是多少？
- 影响：不确认会导致性能测试无法设定通过/失败标准。
- 来源：主需求只说明“快速且响应灵敏”。
- 选项A：核心查询 2 秒内响应|核心查询在 1,000 并发用户、100 万条数据下，95% 请求应在 2 秒内响应。
- 选项B：关键页面 3 秒内加载|关键页面在正常网络条件下，95% 首屏加载时间应小于 3 秒。
```

质量保证报告写法：

```markdown
## 风险警告
- 性能验收缺少可度量指标，当前只能覆盖功能正确性，无法设计可靠的性能通过/失败断言。
```

## 不完整通知需求

原文：

```text
订单状态变化时系统应发送通知。
```

待澄清点：

- 通知渠道是什么：站内信、短信、邮件、推送？
- 哪些状态变化触发？
- 通知给谁？
- 通知内容和发送时限是什么？

可写入初步需求的推荐选项示例：

```markdown
订单状态变为“已发货”时，系统应在 5 分钟内向下单用户发送邮件通知，通知内容包含订单号、新状态、物流单号、物流链接和预计送达日期。
```

## 冲突需求

原文：

```text
注册时手机号必填。
为了降低注册门槛，手机号应为可选。
```

待澄清报告写法：

```markdown
## CF-001 注册
- 模块Key：registration
- 类型：conflict
- 严重级别：blocker
- 问题：注册时手机号到底是必填还是可选？
- 影响：不裁决会影响注册表单、字段校验、数据模型和注册自动化用例。
- 来源：同一来源同时出现“手机号必填”和“手机号可选”。
- 选项A：手机号必填|用户注册时必须填写手机号，系统应校验手机号格式并确保手机号唯一。
- 选项B：手机号可选|用户注册时手机号为可选字段，仅在用户启用短信通知或短信验证时要求填写并验证。
```

## 不可测试安全需求

原文：

```text
系统应当安全并保护用户数据。
```

改写方向：

```markdown
系统应通过以下安全控制保护用户数据：
- 强制密码复杂度：至少 12 位，包含大小写字母、数字和特殊字符。
- 15 分钟内连续 5 次登录失败后锁定账户 15 分钟。
- 所有传输中数据使用 TLS 1.3。
- 静态敏感数据使用 AES-256 加密。
- 记录所有认证尝试，包含时间戳、用户标识、IP 地址和结果。
```

质量保证报告应指出：如果来源没有这些具体规则，安全需求无法形成可验证验收标准。

## 用户故事验收标准不足

原文：

```text
作为用户，我想搜索商品，以便找到我需要的东西。

验收标准：
- 搜索可用
- 展示结果
```

问题：

- 未说明搜索入口、关键词、排序、分页、无结果、错误输入、响应时间。
- “搜索可用”不是可执行验收标准。

更好的验收标准形态：

```gherkin
Given 用户在网站任意页面
When 用户在搜索框输入“laptop”并提交
Then 系统应在 2 秒内展示匹配商品列表
  And 每个结果展示商品图片、名称、价格、评分和库存状态

Given 用户搜索不存在的关键词
When 没有商品匹配
Then 系统显示“未找到结果”
  And 展示搜索建议或热门分类
```

如果来源没有这些信息，不要直接补全为事实；应进入待澄清或质量保证风险。
