# 需求分析 v2.0

基于业界最佳实践（BABOK、IREB、IEEE 830）的三块核心架构。

## 使用场景

- 评审需求文档（BRD、SRS、用户故事）
- 验证验收标准完整性
- 识别需求缺口、冲突、模糊表述
- 评估非功能需求覆盖
- 生成待澄清问题列表

## 工作流程

```
原始需求文档 + 辅助文档
  ↓
┌─────────────────────────────────┐
│ 1️⃣ 需求理解                      │
│ - 解析模块结构                    │
│ - 识别业务对象、规则、状态流转    │
│ - 提取依赖、风险、假设            │
└─────────────────────────────────┘
  ↓
┌─────────────────────────────────┐
│ 2️⃣ 质量评估                      │
│ - 完整性检查（功能 + NFR）        │
│ - 清晰度检查（模糊词）            │
│ - 可测试性检查（验收标准）        │
│ - 一致性检查（冲突）              │
│ - 决策：通过/有条件/拒绝          │
└─────────────────────────────────┘
  ↓
┌─────────────────────────────────┐
│ 3️⃣ 待澄清内容                    │
│ - 汇总所有问题                    │
│ - 从辅助文档自动查找答案          │
│ - 提供建议选项和行内修正          │
│ - 按优先级排序                    │
└─────────────────────────────────┘
  ↓
分析报告 + 优先级问题列表
```

## 1️⃣ 需求理解

### 目标

从原始需求文档中提取结构化信息，构建需求模型。

### 处理内容

#### 模块识别
- 功能模块/子系统
- 模块的功能点（capabilities）
- 模块间依赖关系

#### 业务对象建模
- 核心业务实体（用户、订单、产品）
- 对象属性和字段
- 对象间关系（一对多、多对多）

#### 业务规则提取

**验证规则**：
- 字段必填、格式、范围
- 示例：手机号必填，格式为11位数字

**计算规则**：
- 价格计算、积分计算、折扣
- 示例：订单金额 = 商品总价 - 优惠券金额

**工作流规则**：
- 审批流程、状态机
- 示例：订单金额 > 1000 需要经理审批

**权限规则**：
- 角色权限、操作权限
- 示例：只有管理员可以删除订单

#### 状态流转分析
- 识别有状态的对象
- 提取所有状态和转换条件
- 标注异常状态和回退路径

#### 风险和假设识别
- **技术风险**：性能瓶颈、第三方依赖
- **业务风险**：范围蔓延、需求变更
- **假设**：用户行为、系统环境

### 输出

```typescript
{
  modules: [
    {
      module_key: "order_management",
      module_name: "订单管理",
      capabilities: ["创建订单", "支付订单", "取消订单"],
      business_objects: [...],
      business_rules: [...],
      state_flows: [...]
    }
  ],
  risks: [...],
  assumptions: [...]
}
```

## 2️⃣ 质量评估

### 目标

评估需求文档质量，识别缺口和问题，给出通过/不通过决策。

### 评估维度

#### 完整性检查 (30% 权重)

**功能完整性**：
- ✓ 所有功能点已描述
- ✓ 所有字段、规则、边界已定义
- ✓ 异常场景已覆盖

**非功能需求（NFR）完整性**：

| 类别 | 检查内容 | 示例 |
|------|----------|------|
| 性能 | 响应时间、吞吐量、并发 | 95% 请求 < 2s |
| 安全 | 认证、授权、加密、审计 | JWT + RBAC |
| 可用性 | SLA、容错、恢复时间 | 99.9% 可用性 |
| 可扩展性 | 用户增长、数据量 | 支持10万并发 |
| 兼容性 | 浏览器、设备、API版本 | Chrome/Safari 最新2版本 |
| 合规 | GDPR、HIPAA、行业标准 | 符合 ISO 27001 |

**评分**：
- 90-100 分：缺失项 ≤ 2 个
- 75-89 分：缺失项 3-5 个
- 60-74 分：缺失项 6-10 个
- < 60 分：缺失项 > 10 个

#### 清晰度检查 (25% 权重)

识别模糊表述：

| 模糊词 | 问题 | 建议修正 |
|--------|------|----------|
| "快速" | 无法度量 | "响应时间 < 2s" |
| "用户友好" | 主观判断 | "3步内完成操作" |
| "安全" | 范围不明 | "密码8位+大小写+数字" |
| "可扩展" | 无具体目标 | "支持10万并发用户" |
| "及时" | 时间模糊 | "24小时内处理" |

**评分**：
- 模糊词占比 < 5%：90-100 分
- 5-10%：75-89 分
- 10-20%：60-74 分
- > 20%：< 60 分

#### 可测试性检查 (25% 权重)

**验收标准格式**：

✅ 好的验收标准：
```gherkin
Given: 用户已登录，账户余额100元
When: 用户下单金额50元
Then: 订单创建成功，账户余额变为50元
```

❌ 不好的验收标准：
```
系统应当能够处理订单
```

**测试覆盖缺口**：
- 边界值（最大最小值、临界点）
- 异常路径（错误输入、网络异常）
- 错误提示内容
- 权限测试（无权限、跨租户）
- 并发场景

**评分**：
- 90% 以上功能有完整验收标准：90-100 分
- 75-89%：75-89 分
- 60-74%：60-74 分
- < 60%：< 60 分

#### 一致性检查 (20% 权重)

**规则冲突**：
```
REQ-012: 手机号必填
REQ-089: 手机号可选
→ 冲突，需要澄清
```

**术语不一致**：
```
文档中同时使用："用户"、"客户"、"会员"
→ 建议统一为"用户"
```

**评分**：
- 无冲突：90-100 分
- 1-2 个 minor 冲突：75-89 分
- 3-5 个冲突：60-74 分
- ≥6 个冲突或 ≥2 个 blocker：< 60 分

### 质量决策

**总分计算**：
```
overall = completeness × 0.30 + clarity × 0.25 
        + testability × 0.25 + consistency × 0.20
```

**决策标准**：
- **通过 (approved)**：总分 ≥ 90，无 blocker
- **有条件通过 (conditional)**：总分 75-89，或有 1-2 个 blocker
- **拒绝 (rejected)**：总分 < 75，或有 ≥3 个 blocker

## 3️⃣ 待澄清内容

### 目标

汇总所有需要人工确认的问题，尝试自动找答案，提供修正建议。

### 问题来源

```
待澄清内容
├─ 需求理解阶段：模块边界不清、状态流转缺失
├─ 完整性检查：缺失的规则、字段、NFR
├─ 清晰度检查：模糊词、歧义表述
├─ 可测试性检查：验收标准缺失
└─ 一致性检查：冲突、术语不一致
```

### 自动增强流程

```
1. 识别问题
   ↓
2. 从辅助文档查找相关内容
   ↓
3. 评估证据质量
   ├─ 高可信度 → auto_resolved（自动填充）
   ├─ 中等可信度 → has_suggestions（提供选项）
   └─ 低可信度/未找到 → needs_manual（等待人工）
   ↓
4. 按优先级排序输出
```

### 问题结构

每个待澄清项包含：

```typescript
{
  question: "请确认：订单审批超时时间是多少？",
  impact: "无法设置超时提醒，影响工单处理时效",
  severity: "major",
  
  current_text: "订单金额大于1000元时，需要经理审批",
  suggested_fix: "订单金额大于1000元时，需要经理审批。\n审批超时时间：48小时。",
  
  recommended_options: [
    {
      label: "48小时（来自运营规范）",
      answer_markdown: "审批超时时间：48小时。超时后自动转至上级审批。",
      confidence: "high",
      source: "运营规范.docx"
    }
  ],
  
  resolution_status: "has_suggestions"
}
```

### 优先级排序

问题按以下顺序排列：

1. 🔴 Blocker + 无答案
2. 🟠 Blocker + 有建议
3. 🟡 Major + 无答案
4. 🟡 Major + 有建议
5. 🟢 Minor + 无答案
6. 🟢 Minor + 有建议
7. ✅ 已自动解决（仅供确认）

## 输出报告结构

### 1. 执行摘要
- 质量评分
- 决策结果（通过/有条件/拒绝）
- 待澄清问题数量

### 2. 需求理解
- 识别的模块
- 业务对象和规则
- 风险和假设

### 3. 质量评估
- 各维度分数
- 关键问题（按严重程度）
- NFR 缺口
- 模糊词和冲突列表

### 4. 待澄清内容
- 按优先级排序的问题
- 每个问题的建议选项
- 行内修正建议

### 5. 建议行动
- 下一步建议
- 阻塞问题清单
- 修正优先级

## 使用示例

### 输入

**主需求文档**：
```markdown
# 订单管理模块

用户可以创建订单。订单创建后状态为"待支付"。
用户支付成功后，订单状态变为"已支付"。
订单金额大于1000元时，需要经理审批。
系统应当快速响应用户操作。
```

**辅助文档（运营规范.docx）**：
```markdown
# 审批流程规范

所有审批流程超时时间统一为48小时。
超时后自动转至上级审批。
```

### 输出

**质量评分**：
- 完整性：65/100（缺少 NFR、异常场景）
- 清晰度：70/100（"快速"为模糊词）
- 可测试性：60/100（缺少验收标准）
- 一致性：95/100（无冲突）
- **总分**：70/100

**决策**：conditional（有条件通过）

**待澄清内容**（部分）：

1. **[Blocker]** 请确认：系统响应时间要求是多少？
   - 当前文本："系统应当快速响应用户操作"
   - 建议修正："95% 请求响应时间 < 2 秒"
   - 影响：无法评估性能需求，可能导致上线后性能不足

2. **[Major]** 请确认：订单审批超时时间是多少？
   - 建议选项1：48小时（来自运营规范.docx）✅
   - 建议选项2：24小时（加快流程）
   - 影响：无法设置超时提醒

3. **[Major]** 缺少非功能需求：安全要求
   - 建议补充：认证方式（JWT）、权限控制（RBAC）、数据加密（AES-256）

## 与 v1.0 的区别

| 特性 | v1.0 | v2.0 |
|------|------|------|
| **架构** | 单一 requirement-review | 三块核心（理解+评估+澄清） |
| **NFR 评估** | ❌ 缺失 | ✅ 明确评估6大类 |
| **模糊词处理** | 提示存在 | 提供具体修正建议 |
| **辅助文档** | 独立 agent | 集成到澄清阶段 |
| **行内修正** | ❌ 无 | ✅ 提供 suggested_fix |
| **优先级排序** | 简单分类 | 7级优先级 |
| **决策输出** | quality_gate | 明确的通过/拒绝决策 |
