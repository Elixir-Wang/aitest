# 澄清问题生成方法指南

本文档提供系统化的澄清问题生成方法。最终目标是输出可由人直接裁决、并能在确认后转化为测试用例的业务问题，而不是生成通用质量检查清单。

## 生成链路

每个候选问题必须经过以下链路：

`原文事实 → 具体缺口/歧义/冲突 → 风险触发场景 → 无法形成的测试断言 → 单一裁决问题 → 互斥选项`

任一环节无法成立时，丢弃该候选问题。

### 最小可测单元

先将每个功能点整理为：

`角色/前置条件 + 触发动作 + 输入 + 规则/处理 + 可观察结果 + 状态/数据变化`

仅针对缺失且会影响测试设计或验收判断的要素提问。需求已经明确的内容用于需求理解和后续用例，不重复生成“请确认”。

---

## QA视角快速入手

待澄清内容必须从 QA 视角出发：问题用于判断能不能设计测试、会不会漏测、风险能不能验证。`impact` 字段写测试影响，不写研发实现影响。

对每个功能点，问这 **3 个核心问题**：

### 1. 能不能测？
需求是否明确到能写测试用例？
- 输入、输出是否清晰？
- 成功/失败标准是什么？
- 能否验证结果？

**示例**：
- "登录接口的返回格式是什么？token 放在哪个字段？"（P0）
- "任务执行成功的判断标准是什么？"（P0）

### 2. 会不会漏？
是否覆盖正常、异常、边界场景？
- 正常流程是否完整？
- 异常情况如何处理？
- 边界值、空值如何处理？

**示例**：
- "用户名为空时如何处理？"（P1）
- "网络超时时是否重试？重试几次？"（P1）
- "单次最多可以导出多少条记录？"（P1）

### 3. 会不会错？
高风险场景是否考虑？
- 涉及额度消耗、外部调用、不可逆操作 → 并发、回滚、幂等性
- 涉及多状态流转 → 状态机是否完整
- 依赖第三方系统 → 超时、失败、重试
- 涉及数据一致性 → 事务、补偿

**示例**：
- "两个用户同时编辑同一份配置，如何处理冲突？"（P0）
- "外部服务调用成功但本地状态更新失败时如何处理？"（P0）
- "第三方接口超时时，是否回滚已占用的额度或资源？"（P0）

## 六维扫描法（必选）

对每个功能点，从 6 个维度系统化扫描。只扫描与原文事实相关的维度，不允许因为清单中存在某个维度就机械生成问题。

### 维度 1: 触发条件与前置条件

**核心问题**：
- 谁可以触发？谁不能触发？
- 什么时候可以触发？什么时候不能？
- 需要满足什么前置条件？

**示例问题**：
- "非管理员用户是否可以触发导出功能？"（P1）
- "在系统维护模式下是否允许创建任务？"（P1）
- "删除项目前是否需要先删除项目下的所有文档？"（P0）

---

### 维度 2: 边界与约束

**核心问题**：
- 最大值、最小值是多少？
- 可以为空吗？
- 有格式要求吗？（长度、编码、类型）
- 有数量限制吗？时间限制吗？并发限制吗？

**示例问题**：
- "单次导出的最大记录数是多少？超出时如何处理？"（P1）
- "备注字段的最大长度是多少？超出时是截断还是提示？"（P1）
- "用户名支持哪些字符？是否支持中文、空格、特殊符号？"（P0）
- "同一用户可以同时发起多少个异步任务？"（P1）
- "上传文件的大小限制是多少？支持哪些格式？"（P0）

---

### 维度 3: 异常与恢复

**核心问题**：
- 网络失败怎么办？
- 服务失败怎么办？
- 校验失败怎么办？
- 超时怎么办？
- 给用户什么提示？
- 可以重试吗？
- 部分成功如何处理？

**示例问题**：
- "外部服务调用超时时，任务状态如何处理？用户如何得知结果？"（P0）
- "批量导入时，部分记录失败如何处理？全部回滚还是部分成功？"（P0）
- "文件上传到一半网络断开，是否支持断点续传？"（P1）
- "第三方系统返回错误码500时，是否重试？重试几次？间隔多久？"（P1）

---

### 维度 4: 状态与时序

**核心问题**：
- 什么状态下可以操作？
- 操作后变成什么状态？
- 可以撤销吗？
- 中途退出怎么办？
- 并发操作如何处理？

**示例问题**：
- "已发布的资源是否可以撤回？如果可以，线上访问如何处理？"（P0）
- "用户在导入进行中关闭页面，任务是继续执行还是中止？"（P1）
- "两个管理员同时编辑同一条配置，如何处理冲突？"（P0）
- "任务在'处理中'状态时，用户申请取消，允许吗？已处理数据如何处理？"（P0）

---

### 维度 5: 权限与隔离

**核心问题**：
- 谁可以查看/创建/修改/删除？
- 数据是否按组织/租户/项目隔离？
- 敏感操作是否需要二次确认？
- 是否需要审计？

**示例问题**：
- "普通用户是否可以查看其他用户创建的资源？"（P0）
- "项目成员是否可以删除项目？还是只有项目创建者可以？"（P0）
- "删除项目是否需要二次确认？需要输入项目名称吗？"（P1）
- "修改系统配置是否记录审计日志？日志包含哪些信息？"（P1）
- "多租户场景下，数据是否严格隔离？A租户能否访问B租户的数据？"（P0）

---

### 维度 6: 数据生命周期

**核心问题**：
- 数据保存多久？
- 可以删除吗？软删除还是硬删除？
- 删除后可以恢复吗？
- 需要历史记录吗？版本控制吗？审计日志吗？

**示例问题**：
- "导出记录保留多久？过期后自动删除吗？"（P2）
- "删除的资源数据是否可以恢复？保留多久？"（P1）
- "用户注销账号后，其数据如何处理？立即删除还是保留一段时间？"（P0）
- "需求文档是否支持版本历史？可以回退到之前的版本吗？"（P1）
- "修改配置是否保留历史记录？可以查看修改人和修改时间吗？"（P2）

## 增强方法（根据需求类型选择）

### 反向用例法 ⭐⭐⭐⭐

对每个肯定需求，提出反向场景：
- 用户可以... → 谁不能？什么时候不能？
- 系统应... → 什么时候不应该？失败后呢？
- 支持...格式 → 不支持的呢？如何提示？
- ...后自动... → 什么条件下不自动？

**示例**：
- 原文："用户可以导出任务记录"
  → "非登录用户是否可以导出？"
  → "导出中的任务是否可以再次导出？"

---

### 多干系人视角法 ⭐⭐⭐⭐

从不同角色审视每个功能点：

**用户视角**：
- 易用性、体验、反馈是否清晰？
- 示例："导出失败时，用户如何得知原因和解决方法？"

**运营视角**：
- 监控、统计、异常处理如何进行？
- 示例："如何统计每日导出次数、成功率和平均耗时？"

**QA视角**：
- 是否能设计稳定测试、断言结果、覆盖风险场景？
- 示例："100万条数据导出时，是否有可验证的完成标准和超时处理口径？"

**安全视角**：
- 权限、审计、敏感数据如何保护？
- 示例："导出的数据中是否包含敏感字段？是否需要脱敏？"

---

### 时间轴扫描法 ⭐⭐⭐⭐（异步任务强烈推荐）

从时间维度发现遗漏，适用于异步任务、长流程业务：

**前置阶段**：
- 需要什么权限、前置条件、准备数据？
- 示例："导入前是否需要下载模板？模板格式是什么？"

**执行中**：
- 进行中状态、取消、暂停、进度查看如何处理？
- 示例："导入进行到一半用户想取消，已导入的数据如何处理？"
- 示例："用户如何查看导入进度？是百分比还是已处理条数？"

**执行后**：
- 结果通知、失败反馈、重试、清理如何处理？
- 示例："导入完成后如何通知用户？站内信、邮件还是短信？"
- 示例："导入失败后是否可以重试？是否需要重新上传文件？"

**长期**：
- 数据保留多久？过期如何处理？是否可查询历史？
- 示例："导入记录保留多久？过期后是否自动删除？"

---

### 极端场景法 ⭐⭐⭐⭐（高并发/大数据量推荐）

考虑极端情况：

**极端数据量**：
- 0条、1条、100万条数据如何处理？
- 示例："查询结果有0条数据时，展示什么？"
- 示例："查询结果有100万条数据，如何展示和导出？是否限制最大数量？"

**极端操作**：
- 连续点击、并发操作、反复切换如何处理？
- 示例："用户在1秒内点击10次提交，是否会创建10条重复数据？"
- 示例："两个用户同时修改同一条数据，如何处理冲突？"

**极端状态**：
- 系统重启、资源耗尽、依赖不可用如何处理？
- 示例："系统重启时，正在执行的异步任务如何处理？"
- 示例："数据库连接池耗尽时，新请求如何处理？"

**极端用户**：
- 恶意用户、特殊权限用户、新手误操作如何应对？
- 示例："恶意用户频繁调用导出接口，是否有限流？"

## 方法组合建议

根据需求类型选择方法组合：

| 需求类型 | 推荐方法组合 | 重点关注 |
|---------|-------------|---------|
| **通用需求** | 六维扫描 + 反向用例 + 多干系人视角 | 全面覆盖 |
| **资源变更类** | 六维扫描 + 极端场景 + 时间轴扫描 | 并发、幂等、一致性 |
| **异步任务类** | 六维扫描 + 时间轴扫描 | 进度、取消、通知、清理 |
| **多角色系统** | 六维扫描 + 多干系人视角 | 权限、隔离、审计 |
| **高可用系统** | 六维扫描 + 极端场景 | 异常、恢复、降级 |
| **数据密集型** | 六维扫描 + 极端场景 | 大数据量、性能 |

## 优先级判断

### P0（阻塞测试设计或验收判断）
核心流程或关键规则不清楚，无法设计主流程测试或判断验收是否通过：
- 核心流程不清楚（无法设计主流程测试）
- 关键规则缺失（计算逻辑、校验规则）
- 数据结构不明（字段含义、必填规则、结果口径）
- 状态流转不清（状态机不完整）

**示例**：
- "任务的完整状态流转是什么？"（P0）
- "额度消耗计算规则是什么？"（P0）

### P1（影响重要测试覆盖）
影响异常、边界、权限、集成或高风险场景的测试覆盖：
- 异常处理不明（失败后如何验证）
- 权限不清（谁可以操作、谁不可以操作）
- 集成口径不定（第三方失败、超时、重试如何验证）
- 边界条件不明（最大值、空值处理）

**示例**：
- "外部调用失败时如何处理？"（P1）
- "普通用户是否可以删除资源？"（P1）

### P2（完善细节）
影响测试完整性或回归范围判断，但不阻塞主流程测试：
- 提示文案不明
- 边界情况的细节
- 性能要求不明

**示例**：
- "删除成功的提示文案是什么？"（P2）
- "导出记录保留多久？"（P2）

### P3（优化建议）
未来扩展性或体验优化：
- 未来扩展性
- 体验优化建议

**示例**：
- "是否考虑支持批量删除？"（P3）

### 高风险场景自动升级（至少 P1）

以下场景的问题自动升级优先级：
- ✅ 涉及额度消耗、权限变更、不可逆操作（并发、回滚、幂等性）
- ✅ 涉及并发操作（锁、事务、冲突处理）
- ✅ 依赖第三方系统（超时、失败、重试）
- ✅ 涉及数据一致性（事务、补偿机制）

**示例**：
- "两个用户同时编辑同一份配置，如何处理？"（P0，涉及并发写入）
- "外部服务调用成功但本地状态更新失败时如何处理？"（P0，涉及一致性）

## 澄清问题格式要求

每个澄清问题必须包含：

```json
{
  "id": "clar-001",
  "priority": "P0",
  "module": "配置管理",
  "question": "两个用户同时编辑同一份配置时如何处理？",
  "option_a": "提交时校验版本号，后提交者看到冲突提示并手动合并",
  "option_b": "后提交内容覆盖先提交内容，并记录完整审计日志",
  "source_excerpt": "原文提到：用户可以编辑配置并提交保存。",
  "impact": "影响并发编辑场景的测试用例设计、冲突断言和回归覆盖范围"
}
```

- **question**: 带具体触发场景，一次只问一个可以由人裁决的问题
- **option_a**: 基于上下文最可能的业务裁决，不得虚构原文没有的具体阈值、接口或文案
- **option_b**: 与 A 互斥的另一种业务裁决，不得只是同义改写
- **source_excerpt**: 原文中的可追溯事实，不得填模型推测或“原文未说明”
- **impact**: 明确哪些用例、场景或断言无法形成；使用“无法设计/覆盖/断言/验收 + 具体结果”的表达

### 有效示例

原文事实：“批量导入完成后返回导入结果。”

- 问题：批量导入中部分记录校验失败时，成功记录应提交还是整批回滚？
- 选项 A：提交成功记录，并返回失败记录及原因。
- 选项 B：整批回滚，只要存在失败记录就不写入任何数据。
- 测试影响：无法设计部分成功场景，也无法断言写入条数、失败明细和重试后的数据一致性。

### 无效示例

- “是否需要考虑性能？”：没有具体来源、场景和断言。
- “请明确验收标准”：没有单一裁决点。
- “文件保留 7 天还是 30 天？”：原文未出现保留场景时属于凭空扩展，且阈值是捏造的。
- “采用乐观锁还是分布式锁？”：这是技术实现选择，不是业务裁决。

## 质量检查清单

生成澄清问题后，检查：

- [ ] 每个问题都具体且可回答（不是"是否考虑XXX？"这种开放问题）
- [ ] 每个问题都提供了两个具体的选项
- [ ] 每个问题都包含原文引用
- [ ] 每个问题都从 QA 视角说明了为什么要问（impact 写测试影响）
- [ ] 每个问题都包含具体触发场景和一个裁决点
- [ ] A/B 互斥且没有捏造具体阈值、接口、字段、文案或实现方案
- [ ] 确认答案后至少能形成一个 Given/When/Then 用例
- [ ] 未机械补齐与原文无关的性能、安全、兼容性、审计或数据生命周期问题
- [ ] 优先级判断合理（P0 真的阻塞测试设计或验收判断吗？）
- [ ] 高风险场景的问题优先级至少 P1
- [ ] 问题按优先级排序（P0 → P1 → P2 → P3）
- [ ] 没有重复问题
- [ ] ID 格式正确（clar-001、clar-002...）

---

## 数量与准入

当前 schema 要求 `clarifications` 至少 1 条。只输出通过准入检查的最高价值问题；不得为了凑数量机械补齐六个维度。候选较多时建议保留 5-10 条，超过 15 条必须按相同业务裁决合并。

优先保留：

1. 主流程、关键规则、状态或数据正确性不明，导致无法设计或验收的 P0。
2. 权限、异常、并发、外部依赖等高风险场景无法覆盖的 P1。
3. 确实影响边界断言或回归范围的 P2。

P3 只能用于原文已经出现但仍需确认的低风险细节，不能用于扩展未来能力或凑数。
