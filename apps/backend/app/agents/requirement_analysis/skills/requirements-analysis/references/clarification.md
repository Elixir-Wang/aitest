# 澄清问题生成方法指南

本文档提供系统化的澄清问题生成方法。

---

## QA视角快速入手

对每个功能点，问这 **3 个核心问题**：

### 1. 能不能测？
需求是否明确到能写测试用例？
- 输入、输出是否清晰？
- 成功/失败标准是什么？
- 能否验证结果？

**示例**：
- "登录接口的返回格式是什么？token 放在哪个字段？"（P0）
- "支付成功的判断标准是什么？"（P0）

### 2. 会不会漏？
是否覆盖正常、异常、边界场景？
- 正常流程是否完整？
- 异常情况如何处理？
- 边界值、空值如何处理？

**示例**：
- "用户名为空时如何处理？"（P1）
- "网络超时时是否重试？重试几次？"（P1）
- "单次最多可以导出多少条记录？"（P1）

### 3. 会不会错？
高风险场景是否考虑？
- 涉及金钱、积分、库存 → 并发、回滚、幂等性
- 涉及多状态流转 → 状态机是否完整
- 依赖第三方系统 → 超时、失败、重试
- 涉及数据一致性 → 事务、补偿

**示例**：
- "两个用户同时购买最后一件商品，如何处理？"（P0）
- "支付成功但订单状态更新失败时如何处理？"（P0）
- "第三方接口超时时，是否回滚已扣减的库存？"（P0）

## 六维扫描法（必选）⭐⭐⭐⭐⭐

对每个功能点，从 6 个维度系统化扫描：

### 维度 1: 触发条件与前置条件

**核心问题**：
- 谁可以触发？谁不能触发？
- 什么时候可以触发？什么时候不能？
- 需要满足什么前置条件？

**示例问题**：
- "非管理员用户是否可以触发导出功能？"（P1）
- "在系统维护模式下是否允许创建订单？"（P1）
- "删除项目前是否需要先删除项目下的所有文档？"（P0）

---

### 维度 2: 边界与约束

**核心问题**：
- 最大值、最小值是多少？
- 可以为空吗？
- 有格式要求吗？（长度、编码、类型）
- 有数量限制吗？时间限制吗？并发限制吗？

**示例问题**：
- "单次导出的最大记录数是多少？超出时如何处理？"（P1）
- "订单备注字段的最大长度是多少？超出时是截断还是提示？"（P1）
- "用户名支持哪些字符？是否支持中文、空格、特殊符号？"（P0）
- "同一用户可以同时发起多少个异步任务？"（P1）
- "上传文件的大小限制是多少？支持哪些格式？"（P0）

---

### 维度 3: 异常与恢复

**核心问题**：
- 网络失败怎么办？
- 服务失败怎么办？
- 校验失败怎么办？
- 超时怎么办？
- 给用户什么提示？
- 可以重试吗？
- 部分成功如何处理？

**示例问题**：
- "支付接口调用超时时，订单状态如何处理？用户如何得知结果？"（P0）
- "批量导入时，部分记录失败如何处理？全部回滚还是部分成功？"（P0）
- "文件上传到一半网络断开，是否支持断点续传？"（P1）
- "第三方系统返回错误码500时，是否重试？重试几次？间隔多久？"（P1）

---

### 维度 4: 状态与时序

**核心问题**：
- 什么状态下可以操作？
- 操作后变成什么状态？
- 可以撤销吗？
- 中途退出怎么办？
- 并发操作如何处理？

**示例问题**：
- "已支付的订单是否可以取消？如果可以，退款如何处理？"（P0）
- "用户在导入进行中关闭页面，任务是继续执行还是中止？"（P1）
- "两个管理员同时编辑同一条配置，如何处理冲突？"（P0）
- "订单在'待发货'状态时，用户申请退款，允许吗？"（P0）

---

### 维度 5: 权限与隔离

**核心问题**：
- 谁可以查看/创建/修改/删除？
- 数据是否按组织/租户/项目隔离？
- 敏感操作是否需要二次确认？
- 是否需要审计？

**示例问题**：
- "普通用户是否可以查看其他用户的订单？"（P0）
- "项目成员是否可以删除项目？还是只有项目创建者可以？"（P0）
- "删除项目是否需要二次确认？需要输入项目名称吗？"（P1）
- "修改系统配置是否记录审计日志？日志包含哪些信息？"（P1）
- "多租户场景下，数据是否严格隔离？A租户能否访问B租户的数据？"（P0）

---

### 维度 6: 数据生命周期

**核心问题**：
- 数据保存多久？
- 可以删除吗？软删除还是硬删除？
- 删除后可以恢复吗？
- 需要历史记录吗？版本控制吗？审计日志吗？

**示例问题**：
- "导出记录保留多久？过期后自动删除吗？"（P2）
- "删除的订单数据是否可以恢复？保留多久？"（P1）
- "用户注销账号后，其数据如何处理？立即删除还是保留一段时间？"（P0）
- "需求文档是否支持版本历史？可以回退到之前的版本吗？"（P1）
- "修改配置是否保留历史记录？可以查看修改人和修改时间吗？"（P2）

## 增强方法（根据需求类型选择）

### 反向用例法 ⭐⭐⭐⭐

对每个肯定需求，提出反向场景：
- 用户可以... → 谁不能？什么时候不能？
- 系统应... → 什么时候不应该？失败后呢？
- 支持...格式 → 不支持的呢？如何提示？
- ...后自动... → 什么条件下不自动？

**示例**：
- 原文："用户可以导出订单数据" 
  → "非登录用户是否可以导出？"
  → "导出中的订单是否可以再次导出？"

---

### 多干系人视角法 ⭐⭐⭐⭐

从不同角色审视每个功能点：

**用户视角**：
- 易用性、体验、反馈是否清晰？
- 示例："导出失败时，用户如何得知原因和解决方法？"

**运营视角**：
- 监控、统计、异常处理如何进行？
- 示例："如何统计每日导出次数、成功率和平均耗时？"

**开发视角**：
- 技术实现、性能、可测试性如何？
- 示例："100万条数据导出时，是否会超时？是否需要异步处理？"

**安全视角**：
- 权限、审计、敏感数据如何保护？
- 示例："导出的数据中是否包含敏感字段？是否需要脱敏？"

---

### 时间轴扫描法 ⭐⭐⭐⭐（异步任务强烈推荐）

从时间维度发现遗漏，适用于异步任务、长流程业务：

**前置阶段**：
- 需要什么权限、前置条件、准备数据？
- 示例："导入前是否需要下载模板？模板格式是什么？"

**执行中**：
- 进行中状态、取消、暂停、进度查看如何处理？
- 示例："导入进行到一半用户想取消，已导入的数据如何处理？"
- 示例："用户如何查看导入进度？是百分比还是已处理条数？"

**执行后**：
- 结果通知、失败反馈、重试、清理如何处理？
- 示例："导入完成后如何通知用户？站内信、邮件还是短信？"
- 示例："导入失败后是否可以重试？是否需要重新上传文件？"

**长期**：
- 数据保留多久？过期如何处理？是否可查询历史？
- 示例："导入记录保留多久？过期后是否自动删除？"

---

### 极端场景法 ⭐⭐⭐⭐（高并发/大数据量推荐）

考虑极端情况：

**极端数据量**：
- 0条、1条、100万条数据如何处理？
- 示例："查询结果有0条数据时，展示什么？"
- 示例："查询结果有100万条数据，如何展示和导出？是否限制最大数量？"

**极端操作**：
- 连续点击、并发操作、反复切换如何处理？
- 示例："用户在1秒内点击10次提交，是否会创建10条重复数据？"
- 示例："两个用户同时修改同一条数据，如何处理冲突？"

**极端状态**：
- 系统重启、资源耗尽、依赖不可用如何处理？
- 示例："系统重启时，正在执行的异步任务如何处理？"
- 示例："数据库连接池耗尽时，新请求如何处理？"

**极端用户**：
- 恶意用户、特殊权限用户、新手误操作如何应对？
- 示例："恶意用户频繁调用导出接口，是否有限流？"

## 方法组合建议

根据需求类型选择方法组合：

| 需求类型 | 推荐方法组合 | 重点关注 |
|---------|-------------|---------|
| **通用需求** | 六维扫描 + 反向用例 + 多干系人视角 | 全面覆盖 |
| **交易/支付类** | 六维扫描 + 极端场景 + 时间轴扫描 | 并发、幂等、一致性 |
| **异步任务类** | 六维扫描 + 时间轴扫描 | 进度、取消、通知、清理 |
| **多角色系统** | 六维扫描 + 多干系人视角 | 权限、隔离、审计 |
| **高可用系统** | 六维扫描 + 极端场景 | 异常、恢复、降级 |
| **数据密集型** | 六维扫描 + 极端场景 | 大数据量、性能 |

## 优先级判断

### P0（阻塞开发）
核心流程或关键规则不清楚，无法开始编码：
- 核心流程不清楚（无法写主流程代码）
- 关键规则缺失（计算逻辑、校验规则）
- 数据结构不明（表结构、字段类型）
- 状态流转不清（状态机不完整）

**示例**：
- "订单的完整状态流转是什么？"（P0）
- "积分计算规则是什么？"（P0）

### P1（影响一致性）
影响系统一致性、用户体验或交付质量：
- 异常处理不明（失败后如何处理）
- 权限不清（谁可以操作）
- 集成方式不定（对接第三方的方式）
- 边界条件不明（最大值、空值处理）

**示例**：
- "支付失败时如何处理？"（P1）
- "普通用户是否可以删除订单？"（P1）

### P2（完善细节）
影响细节体验，但不阻塞开发：
- 提示文案不明
- 边界情况的细节
- 性能要求不明

**示例**：
- "删除成功的提示文案是什么？"（P2）
- "导出记录保留多久？"（P2）

### P3（优化建议）
未来扩展性或体验优化：
- 未来扩展性
- 体验优化建议

**示例**：
- "是否考虑支持批量删除？"（P3）

### 高风险场景自动升级（至少 P1）

以下场景的问题自动升级优先级：
- ✅ 涉及金钱、积分、库存（并发、回滚、幂等性）
- ✅ 涉及并发操作（锁、事务、冲突处理）
- ✅ 依赖第三方系统（超时、失败、重试）
- ✅ 涉及数据一致性（事务、补偿机制）

**示例**：
- "两个用户同时购买最后一件商品，如何处理？"（P0，涉及库存）
- "支付成功但订单状态更新失败时如何处理？"（P0，涉及一致性）

## 澄清问题格式要求

每个澄清问题必须包含：

```json
{
  "id": "clar-001",
  "priority": "P0",
  "module": "订单",
  "question": "两个用户同时购买最后一件商品时如何处理？",
  "option_a": "使用库存锁，先到先得，后到的提示'库存不足'",
  "option_b": "允许超卖，后台异步处理库存不足的订单",
  "source_excerpt": "原文提到：用户可以下单购买商品。",
  "impact": "影响并发场景下的库存一致性和用户体验"
}
```

- **question**: 具体的问题（清晰、可回答）
- **option_a**: 最可能的推荐答案（具体、可执行）
- **option_b**: 次可能的推荐答案（具体、可执行）
- **source_excerpt**: 问题来源的原文片段（帮助用户快速定位上下文）
- **impact**: 为什么要问这个问题（说明影响）

---

## 质量检查清单

生成澄清问题后，检查：

- [ ] 每个问题都具体且可回答（不是"是否考虑XXX？"这种开放问题）
- [ ] 每个问题都提供了两个具体的选项
- [ ] 每个问题都包含原文引用
- [ ] 每个问题都说明了为什么要问（impact）
- [ ] 优先级判断合理（P0 真的阻塞开发吗？）
- [ ] 高风险场景的问题优先级至少 P1
- [ ] 问题按优先级排序（P0 → P1 → P2 → P3）
- [ ] 没有重复问题
- [ ] ID 格式正确（clar-001、clar-002...）
