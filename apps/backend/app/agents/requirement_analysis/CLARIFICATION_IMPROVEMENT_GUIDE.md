# 待澄清智能体改进指南 - 测试驱动视角

## 🎯 改进概述

### 核心问题诊断

**原问题**：待澄清智能体没有内容输出

**根本原因**：
1. ❌ `clarify_node.py` 使用纯函数式逻辑，**没有调用** `clarification.py` 中定义的 LLM Agent
2. ❌ `clarification.py` 中的 `CLARIFICATION_SYSTEM_PROMPT` 和 `run_clarification_agent` 完全被架空
3. ❌ 原有的规则式逻辑无法生成有深度的测试驱动澄清内容

### 解决方案

✅ **已修复**：
- 重写 `clarify_node.py`，现在调用 `run_clarification_agent`
- 全面升级 `CLARIFICATION_SYSTEM_PROMPT`，注入测试专业知识

✅ **提升效果**：
- 从"规则式问题提取" → "测试驱动智能澄清"
- 从"简单问题列表" → "可执行的测试视角分析"
- 从"无建议" → "基于测试经验的推荐选项"

## 📊 测试驱动澄清的 7 大维度

### 1️⃣ 行为契约澄清（API/接口层）

**目标**：确保每个接口都有明确的输入-输出契约

**澄清要点**：
- ✅ 请求参数：必填/可选、类型、格式、取值范围
- ✅ 成功响应：状态码、响应体结构、关键字段
- ✅ 失败响应：错误码枚举、错误信息格式
- ✅ 幂等性：重复请求、并发请求的处理
- ✅ 批量操作：部分失败的处理逻辑

**示例问题**：
```
❓ 问题：用户注册接口的响应格式不明确
📍 测试影响：前端无法解析、测试无法断言、监控无法判定健康度
💡 推荐：成功时返回 200 + {id, username, created_at}；失败时返回 400/409 + {error_code, message}
🧪 测试用例：
   - 注册成功时返回 200 且响应包含 id 和 username
   - 用户名重复时返回 409 且 error_code 为 USER_EXISTS
```

---

### 2️⃣ 状态流转澄清（状态机层）

**目标**：确保状态机的每个转换都有明确规则

**澄清要点**：
- ✅ 状态定义：所有可能的状态及含义
- ✅ 流转规则：哪些操作可触发状态变化
- ✅ 非法流转：不允许的操作如何拒绝
- ✅ 中间态：临时状态的超时处理
- ✅ 终态判定：何时进入不可逆状态

**示例问题**：
```
❓ 问题：订单从'待支付'到'已取消'的状态流转规则不明确
📍 测试影响：无法设计状态机测试、无法验证非法操作被拒绝、数据修复无法判断合法性
💡 推荐：待支付 → [用户取消/超时30分钟] → 已取消；已支付后不可取消
🧪 测试用例：
   - 订单待支付时用户可取消，状态变更为已取消
   - 订单已支付时用户取消失败，返回错误'订单已支付，无法取消'
   - 订单待支付超过30分钟自动取消
```

**Given-When-Then 格式**：
```gherkin
Given 订单处于'已支付'状态
When 用户尝试取消订单
Then 应返回错误'订单已支付，无法取消'
And 订单状态保持'已支付'不变
```

---

### 3️⃣ 数据一致性澄清（数据层）

**目标**：确保数据完整性约束和并发控制策略

**澄清要点**：
- ✅ 唯一性：哪些字段必须唯一、范围（全局/租户/用户）
- ✅ 关联规则：删除、更新时的级联行为
- ✅ 并发控制：乐观锁/悲观锁/队列
- ✅ 幂等性：重复提交的处理
- ✅ 回滚规则：哪些操作支持撤销

**示例问题**：
```
❓ 问题：多用户同时修改同一配置项时的并发控制策略不明确
📍 测试影响：数据覆盖测试无法设计、压测时无法验证一致性、生产环境可能数据丢失
💡 推荐：采用乐观锁（版本号），后提交者修改失败并返回冲突错误
🧪 测试用例：
   - 用户A和用户B同时修改配置，后提交者收到版本冲突错误
   - 用户A修改后版本号递增，用户B使用旧版本号提交失败
```

---

### 4️⃣ 权限边界澄清（安全层）

**目标**：确保每个操作都有明确的权限控制

**澄清要点**：
- ✅ 认证要求：需要哪些角色/权限
- ✅ 拒绝行为：无权限时返回403还是隐藏入口
- ✅ 数据隔离：租户隔离、部门隔离、个人数据
- ✅ 二次验证：敏感操作是否需要确认
- ✅ 审计日志：记录哪些字段

**示例问题**：
```
❓ 问题：删除用户操作的权限要求不明确
📍 测试影响：权限测试无法设计、安全扫描无法验证、越权漏洞无法发现
💡 推荐：仅系统管理员可删除；需二次确认；记录审计日志（操作人、时间、被删除用户ID）
🧪 测试用例：
   - 普通用户尝试删除时返回403
   - 系统管理员未确认时删除失败
   - 删除成功后审计日志包含完整信息
```

---

### 5️⃣ 边界值与异常路径澄清（健壮性层）

**目标**：确保所有边界和异常场景都有明确处理

**澄清要点**：
- ✅ 边界值：最小值、最大值、精度、单位
- ✅ 空值处理：默认值、报错、跳过
- ✅ 极端情况：空列表、超大文件、特殊字符
- ✅ 外部依赖：超时、失败、降级
- ✅ 资源限制：存储满、内存不足

**示例问题**：
```
❓ 问题：商品价格字段的取值范围不明确
📍 测试影响：边界值测试无法设计、异常输入无法验证、生产环境可能出现非法数据
💡 推荐：价格范围 [0.01, 999999.99]，精度2位小数；超出时返回 400 + "价格必须在0.01-999999.99之间"
🧪 测试用例：
   - 价格为0时返回错误
   - 价格为0.01时创建成功
   - 价格为999999.99时创建成功
   - 价格为1000000时返回错误
   - 价格精度超过2位时返回错误
```

---

### 6️⃣ 时序与异步澄清（时间层）

**目标**：确保时间相关的行为都有明确规则

**澄清要点**：
- ✅ 时间窗口：操作有效期、过期行为
- ✅ 超时处理：超时后的状态、补偿措施
- ✅ 异步任务：状态查询、成功/失败/进行中
- ✅ 重试策略：重试次数、间隔、最终失败
- ✅ 定时任务：执行时间、频率、失败处理

**示例问题**：
```
❓ 问题：订单支付超时的处理逻辑不明确
📍 测试影响：超时测试无法设计、定时任务测试无法验证、生产环境可能出现僵尸订单
💡 推荐：订单创建后30分钟内未支付自动取消；每5分钟扫描一次；取消后库存释放
🧪 测试用例：
   - 订单创建29分59秒内支付成功
   - 订单创建30分01秒后自动取消
   - 订单取消后库存增加对应数量
   - 定时任务每5分钟执行一次
```

---

### 7️⃣ 验收标准澄清（交付层）

**目标**：确保功能有明确的交付和验收标准

**澄清要点**：
- ✅ 功能完整性：什么算"完成"
- ✅ 性能指标：响应时间、吞吐量、并发
- ✅ 兼容性：浏览器、操作系统、设备
- ✅ 可用性：SLA、故障恢复
- ✅ 用户体验：加载提示、错误提示、成功反馈

**示例问题**：
```
❓ 问题：用户列表查询的性能要求不明确
📍 测试影响：性能测试无法设计、压测无法判定通过、上线后可能性能不达标
💡 推荐：10万用户数据下，分页查询响应时间 < 500ms（99分位）；支持1000并发
🧪 测试用例：
   - 查询第1页时响应时间 < 500ms
   - 查询第1000页时响应时间 < 500ms
   - 1000并发查询时成功率 > 99%
   - 查询时显示加载骨架屏
```

## 🔧 实施建议

### 对于团队

**1. 在需求评审时使用这些维度作为检查清单**
```
□ 每个 API 是否有明确的输入输出契约？
□ 每个状态流转是否有明确的规则？
□ 并发场景是否有明确的处理策略？
□ 权限边界是否清晰？
□ 边界值和异常路径是否定义？
□ 超时和异步逻辑是否明确？
□ 验收标准是否可量化？
```

**2. 在编写测试用例前，先澄清这些维度**
- 不要等到测试阶段才发现需求不明确
- 澄清后的需求应该可以直接转化为测试用例
- 每个澄清项都应该有对应的 Given-When-Then

**3. 使用统一的澄清格式**
```markdown
## [功能名称]待澄清项

### 问题
[具体的模糊点]

### 测试影响
[不澄清会导致哪些测试无法做]

### 推荐方案
[基于测试经验的建议]

### 测试用例
- [ ] [正常路径测试]
- [ ] [异常路径测试]
- [ ] [边界值测试]
```

## 🎓 最佳实践

### ✅ DO：好的澄清问题

```
❓ "请确认用户注册接口成功时返回哪些字段，失败时返回哪些错误码？"
→ 具体、可回答、有明确决策点

❓ "请确认订单从'待支付'状态可以流转到哪些状态？每种流转的触发条件是什么？"
→ 关注状态机完整性

❓ "请确认两个用户同时修改同一配置时，系统如何处理冲突？"
→ 关注并发和数据一致性
```

### ❌ DON'T：避免的澄清问题

```
❌ "性能需求不明确"
→ 过于宽泛，无法指导测试

❌ "需要补充非功能需求"
→ 没有说明具体缺失什么

❌ "文档格式需要优化"
→ 与测试无关
```

## 📝 总结

**核心理念**：
> 好的需求 = 可测试的需求
> 澄清的目标 = 让每个需求都能转化为明确的、可执行的测试用例

**测试驱动澄清的价值**：
1. **提前发现问题**：在需求阶段发现测试阶段才能发现的问题
2. **降低返工成本**：避免因需求不明确导致的重复开发
3. **提升测试质量**：有明确的断言点和验证标准
4. **加速交付**：减少测试阶段的需求澄清往返

**关键成功因素**：
- 🎯 始终从"测试如何验证"的角度思考
- 📋 使用系统化的 7 大维度检查清单
- 💡 提供可操作的、具体的推荐方案
- 🧪 每个澄清项都附带测试用例示例

---

**适用场景**：
- ✅ 敏捷开发团队的需求评审
- ✅ 测试驱动开发（TDD）流程
- ✅ 行为驱动开发（BDD）流程
- ✅ API 设计评审
- ✅ 验收测试设计

**不适用场景**：
- ❌ 技术实现细节（由开发决定）
- ❌ UI 视觉设计（由设计师决定）
- ❌ 性能优化方案（需要技术方案评审）
