# 测试点 Markdown 修改与 AI 修改设计

## 背景

当前测试点生成智能体返回结构化测试点，后端将每个测试点保存到 `test_points` 表，测试用例生成流程直接读取这些结构化记录。前端则以可编辑表格展示测试点。

目标是让测试点页面尽量保持与“最终需求”页面一致，并支持对当前最终需求版本下的全部测试点进行人工修改和 AI 修改。

## 目标

- 测试点默认以 Markdown 文档形式预览。
- 标题栏提供“修改”和“AI 修改”，布局、按钮状态和编辑区尽量复用最终需求页面。
- 人工修改编辑整份测试点 Markdown，一次保存全部变化。
- AI 修改接收完整测试点 Markdown 和用户指令，返回完整的更新后 Markdown。
- 保存后将 Markdown 严格解析并同步回结构化测试点，保证测试用例生成等下游功能继续可用。

## 非目标

- 本次不增加测试点版本记录页面。
- 本次不修改最终需求和测试用例生成的业务流程。
- 本次不保留当前逐单元格编辑和逐条保存交互。
- 本次不创建新的通用 AI 文档编辑能力，直接复用现有 `/agents/document-editor/run` 接口。

## 数据模型与数据流

结构化测试点仍是持久化数据和下游消费的唯一数据源。Markdown 是统一的展示、人工编辑和 AI 编辑格式，不额外维护第二份独立的 Markdown 数据，避免双数据源不一致。

读取流程：

1. 后端读取当前最终需求版本对应的结构化测试点。
2. 后端按固定模板序列化为 Markdown，并通过测试点概览接口返回。
3. 前端使用 `MarkdownPreview` 展示 Markdown。

人工修改流程：

1. 用户点击“修改”。
2. 前端使用 `StandardMarkdownEditor` 编辑当前完整 Markdown。
3. 用户点击“保存”。
4. 前端调用测试点 Markdown 批量保存接口。
5. 后端解析、校验并在事务中替换当前版本的结构化测试点。
6. 前端重新加载测试点概览并退出编辑态。

AI 修改流程：

1. 用户点击“AI 修改”并输入修改要求。
2. 前端调用现有 `/agents/document-editor/run`，请求体传入完整测试点 Markdown 和修改要求。
3. AI 返回完整的更新后 Markdown。
4. 前端调用同一个测试点 Markdown 批量保存接口。
5. 后端解析、校验并事务性同步结构化测试点。
6. 前端刷新预览并提示修改摘要。

## Markdown 规范

Markdown 使用稳定、可逆的固定模板。每个测试点必须包含唯一的 `point_key`：

```markdown
# 测试点

### [login.success] 使用正确账号密码登录成功

| 字段 | 内容 |
| --- | --- |
| 模块 | 登录 |
| 类型 | 功能 |
| 优先级 | P0 |
| 状态 | draft |

**描述**

验证用户使用正确凭据可以成功登录。

**前置条件**

- 用户账号已创建
- 登录服务正常

**验证点**

- 登录成功并进入首页
- 建立有效会话

**来源引用**

- 需求 3.1

**备注**

无
```

解析规则：

- `### [point_key] 标题` 是测试点边界，`point_key` 必须唯一且非空。
- 模块、类型、优先级和状态从字段表读取。
- 描述、前置条件、验证点、来源引用和备注按固定小节读取。
- 类型和优先级必须符合现有枚举。
- 每个测试点至少包含标题、描述和一个验证点。
- 已存在的 `point_key` 保留原测试点 ID；新增 `point_key` 创建新 ID；Markdown 中删除的测试点同步删除。
- 保存前完成整份文档校验；任意测试点不合法时整批拒绝，不允许部分保存。

## API 设计

扩展现有测试点概览响应：

```json
{
  "requirement_version_id": "reqver-...",
  "requirement_version_no": 2,
  "run": null,
  "points": [],
  "markdown_content": "# 测试点\n..."
}
```

新增批量保存接口：

```text
PUT /projects/{project_id}/requirements/{document_id}/test-points/markdown
```

请求体：

```json
{
  "markdown_content": "# 测试点\n..."
}
```

响应返回更新后的测试点概览。接口要求管理员权限，并且只允许修改当前最终需求版本的测试点。

AI 修改继续使用：

```text
POST /agents/document-editor/run
```

不新增测试点专用 AI 接口。

## 前端交互

- `ShellSection` 顶部左侧显示“测试点”。
- 存在测试点且非编辑态时，右侧显示“AI 修改”和“修改”。
- 点击“修改”后，右侧切换为“保存”和“取消”。
- “AI 修改”使用与最终需求相同的 `AiEditPrompt` 交互和加载状态。
- 非编辑态使用 `MarkdownPreview`，编辑态使用 `StandardMarkdownEditor`。
- 空状态保持当前插图、标题和说明，不显示修改按钮。
- AI 修改或人工保存失败时保留当前编辑内容，不覆盖服务端数据。
- 保存成功后重新请求概览，确保页面展示以后端解析结果为准。

## 错误处理

- Markdown 格式错误返回可读的字段级错误，例如“测试点 login.success 缺少验证点”。
- `point_key` 重复时拒绝整批保存。
- 当前最终需求版本变化时返回冲突错误，前端提示刷新页面后重试。
- AI 返回空内容时不调用保存接口，并提示“AI 未修改测试点”。
- AI 返回无法解析的 Markdown 时不更新数据库，并保留 AI 输出供用户继续人工调整。

## 测试与验证

后端测试：

- 结构化测试点序列化为 Markdown。
- Markdown 解析后保持字段一致的往返测试。
- 新增、修改、删除测试点的批量同步测试。
- 重复 `point_key`、缺少必填段落、非法枚举的失败测试。
- 非管理员、无最终需求版本和版本冲突测试。
- 批量保存失败时数据库不发生部分更新。

前端验证：

- 预览态、人工编辑态、AI 修改输入态与最终需求页面布局一致。
- 空状态不显示修改按钮。
- 保存、取消、AI 修改成功和失败状态正确。
- 运行 Biome lint、类型检查和相关构建检查。

## 兼容性

- 保留现有结构化测试点表和读取接口字段，避免影响测试用例生成。
- 现有单条 PATCH 接口可暂时保留供兼容使用，但新页面不再调用。
- 已生成的历史测试点无需迁移，读取时直接序列化为 Markdown。
