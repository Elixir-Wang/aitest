# 站点探索日志展示改造规范

## 背景

当前站点探索详情页的“探索日志”tab 仍以 `run.log` 原始文本为主，信息密度低，无法快速回答以下问题：

- 这次探索总体进展如何？
- 哪个页面、哪个动作导致了跳转或失败？
- 哪一步写入了产物、触发了阻塞或安全拦截？
- 某条日志和哪个页面、edge、产物对应？

系统日志页面已经提供了标准的审计列表、筛选和详情抽屉能力，但它解决的是“操作审计查询”，不是“探索过程追踪”。探索日志应该借用系统日志的交互模式，而不是直接复用系统日志的展示语义。

## 目标

- 将探索日志从“逐行原始文本”升级为“结构化事件时间线”。
- 默认展示探索事件摘要，支持按类型、页面、级别和关键词筛选。
- 每条日志支持展开查看上下文、动作、结果和产物引用。
- 保留原始 `run.log` 作为证据源和兜底查看方式。
- 与系统日志保持一致的列表、筛选和详情体验，但保留探索专属语义。

## 非目标

- 不把探索日志改造成通用系统审计页。
- 不新增独立 `events.jsonl` 或第二套日志事实源。
- 不在前端自行推断页面、动作或 edge。
- 不保存截图、trace、HTML 快照或独立 locator 文件。
- 不把探索日志替代探索概览、探索报告或页面证据页。

## 问题定义

当前探索日志展示的问题不是“没有日志”，而是“日志没有结构”：

1. 逐行文本无法快速定位关键事件。
2. 文本流缺少统一摘要，人工扫描成本高。
3. 页面、动作、阻塞、产物混在一起，缺少过滤维度。
4. 缺少和 `page.yaml`、`graph.yaml`、`blockers.yaml` 的跳转关系。

因此，改造目标应是把 `run.log` 解析为前端可消费的事件列表，并提供证据跳转，而不是继续堆叠纯文本。

## 设计原则

1. 探索日志是“过程追踪”，不是“系统审计”。
2. 默认只显示摘要，详情按需展开。
3. 事件类型优先于原始字符串。
4. 页面、动作、结果、产物应能相互跳转。
5. 原始日志始终可见，但不占主视图。
6. 前端不伪造事件，不补推断业务含义。

## 现状依据

当前已有基础：

- 探索详情页：`apps/frontend/src/app/(main)/projects/[projectId]/exploration/[runId]/page.tsx`
- 探索日志接口：`GET /api/v1/projects/{project_id}/exploration-runs/{run_id}/log`
- 日志事实源：`logs/run.log`
- 探索产物：`run.yaml`、`summary.yaml`、`graph.yaml`、`blockers.yaml`、`pages/*.yaml`
- 系统日志页：`apps/frontend/src/app/(main)/settings/logs/page.tsx`

现有探索日志面板以表格形式逐行渲染文本，缺少筛选、分组和详情层。

## 展示模型

### 页面结构

探索日志 tab 分为三层：

1. 顶部摘要
2. 结构化事件列表
3. 原始日志折叠区

### 顶部摘要

顶部固定展示：

- 当前运行状态
- 已完成页面数
- 已记录动作数
- 阻塞数
- 错误数
- 最近一次关键事件时间

摘要用于回答“跑到哪了”和“卡在哪了”，不替代完整日志。

### 结构化事件列表

按事件卡片或列表项展示，每条事件至少包含：

- 时间
- 事件类型
- 页面
- 动作或结果
- 严重级别
- 摘要

事件类型建议沿用已有运行语义：

```yaml
log_types:
  run_started: 探索开始
  login_started: 登录开始
  login_completed: 登录完成
  page_discovered: 发现页面
  page_visited: 访问页面
  accessibility_captured: 生成无障碍树
  action_detected: 发现可操作元素
  action_executed: 执行动作
  edge_created: 记录页面关系
  artifact_written: 写入产物
  blocked: 探索阻塞
  skipped: 跳过页面或动作
  safety_blocked: 安全策略拦截
  error: 错误
  run_completed: 探索完成
```

### 事件详情

展开一条事件后展示：

- 页面 ID、标题、URL
- 动作名称和元素信息
- edge ID、目标页面或关系类型
- 产物路径
- 错误原因或阻塞原因
- 对应原始日志行

### 原始日志兜底

原始 `run.log` 应放在折叠区或“查看原始日志”按钮之后，作为：

- 审计证据
- 调试兜底
- 结构化解析失败时的保底展示

## 数据契约

### 现有接口保留

保留现有接口：

- `GET /api/v1/projects/{project_id}/exploration-runs/{run_id}/log`

当前接口继续返回 `log_path`、`log_content` 或等价字段，不强制新增第二条日志 API。

### 建议补充的派生字段

如果后端已有 `run.log` 解析入口，可在现有响应中补充派生字段：

- `entries`: 结构化事件数组
- `summary`: 运行摘要
- `counts`: 页面数、动作数、阻塞数、错误数
- `raw_log_path`: 原始日志路径

如果短期内不便改后端，前端可以先在本地解析 `run.log`，但解析规则必须与 runner 的日志格式严格对齐。

### 事件字段

```yaml
entry:
  id: log-0008
  type: action_executed
  level: info
  time: "2026-05-30T10:21:08+08:00"
  page_id: page-001
  page_title: 用户列表
  url: /users
  action_name: 点击「详情」
  result: page-002
  summary: 访问用户列表后点击详情按钮，跳转到用户详情页
  artifact_path: pages/page-001-user-list.yaml
```

## 前端设计

### 交互

探索日志页应提供：

- 事件类型筛选
- 页面筛选
- 级别筛选
- 关键词搜索
- 展开/收起详情
- 原始日志切换

### 展示文案

列表摘要格式建议：

```text
10:21:03  访问页面      用户列表          /users
10:21:05  生成产物      页面 YAML         pages/page-001-user-list.yaml
10:21:08  执行动作      点击「详情」       page-001 -> page-002
10:21:09  记录关系      edge-001          navigation
10:21:16  安全拦截      删除按钮被跳过
```

### 组件建议

可在现有探索页内增加以下组件边界：

- `ExplorationLogSummary`
- `ExplorationLogFilters`
- `ExplorationLogTimeline`
- `ExplorationLogEntryDetail`
- `ExplorationRawLogDrawer`

不要求新建通用日志组件，避免和系统日志页语义混淆。

## 与系统日志的关系

系统日志可作为交互范式参考，但不可直接复用其展示语义：

- 系统日志强调“谁做了什么”
- 探索日志强调“探索过程发生了什么”

可复用的能力：

- 表格/列表筛选模式
- 详情抽屉
- 关键词搜索
- 条件组合查询

不应复用的内容：

- 审计模块、动作、对象类型的系统化枚举
- 导出、保留策略、管理员审计语义
- 对普通系统操作日志的字段布局

## 验收标准

1. 默认进入“探索日志”时，不再以原始 `pre` 文本作为主视图。
2. 日志可按事件类型、页面、级别和关键词筛选。
3. 每条日志可展开查看上下文、动作、结果和产物引用。
4. 用户可切换到原始 `run.log` 查看完整文本。
5. 页面、动作、edge、产物之间存在明确引用关系。
6. 结构化解析失败时，页面仍能展示原始日志内容。

## 迁移策略

第一阶段：

- 保留现有 `run.log` 接口。
- 前端改为“摘要 + 结构化列表 + 原始日志兜底”。

第二阶段：

- 如果 runner 已稳定输出结构化行，可在后端增加解析后的 entries 派生字段。
- 如果日志格式不稳定，保持原始文本兼容。

第三阶段：

- 视需要把关键事件与页面证据、graph edge、blocker 详情打通。

## 明确不做

- 不新增独立日志数据库表。
- 不将探索日志并入系统日志表。
- 不把探索日志改成时间线报告页。
- 不引入 ELK、OpenSearch 或外部日志平台。
- 不强制迁移旧探索 run。
