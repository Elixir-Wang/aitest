# 需求概览工作流设计

## 目标

将需求详情中的文件处理能力整理为一个清晰的需求概览工作流，支持从原始文件查看、标准 Markdown 文件编辑、智能合并、冲突处理到初始需求展示的闭环。

本设计只定义需求概览页内部的信息结构、交互和接口边界。版本记录需要放在 `最终需求` 之后，作为需求概览内的最后一个 Tab；外层版本记录入口可以保留，但不再是唯一入口。

## 背景依据

- PRD 已明确原始文件必须保留，Markdown 工作稿可以迭代编辑。
- 现有多来源上传设计已明确：一个需求实体可以包含多个来源文件，每个来源文件先独立转换为标准 Markdown，用户确认归并后才生成工作稿。
- 当前详情页已有来源文件列表、原始文件预览、转换稿预览和当前工作稿预览，但信息被拆在表格和抽屉中，主流程不够直观。

## 范围

本期包含：

- 将需求概览页内部 Tab 设计为：`概览`、`原始文件`、`标准文件`、`初始需求`、`版本记录`。
- 当合并出现冲突时，临时显示 `冲突处理` Tab；冲突解决后隐藏。
- 原始文件 Tab 支持选择文件并预览原始文件信息和可预览内容。
- 标准文件 Tab 支持选择标准 Markdown 文件、原地编辑、保存和发起合并。
- 初始需求 Tab 展示合并后的 Markdown 内容。
- 新增需求合并智能体边界，负责合并所有标准 Markdown、去重和识别冲突。

本期不包含：
- 知识库生成。
- 测试用例生成。
- 不明确需求的澄清和评审处理。
- Word 高保真正文渲染能力，除非后端已有可复用能力。
- 冲突历史审计页面。

## 页面结构

页面路由沿用现有需求详情路由：

```text
/projects/{project_id}/requirements/{document_id}
```

页面标题建议改为“需求概览”，保留现有项目上下文、返回入口和需求名称。

页面内 Tab：

```text
概览 / 原始文件 / 标准文件 / 初始需求 / 版本记录
```

当存在未解决冲突时显示：

```text
概览 / 原始文件 / 标准文件 / 初始需求 / 冲突处理 / 版本记录
```

冲突全部解决并再次合并成功后，`冲突处理` Tab 隐藏。

## 概览 Tab

概览 Tab 是处理状态看板，不承担正文编辑。

展示内容：

- 需求名称。
- 所属项目。
- 原始文件总数。
- 转换成功、转换警告、转换失败数量。
- 可参与合并的标准文件数量。
- 待处理冲突数量。
- 初始需求生成状态。
- 最近更新时间。
- 原始文件列表。

原始文件列表字段：

- 文件名。
- 格式。
- 上传时间。
- 转换状态。
- 标准文件状态。
- 合并状态。
- 冲突状态。

列表中的文件名可以作为跳转入口：

- 点击原始文件名，切换到 `原始文件` Tab 并选中该文件。
- 点击标准文件状态，切换到 `标准文件` Tab 并选中该文件。
- 存在冲突时，点击冲突状态切换到 `冲突处理` Tab。

## 原始文件 Tab

原始文件 Tab 用于查看上传材料，不提供编辑能力。

交互结构：

- 顶部：文件切换组件。
- 下方：所选原始文件的信息和预览区。

文件切换组件展示：

- 原始文件名。
- 文件格式。
- 转换状态。
- 上传时间。

预览规则：

- `pdf`：优先使用浏览器原生能力内嵌预览。
- `md`、`txt`：直接文本预览。
- `doc`、`docx`：展示文件基础信息和访问入口；不假装提供高保真正文预览。
- 其他格式：展示文件基础信息和无法直接预览的说明。

原始文件不可修改。任何修订都应发生在标准文件或后续需求工作稿中。

## 标准文件 Tab

标准文件 Tab 用于查看和修订每个来源文件转换后的 Markdown。

交互结构：

- 顶部：文件切换组件。
- 中部：当前标准 Markdown 预览或编辑区。
- 底部：操作区。

默认状态为预览模式，复用现有 `MarkdownPreview` 样式，并保持与当前工作稿预览一致。

操作区：

- `修改`：将当前预览区原地切换为 Markdown 编辑区。
- `合并`：发起需求合并智能体，合并当前需求下所有可参与合并的标准 Markdown。

编辑模式：

- 当前预览区替换为 Markdown 编辑器。
- 展示 `保存` 和 `取消`。
- `保存` 只更新当前来源文件对应的标准 Markdown 内容。
- `保存` 不生成需求版本变更。
- `取消` 放弃本次未保存编辑，恢复预览模式。

合并规则：

- 合并范围是当前需求下所有转换成功或有警告且未废弃的标准 Markdown。
- 当前选中文件只影响预览和编辑对象，不限制合并范围。
- 如果没有可合并标准文件，前端应显示明确错误。

## 初始需求 Tab

初始需求 Tab 用于展示合并后的项目级 Markdown 初始需求。

未生成时显示空态：

```text
尚未生成初始需求，请先在标准文件中发起合并。
```

合并成功后：

- 展示合并后的 Markdown 内容。
- 样式复用 `MarkdownPreview`。
- 重复内容应已经由合并智能体去重整合。
- 不明确内容不在本流程处理，后续进入需求评审。

初始需求是否写入正式版本由后端合并接口控制。本设计倾向于合并成功后生成初始工作稿版本，并将该版本内容展示在初始需求 Tab。

## 版本记录 Tab

版本记录 Tab 放在最终需求或初始需求正文 Tab 之后，用于追溯当前需求文档所有正式版本变更。

展示内容：

- 当前生效版本号。
- 版本号。
- 摘要。
- 创建时间。
- 操作。

记录规则：

- 每次最终需求内容发生变化，都必须创建新的 `source_document_versions` 记录。
- 每条版本记录必须保留 `source_action`、`change_summary`、`diff_summary` 和 `created_at`。
- 修改标准文件、原始文件转换重试、需求分析草稿更新不直接写入最终需求版本记录。
- 只有写入最终需求并更新 `source_documents.current_version_id` 的动作，才视为最终需求变更。
- 每个版本的最终需求内容必须独立存储，切换版本只更新当前生效版本指针，不覆盖历史版本内容。
- 来源动作固定展示为 `需求分析转为最终需求`，不作为列表列展示。
- 列表摘要优先使用 `diff_summary`，为空时使用 `change_summary`。
- 操作列提供小眼睛按钮，点击后以弹窗展示版本详情和该版本最终需求预览。
- 弹窗内提供 `切换为当前版本` 操作；当前生效版本显示当前状态并禁用切换。

接口复用：

```http
GET /api/v1/projects/{project_id}/requirements/{document_id}/versions
GET /api/v1/projects/{project_id}/requirements/{document_id}/versions/{version_id}
PUT /api/v1/projects/{project_id}/requirements/{document_id}/versions/{version_id}/current
```

版本记录为空时显示：

```text
尚未生成最终需求版本。
```

## 冲突处理 Tab

冲突处理 Tab 是条件 Tab。

显示条件：

- 需求合并智能体识别出冲突。
- 存在未解决冲突记录。

隐藏条件：

- 用户解决所有冲突。
- 再次调用合并智能体后合并成功。

冲突内容展示：

- 冲突项标题。
- 涉及来源文件。
- 冲突片段 A。
- 冲突片段 B。
- 用户选择或手动填写的解决结果。

冲突解决方式：

- 选择保留某个来源表述。
- 手动编辑最终表述。
- 标记为合并后的统一表述。

冲突解决后：

- 保存用户解决结果。
- 用户可以再次点击合并。
- 需求合并智能体应把冲突解决结果作为强约束输入。

不明确内容不进入冲突处理 Tab。此处只处理不同来源之间互相矛盾、互斥或无法同时成立的内容。

## 需求合并智能体

新增智能体：

```text
RequirementMergeAgent
```

职责：

- 读取当前需求下所有可参与合并的标准 Markdown。
- 将重复内容合并为一份。
- 按业务模块组织初始需求，而不是按文件简单拼接。
- 保留来源引用。
- 识别冲突内容并生成冲突项。
- 在用户解决冲突后，继续合并并生成初始需求 Markdown。

不负责：

- 不明确需求澄清。
- 需求评审。
- 知识库生成。
- 测试用例生成。
- 自动化代码生成。

输出分两类：

合并成功：

```json
{
  "status": "merged",
  "version_id": "version-xxx",
  "version_no": 1,
  "markdown_content": "# 初始需求",
  "merge_summary": "已合并 3 个标准文件，去重 12 处。",
  "source_file_ids": ["file-a", "file-b"]
}
```

发现冲突：

```json
{
  "status": "conflict",
  "conflict_count": 2,
  "conflicts": [
    {
      "id": "conflict-xxx",
      "title": "登录失败锁定次数不一致",
      "source_file_names": ["需求说明.docx", "补充说明.md"],
      "fragment_a": "连续 5 次失败后锁定账号。",
      "fragment_b": "连续 3 次失败后锁定账号。",
      "resolution": ""
    }
  ]
}
```

## 接口设计

### GET /projects/{project_id}/requirements/{document_id}/overview

返回需求概览页所需汇总信息。

包含：

- 需求基础信息。
- 文件状态统计。
- 原始文件列表。
- 是否存在未解决冲突。
- 初始需求版本信息。

### GET /requirement-files/{mapping_id}/original

沿用现有原始文件预览接口。

返回：

- 原始文件名。
- 文件格式。
- 可预览内容或访问路径。
- 内容类型。

### GET /requirement-files/{mapping_id}/markdown

沿用现有标准 Markdown 获取接口。

返回：

- 原始文件名。
- Markdown 内容。
- 转换摘要。
- 最近保存时间。

### PUT /requirement-files/{mapping_id}/markdown

保存单个标准 Markdown 文件。

请求：

```json
{
  "markdown_content": "# 标准文件内容",
  "change_summary": "人工修订字段说明"
}
```

规则：

- 只更新该来源文件的标准 Markdown。
- 不生成正式需求版本。
- 不修改初始需求版本。
- 不覆盖原始文件。

### POST /projects/{project_id}/requirements/{document_id}/merge

发起合并。

规则：

- 合并所有可参与合并的标准 Markdown。
- 如果存在未解决冲突，必须带入已解决结果。
- 发现新冲突时返回 `status = conflict`。
- 合并成功时返回 `status = merged`，并生成或更新初始需求内容。

### GET /projects/{project_id}/requirements/{document_id}/conflicts

返回当前未解决冲突。

### PUT /projects/{project_id}/requirements/{document_id}/conflicts/{conflict_id}

保存单个冲突解决结果。

请求：

```json
{
  "resolution": "连续 5 次失败后锁定账号。",
  "resolution_type": "manual"
}
```

## 状态规则

标准文件状态：

- `not_generated`：尚未生成标准 Markdown。
- `ready`：可预览和合并。
- `edited`：用户已手动修改。
- `failed`：转换失败，不能参与合并。

合并状态：

- `not_started`：尚未合并。
- `merging`：合并中。
- `conflict`：存在未解决冲突。
- `merged`：已生成初始需求。

冲突状态：

- `none`：无冲突。
- `open`：存在未解决冲突。
- `resolved`：冲突已解决，等待再次合并。

## 测试策略

前端测试重点：

- 需求概览页显示基础 Tab，并在最终需求或初始需求正文后显示 `版本记录` Tab。
- 存在冲突时显示 `冲突处理` Tab。
- 冲突解决并合并成功后隐藏 `冲突处理` Tab。
- 原始文件 Tab 选择文件后展示对应文件信息。
- 标准文件 Tab 选择文件后展示对应 Markdown。
- 点击 `修改` 后预览区原地变为编辑区。
- 保存标准文件后仍停留在标准文件 Tab，并且不出现版本变更提示。
- 点击 `合并` 调用合并接口，合并范围不受当前选中文件限制。
- 合并成功后初始需求 Tab 展示合并后的 Markdown。
- 合并冲突后跳转或切换到冲突处理 Tab。

后端测试重点：

- 保存标准 Markdown 不创建 `SourceDocumentVersion`。
- 合并接口读取所有可合并标准文件。
- 重复内容在合并结果中只保留一份。
- 冲突返回 `status = conflict` 且不生成最终初始需求版本。
- 冲突解决结果保存后可再次合并。
- 再次合并成功后冲突状态关闭。

## 风险与处理

- **冲突与不明确内容边界混淆**：冲突只表示来源之间互相矛盾或互斥；不明确内容留到需求评审。
- **标准文件编辑误认为版本变更**：保存文案必须明确为“标准文件已保存”，不能提示“版本已生成”。
- **合并范围误解**：合并按钮旁可用简短状态说明展示“将合并全部可用标准文件”。
- **Word 预览能力不足**：不要在前端伪造 Word 正文预览，只展示基础信息和访问入口。
- **条件 Tab 闪烁**：冲突状态应来自概览接口或合并接口返回，前端用单一状态控制是否显示冲突处理 Tab。

## 推荐实施顺序

1. 扩展后端概览、标准文件保存、合并和冲突接口。
2. 增加 `RequirementMergeAgent` 定义和服务编排，先用可测试的确定性合并策略包住智能体调用边界。
3. 改造需求详情页为需求概览页内部四 Tab。
4. 抽取文件切换组件，供原始文件和标准文件 Tab 复用。
5. 实现标准文件原地编辑和保存。
6. 实现合并按钮、冲突条件 Tab 和初始需求展示。
7. 补充后端单元测试、前端 lint/build、浏览器路由验证。
