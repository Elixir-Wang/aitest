# SSE 指标配置可用性优化设计

## 目标

让性能测试用户优先理解“这个指标何时触发、样本表现如何”，而不是直接面对 SSE 协议和 JSONPath 的底层字段；同时让三种指标缺失策略具有真实、可区分的运行语义。

## 当前问题

- 展开配置中的指标名称、SSE 事件名、JSONPath、期望值均无标签，只能依靠当前值猜测含义。
- `message` 是 SSE 协议事件名，但在业务界面中缺少解释且通常区分度较低。
- 样本事件是验证证据，却被放在底层配置之后，信息层级不合理。
- `record_null` 与 `ignore` 当前都会进入 `missing_metric_ids`，报告行为没有差异。

## 交互设计

### 默认信息层

每个已选指标默认展示：

- 指标名称与验证状态。
- 业务化触发条件，例如“当 SSE 事件 `message` 的 `$.data.event_type` 等于 `answer`”。
- 样本序号、首次到达耗时、命中次数及“仅取首次”提示。
- 独立的“查看命中事件”折叠区，展示用于验证规则的样本 JSON。

### 高级匹配规则

原“展开配置”改名为“高级匹配规则”，字段使用明确标签：

- 指标名称
- SSE 事件类型
- JSON 字段路径
- 期望值
- 未命中时

缺失策略文案：

- `record_null`：记录为缺失，不影响请求
- `fail_request`：将请求标记为失败
- `ignore`：忽略本次指标

并提供简短说明，明确该选项只在请求未命中指标时生效。

## 运行语义

- `record_null`：指标未命中时写入 `missing_metric_ids`，报告增加 `missing_count`，请求保持成功。
- `fail_request`：指标未命中时写入 `missing_metric_ids`，报告增加 `missing_count`，请求标记失败。
- `ignore`：指标未命中时不写入 `missing_metric_ids`，不增加 `missing_count`，也不影响请求结果。

## 兼容性

- 不修改 API 字段名和配置结构。
- 保留三种既有枚举值，已有配置无需迁移。
- 已命中的指标无论缺失策略为何，仍正常记录首次命中耗时。

## 验收标准

- 展开区域中每个输入控件均有可见标签。
- 默认卡片用自然语言展示完整匹配条件。
- 样本 JSON 通过“查看命中事件”独立呈现。
- `ignore` 未命中时不出现在缺失统计中。
- `record_null` 与 `fail_request` 保持现有缺失统计行为。
