### 2. 简化缓存失效策略（第 9.3 节）

#### 删除的复杂逻辑
- ❌ 页面签名对比（signature 字段）
- ❌ element_count 统计
- ❌ 30% 变化阈值
- ❌ 标题变化检测
- ❌ 自动失效检测

#### 新的简单策略

**核心原则**:
- ✅ **有缓存就用** - 不做复杂的变化检测
- ✅ **手动刷新** - 通过前端界面手动刷新指定页面
- ✅ **自动失效** - （可选）探索时如果定位器失效，自动重新探索

**失效方式 1: 手动刷新**
- 在前端缓存管理界面点击"更新"按钮
- 调用 API 刷新指定页面或全部缓存

**失效方式 2: 自动失效检测（可选，默认关闭）**
```python
def use_cached_page(cached_page, url):
    # 随机抽取 1-2 个关键元素验证
    # 如果定位器失效 → 重新探索
    # 验证通过 → 使用缓存
```

**推荐**: 默认不做自动检测，完全依赖手动刷新
- 简单，容易理解
- 性能好（< 1 秒判断）
- 用户可控（在前端界面随时刷新）

## 🔍 关键设计决策记录

### 决策 1: 缓存策略简化
**问题**: 复杂的签名对比（element_count、30% 阈值）难以理解，且无法区分结构变化和数据变化（如列表项增多）

**方案**: 删除所有自动检测，改为手动刷新

**理由**: 
- 简单，易于理解和实施
- 用户可控，想刷新就刷新
- 性能好，< 1 秒判断

### 决策 2: 前端缓存管理界面
**问题**: 用户需要可视化查看和管理缓存

**方案**: 类似知识库的文件树 + 详情页 + 刷新功能

**理由**:
- 用户熟悉知识库的交互方式
- 文件树结构清晰
- 支持查看、刷新、批量操作

### 决策 3: env_urls 不存储
**问题**: 跨环境 URL 映射是否需要存储

**方案**: 不存储，通过 URL 归一化解决

**理由**:
- 简化数据结构
- 归一化路径已足够支持跨环境
