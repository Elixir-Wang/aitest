# 硅基员工动态办公室设计 Spec

**日期**：2026-07-27  
**范围**：重构 `/agents` 页面的动态办公室画布，增加 CEO 视觉占位和差异化人物动画设计。  
**状态**：已确认  
**背景基准**：`apps/backend/gj_bg.webp`

## 1. 背景与目标

现有动态办公室按固定网格展示员工，能够表达员工状态，但不能清晰体现部门归属、协作关系和人物差异。当前内联 SVG 人物主要依靠颜色、发型和眼镜进行区分，也不适合继续承载复杂动作和后续互动。

本次设计将动态办公室改造为“协作链路办公室”：

- 12 名硅基员工按真实部门组成四个工作岛。
- 四个工作岛体现从需求到运行分析的协作顺序。
- 背景主屏前预留一名独立的硅基 CEO。
- 每个人物拥有可辨识的外观、工位道具和个性动作。
- 使用项目已有的 PixiJS + Spine 骨骼动画系统实现成熟、可扩展的角色表现。
- 保留现有员工详情、任务状态、轮询和页面其他区域。

用户应能在不阅读下方员工列表的情况下识别：

- 每位员工所属部门及其同组成员。
- 需求工程、测试设计、自动化工程、运行与分析之间的协作顺序。
- 哪些员工和部门当前处于活跃状态。
- 不同人物的身份、岗位特点和当前行为。
- CEO 在整个办公室中的统筹位置。

## 2. 范围

### 2.1 本次范围

- 动态办公室背景、空间布局和部门分区。
- CEO 的位置、视觉形象、稳定前端标识和未来交互边界。
- 12 名员工的差异化人物设计。
- Spine 角色资产契约、动画状态机和运行时接入方案。
- 员工状态、点击详情、响应式、无障碍和性能规则。
- 动态办公室相关的前端契约测试和视觉验证要求。

### 2.2 非目标

- 本次不实现 CEO 的业务接口、对话、任务调度或本地模拟交互。
- 不将 CEO 注册到 `/agents/employees`，也不计入员工或运行任务统计。
- 不实现真实任务依赖图、任务转交动画或跨员工任务血缘。
- 不新增员工、部门编辑、座位拖拽或办公室配置功能。
- 不改造 `/agents` 页面的员工卡片、列表、筛选和详情抽屉。
- 不修改现有员工和任务后端 API。

## 3. 已确认约束

- 背景设计基准为 `apps/backend/gj_bg.webp`。
- 浏览器不可直接引用后端磁盘路径；实现时应将同一素材纳入前端静态资源，由动态办公室引用前端静态 URL。
- 使用已有 `GET /agents/employees` 数据，不新增、猜测或修改员工接口。
- 使用已有运行任务数据和轮询节奏，不改变任务状态计算逻辑。
- 保留现有员工点击行为：点击员工后打开当前详情抽屉。
- 保留现有状态语义：工作中、专注中、协作中、空闲。
- CEO 只作为独立的前端视觉实体，不混入员工数组。
- 视觉休息、眨眼和睡觉等行为不写回业务状态，也不能被误解为真实任务状态。

## 4. 现有能力与技术选型

项目已经具备以下动画基础：

- `apps/frontend/src/scene/OfficeScene.ts`：PixiJS 办公室场景和生命周期。
- `apps/frontend/src/scene/characters/SpineCharacter.ts`：Spine 角色加载、朝向和状态动画。
- `apps/frontend/src/scene/entities/AgentEntity.ts`：员工场景实体和点击命中。
- `apps/frontend/src/scene/assets/loadSpineAssets.ts`：Spine 资源加载。
- `apps/frontend/src/scene/systems/AnimationSystem.ts`：人物动画更新。
- `apps/frontend/src/scene/layout/officeLayout.ts`：办公室逻辑坐标和透视布局。

### 4.1 选定方案

最终方案为：**复用现有 PixiJS + Spine 运行时，采用一套基础骨骼、13 套角色皮肤与道具、多轨状态动画。**

该方案优于继续扩展内联 SVG：

- 骨骼、皮肤、附件和动画可以稳定复用。
- 支持状态切换、动画混合、面部叠加和个性动作。
- 适合后续增加 CEO 交互、员工走动和更多行为。
- 项目已经包含相关运行时，不需要引入新的前端动画框架。

### 4.2 不采用方案

- **继续扩展内联 SVG**：适合简单呼吸和眨眼，不适合维护 13 套复杂人物、动作混合和交互状态。
- **Lottie**：适合播放预制动画，但不适合多状态人物、骨骼换肤和运行时交互。
- **重新引入 Rive**：具备状态机能力，但与项目已有 Spine 能力重复，会增加资源链路、运行时和维护成本。
- **逐帧雪碧图**：资源体积大，换肤困难，动作组合和响应式质量较差。

## 5. 数据模型与分区

办公室布局仅依赖现有员工对象中的：

| 字段 | 用途 |
| --- | --- |
| `id` | 稳定角色标识、人物配置映射和点击选择。 |
| `department` | 分配部门工作岛。 |
| `seat_index` | 同一部门内稳定排序。 |
| `name`、`capability_name` | 展示姓名和无任务时的能力说明。 |
| `accent_color` | 员工局部识别色，不替代状态色。 |
| 运行任务及其状态 | 推导员工业务状态和当前任务。 |

### 5.1 工作岛

| 顺序 | 部门 | 员工 |
| --- | --- | --- |
| 1 | 需求工程 | 文档编辑师、需求标准化专员、需求分析师 |
| 2 | 测试设计 | 知识研究员、测试用例设计师、测试点设计师 |
| 3 | 自动化工程 | API 测试设计师、API 场景编排师、UI 自动化工程师 |
| 4 | 运行与分析 | 站点探索员、性能脚本工程师、性能分析师 |

未知 `department` 不得被错误归入现有部门。未知部门员工应进入画布末尾的“其他”区域，并沿用 `seat_index` 排序；该区域默认不绘制跨岛协作连线。

### 5.2 CEO 前端模型

CEO 不进入员工接口或业务状态模型。场景内部使用独立配置：

```ts
type OfficeExecutive = {
  id: "office-ceo";
  displayName: "硅基 CEO";
  role: "战略调度官";
  characterProfileId: "ceo";
  interactive: false;
};
```

约束：

- `office-ceo` 是稳定前端标识，供后续交互扩展使用。
- 当前 `interactive` 固定为 `false`，不得触发伪造的对话、菜单或业务动作。
- CEO 不计入员工人数、活跃人数和运行任务总数。
- 后续启用交互时，应先定义真实交互场景和接口，再将 `interactive` 切换为 `true`。

## 6. 空间布局

### 6.1 背景

- 使用确认的 `gj_bg.webp` 办公室素材，保留主屏、两侧信息板、植物和地面透视关系。
- 将同一背景文件复制或构建到前端静态资源目录，使用稳定 URL 加载；不得让浏览器读取 `apps/backend` 磁盘路径。
- 使用轻量渐变遮罩降低地面反光对人物、状态文字和部门铭牌的干扰。
- 背景不得承载必须读取的业务信息；所有部门、员工、状态和任务内容均由前端文本呈现。

### 6.2 CEO 位置

- CEO 位于背景主屏正前方、四个工作岛之间的中心总裁台。
- CEO 保持与背景主屏中心线对齐，作为整个办公室的主视觉锚点。
- CEO 视觉比例约为普通员工的 `1.2` 倍，但不能遮挡背景主屏标题和两侧信息板。
- CEO 工位显示“硅基 CEO”和“战略调度官”，并可附带运行中任务总数作为全局观察信息。
- 当前不显示可点击光标、未读提示或可交互按钮。
- CEO 使用独立点击命中区域占位，但在当前版本中关闭指针事件；未来可在不改变空间布局的情况下启用。

### 6.3 四个工作岛

- 宽屏从左至右排列：需求工程 → 测试设计 → 自动化工程 → 运行与分析。
- 每个工作岛包含部门铭牌、三张员工工位和部门活动氛围光。
- 工作岛放置在背景地面留白区域，避开门窗、主屏、植物和右侧陈列区。
- 同部门员工按照 `seat_index` 由左至右、由前至后排序，刷新和状态变化不得导致换位。
- 每个工位显示角色、姓名、状态和当前任务或能力说明。

### 6.4 协作链路

- 相邻工作岛之间使用低对比度蓝色光轨提示固定阅读顺序：需求工程 → 测试设计 → 自动化工程 → 运行与分析。
- 光轨只表达产品定义的协作顺序，不表达真实任务血缘、传输进度或具体员工间的任务交接。
- 当相邻工作岛任一方存在活跃员工时，可显示低频流光；默认保持静止或近乎静止。
- 未知部门的“其他”区域不接入协作链路。

## 7. 人物视觉系统

### 7.1 Spine 资产结构

13 个角色使用同一基础骨骼契约，每个角色通过皮肤、插槽附件和个性动画形成差异。

基础骨骼至少包含：

- `root`、`body`、`chest`、`neck`。
- `head-base`、`head-turn`。
- 左右眼、眼皮、眉毛和瞳孔。
- 嘴部或基础口型插槽。
- 左右上臂、前臂和手部。
- 发型、面部配饰、服装、工牌和手持道具插槽。

每套皮肤必须可以独立定义：

- 发型和发色。
- 肤色和脸部细节。
- 服装剪影和岗位配色。
- 眼镜、耳机、发饰等附件。
- 手持道具和桌面岗位道具。
- 工牌和角色识别图形。

人物差异不能仅通过衣服颜色实现，至少应在发型、轮廓、配饰和岗位道具四类特征中体现三类。

| 文档编辑师 | 卷发、浅色衬衫、手写笔、文档夹 | 翻阅文档、低头校对 |

### 7.3 角色配置清单

新增纯前端人物配置，以员工 `id` 为键，不改变后端员工结构：

```ts
type CharacterProfile = {
  employeeId: string;
  skin: string;
  accessorySlots: string[];
  deskProps: string[];
  idleActions: string[];
  stateActions: Partial<Record<AgentState, string>>;
  fallbackPose: string;

```

建议文件：

`apps/frontend/src/scene/characters/character-manifest.ts`

要求：

- 所有 12 个员工 `id` 必须有明确配置。
- CEO 使用独立的 `ceo` 配置，不复用员工 `id`。
- 缺失配置时必须使用稳定的默认皮肤和动作，不得让场景加载失败。
- 角色配置只负责视觉，不包含业务状态和 API 调用。

## 8. 动画状态机

### 8.1 多轨动画

Spine 使用多轨动画组合：

| 轨道 | 职责 | 示例 |
| --- | --- | --- |
| Track 0 | 业务主状态循环 | `idle`、`working`、`thinking`、`talking` |
| Track 1 | 面部叠加动作 | `blink`、`look-left`、`look-right`、`smile` |
| Track 2 | 个性动作 | 点头、歪头、翻页、输入、查看图表 |
| Track 3 | 本地休息表现 | `yawn`、`sleep-start`、`sleep-loop`、`wake-up` |

主状态切换使用 Spine 动画混合，建议混合时间为 `120–200ms`，防止姿势跳变。

### 8.2 业务状态映射

| 业务状态 | 主动画 | 视觉状态 |
| --- | --- | --- |
| `working` | 岗位工作循环或输入动作 | 绿色状态、桌面屏幕柔光、部门微光 |
| `thinking` | 思考姿势或查看资料 | 蓝色状态、短暂焦点环、部门微光 |
| `talking` | 手势或交流姿势 | 橙色状态、轻量协作强调 |
| `idle` | 角色专属待机 | 中性状态，可触发面部和低频个性动作 |
| `walking` | 四向行走 | 仅在后续启用场景移动时使用 |

### 8.3 本地表现状态

为避免把视觉行为混入业务事实，新增仅存在于场景内部的表现状态：

```ts
type PresentationMode = "normal" | "resting" | "sleeping";
```

- `PresentationMode` 不写回 `Agent.state`。
- 工作中、专注中或协作中的员工不得进入睡觉表现。
- 只有持续空闲达到前端定义时间后，才允许随机进入短暂休息或睡觉表现。
- 任意业务状态变化、员工点击或页面重新聚焦时，应立即播放 `wake-up` 并恢复业务状态动画。
- 状态文字仍显示真实的“空闲”，不能显示虚假的后端“睡眠状态”。

### 8.4 人类化动作调度

- 眨眼间隔使用带上下限的随机调度，例如每 `3–8s` 一次，而不是固定同步播放。
- 头部转动、视线切换和个性动作使用更长随机间隔，避免全员同时动作。
- 每个角色使用由员工 `id` 派生的稳定随机种子，使行为有差异但测试可复现。
- 同一角色不能同时触发互斥动作，例如睡觉时不得翻页或输入。
- 动画调度在标签页不可见时暂停；恢复可见后重新计算下一次行为时间。
- `prefers-reduced-motion: reduce` 下停止随机动作和循环位移，仅保留静态姿势及必要状态切换。

## 9. 状态与交互

### 9.1 状态颜色

| 状态 | 颜色 | 画布反馈 |
| --- | --- | --- |
| 工作中 | 绿色 | 状态点、桌面屏幕柔光与部门微光 |
| 专注中 | 蓝色 | 状态点、短暂焦点环与部门微光 |
| 协作中 | 橙色 | 状态点与轻量协作强调 |
| 空闲 | 中性灰 | 保留基本信息，不显示业务活跃特效 |

- `accent_color` 只用于角色或工位的局部识别，不能替代全局状态色。
- 状态更新只更新受影响员工、部门氛围和相邻光轨，不得重新排列人物。

### 9.2 员工交互

- 员工人物和工位组成完整可点击区域，继续触发现有详情抽屉。
- DOM 交互层必须保留员工姓名、状态和当前任务的可访问性标签。
- Canvas/Spine 负责画面，DOM 按钮负责键盘、焦点、读屏和点击语义。
- 悬停时允许角色轻微抬升、注视用户或短暂挥手，但不能遮挡邻近角色和部门铭牌。

### 9.3 CEO 交互预留

- 当前 CEO 仅渲染形象、名称和角色说明。
- 当前不得打开空抽屉、伪造聊天回复或显示不可用菜单。
- 为 CEO 保留独立场景实体、稳定坐标和命中区域接口。
- 后续接入交互前需要单独确认交互目标、输入输出、权限、接口和异常行为。

## 10. 响应式规则

| 断点 | 布局 |
| --- | --- |
| 宽屏（≥1280px） | 四个工作岛横向排列；CEO 位于主屏前方中心。 |
| 中屏（640–1279px） | 四岛按 2×2 排列；CEO 保持顶部中心；阅读顺序不变。 |
| 窄屏（<640px） | 四岛纵向堆叠；CEO 位于画布顶部；隐藏跨岛光轨。 |

要求：

- 人物按场景尺寸等比缩放，不按 DOM 字号无限缩小。
- 员工姓名、状态和任务保持可读，点击命中区满足触控使用。
- 窄屏可减少装饰和个性动作，但不能隐藏员工或真实状态。
- 背景裁切必须保持主屏与 CEO 可见，不得把 CEO 裁出画布。

## 11. 性能、生命周期与降级

- 复用单个 PixiJS `Application` 和现有 ticker，不为每个角色创建独立 Canvas。
- Spine 纹理采用共享 atlas 或少量按部门拆分的 atlas，避免 13 次重复网络和纹理解码。
- 场景初始化时统一预加载必要 skeleton、atlas 和 texture；显示明确的加载状态。
- 页面卸载时销毁角色、事件、ticker 订阅和 Pixi 资源引用，避免重复进入页面后泄漏。
- 标签页隐藏时暂停非必要 ticker 和随机行为。
- 角色资源加载失败时降级到现有内联 SVG 或稳定静态人物，不影响员工点击和状态文本。
- 背景加载失败时使用中性办公室底色，不能阻塞人员和状态展示。
- 不引入新的全局状态、轮询或后端依赖。

## 12. 无障碍

- 每个员工继续使用真实 DOM 按钮作为交互入口。
- 按钮可访问名称包含员工姓名和真实状态。
- 焦点状态必须清晰，不依赖 Canvas 内部描边。
- 状态同时使用文字和颜色，不能只依赖色彩。
- CEO 当前为非交互展示元素，不进入无意义的 Tab 顺序。
- 所有装饰动画支持系统减少动态效果偏好。
- 背景图不包含不可替代的业务信息。

## 15. 测试要求

### 15.1 单元与契约测试

- 验证员工按 `department` 进入四个已知工作岛。
- 验证同部门按 `seat_index` 稳定排序。
- 验证未知部门进入“其他”区域且不参与协作链路。
- 验证 CEO 使用 `office-ceo`，不进入员工统计或员工点击逻辑。
- 验证 12 个员工和 CEO 均存在人物配置。
- 验证缺失皮肤或动画时使用明确 fallback。
- 验证业务状态到 Spine 主动画的映射。
- 验证睡觉表现不改变真实 `Agent.state`。
- 验证工作状态变化可以打断睡觉并恢复正确动画。
- 验证减少动态效果偏好关闭随机动作。

### 15.2 视觉与交互验证

- 在宽屏、中屏和窄屏检查工作岛、CEO、文本和按钮命中区。
- 检查 13 个角色的外观能够明显区分，而不是只改变颜色。
- 检查头部转动、眨眼、视线、睡觉和唤醒动作无穿模或位置跳跃。
- 检查不同员工随机动作不会同步播放。
- 点击每个部门至少一名员工，确认现有详情抽屉正常打开。
- 确认 CEO 当前不会触发伪交互。
- 确认背景静态资源请求成功，不存在浏览器直接读取后端磁盘路径的行为。
- 启用系统减少动态效果偏好，确认人物保持静态且状态信息完整。

### 15.3 性能验证

- 反复进入和离开 `/agents` 后无重复 ticker、事件或 Canvas。
- 13 个角色同时显示时保持可接受的交互流畅度。
- 标签页隐藏后非必要动画暂停。
- 角色或背景资源失败时降级内容仍可操作。

## 16. 验收标准

- 动态办公室使用确认的 `gj_bg.webp` 办公室视觉，并从前端静态资源加载。
- CEO 位于主屏前的中心总裁台，具有独立形象和稳定 `office-ceo` 标识。
- CEO 当前不绑定后端、不计入任务统计、不触发伪交互。
- 12 名员工按四个真实部门分岛展示，岛内顺序稳定。
- 四个部门的协作顺序可直观识别。
- 13 个角色拥有可明显区分的发型、轮廓、配饰和岗位道具。
- 人物可表现头部移动、眨眼、注视、岗位动作、休息和唤醒。
- 视觉睡觉行为不改变或伪造后端业务状态。
- 员工状态和当前任务继续随现有数据更新。
- 点击员工继续打开现有详情抽屉。
- 页面其他区域和后端 API 行为不发生变化。
- 宽屏、中屏和窄屏均无角色遮挡、文字重叠或不可点击问题。
- 减少动态效果偏好下，页面无非必要动画且状态信息仍完整。
