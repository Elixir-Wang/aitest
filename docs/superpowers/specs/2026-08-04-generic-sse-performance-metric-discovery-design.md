# 通用 SSE 性能指标发现与生成设计规范

## 1. 文档状态

- 日期：2026-08-04
- 状态：待评审
- 适用模块：性能测试、SSE 指标配置、AI 指标发现
- 替代范围：替代现有设计中固定生成 `call_llm_start` 和 `first_answer` 两个指标的假设
- 保留能力：复用现有 `PerformanceSseConfig`、SSE 解析器、匹配器、样本回放和 Locust 运行采集能力

## 2. 背景

当前 SSE 指标生成功能将一种特定 LLM 流式协议作为默认业务模型：

- AI 提示词要求必须生成 `call_llm_start` 和 `first_answer`。
- AI 输出 Schema 要求至少返回两个指标。
- 确定性兜底同样固定生成上述两个指标。
- 服务端以固定指标 ID 判断生成结果是否有效。
- 前端将 AI 子步骤失败显示为整体警告，即使最终兜底规则已经通过样本验证。

该实现可以处理当前示例，但无法通用于其他 SSE 接口。例如任务进度、文件处理、工作流执行、视频生成、数据分析、消息订阅等接口可能完全不存在 `call_llm_start`、`answer` 或 `query_end`。

系统需要从“固定指标生成器”升级为“通用 SSE 性能指标发现器”：先从真实样本提取客观事件事实，再分析哪些事件值得作为性能指标，最后由确定性回放和用户确认决定正式配置。

## 3. 目标

### 3.1 产品目标

- 不预设接口所属业务和事件语义。
- 不内置任何必须存在的 SSE 指标或事件值。
- 基于真实样本发现最有性能观测价值的候选指标。
- 允许 AI 推荐零个、一个或多个候选指标。
- 所有候选指标必须具有真实样本证据并通过确定性回放。
- AI 不可用时仍能展示结构化事件目录和规则型候选，不生成固定业务指标。
- 用户可以选择、编辑、验证和应用候选指标。
- 用户关闭配置弹窗后，未应用的生成结果和编辑内容不得丢失。
- 最终结果成功时不得用内部 AI 降级警告误导用户。

### 3.2 技术目标

- 继续复用现有 `PerformanceSseMetric` 和 `PerformanceSseMatch` 作为正式运行配置。
- 将“样本事实提取”“AI 语义分析”“规则回放验证”“正式配置生成”拆分为独立步骤。
- 指标 ID 由服务端确定性生成，不接受 AI 随意命名。
- AI 只分析服务端提供的受限候选，不得发明事件名、JSONPath 或字段值。
- 保持历史已保存 SSE 配置和性能报告兼容。

## 4. 非目标

- 不让 AI 生成或修改 Locust Python 代码。
- 不执行 AI 返回的脚本、表达式或不受限正则。
- 不使用服务端时间戳替代客户端单调时钟。
- 不自动应用 AI 推荐结果。
- 不保证单个样本可以证明事件在所有请求中稳定存在。
- 不在本次改造中增加复杂的多条件布尔表达式。
- 不自动推断企业级业务 SLA 或性能阈值。
- 不把所有 SSE 事件都保存为正式性能指标。

## 5. 核心原则

### 5.1 事实先于语义

程序先从真实采集样本中提取事件、路径、值、出现次数和到达耗时。AI 只能解释这些已确认事实，不能创造事实。

### 5.2 推荐不等于应用

系统输出的是候选指标。候选必须经过样本回放，用户明确勾选并点击应用后，才能进入 `request_config.sse.metrics`。

### 5.3 不确定性必须可见

如果事件名称只能弱推断业务语义，界面必须显示“可能”“疑似”或低置信度，不得将推断包装成确定事实。

### 5.4 允许没有答案

没有高质量候选时，系统必须返回空推荐列表和完整事件目录，而不是生成固定占位指标。

### 5.5 最终结果优先

用户提示按最终可用性决定。AI 未采用但确定性候选有效属于成功或可继续状态，不属于整体失败。

### 5.6 客户端时钟是唯一耗时来源

候选指标的样本耗时和正式压测耗时均使用客户端单调时钟计算。SSE 载荷中的时间字段仅作为结构证据，不作为正式耗时来源。

## 6. 名词定义

### 6.1 事件事实

由程序从真实 SSE 样本中提取的客观信息，包括：

- SSE `event` 名称。
- 数据来源，例如 `data_json` 或 `data_text`。
- JSONPath。
- 观察到的字段值。
- 值类型。
- 命中次数。
- 首次和最后一次事件序号。
- 首次和最后一次客户端到达耗时。
- 是否存在非空内容。

### 6.2 候选指标

尚未进入正式压测配置的指标建议，包含匹配规则、展示名称、指标分类、推荐理由、置信度、样本证据和回放结果。

### 6.3 正式指标

用户明确选择并应用后保存到 `PerformanceSseConfig.metrics` 的指标。正式指标参与 Locust 运行、目标判断、报告展示和历史对比。

### 6.4 结构识别

不依赖 AI，根据事件结构、位置、内容和命名模式生成候选的确定性分析过程。结构识别不得宣称掌握准确业务含义。

## 7. 总体流程

```mermaid
flowchart LR
    A["运行真实接口或场景"] --> B["标准化 SSE 样本"]
    B --> C["提取事件事实目录"]
    C --> D["生成结构型候选"]
    C --> E["AI 语义分析与排序"]
    D --> F["合并和去重候选"]
    E --> F
    F --> G["确定性样本回放"]
    G --> H["展示已验证候选"]
    H --> I["用户选择和编辑"]
    I --> J["重新验证"]
    J --> K["明确应用正式配置"]
```

### 7.1 流程说明

1. 使用当前未保存的请求参数运行真实接口或场景目标步骤。
2. 采集标准化 SSE 事件和客户端到达偏移。
3. 程序生成事件事实目录。
4. 程序生成无需业务语义即可确认的结构型候选。
5. AI 在受限事件事实范围内分析业务价值并给出语义候选。
6. 服务端合并相同匹配规则，保留更完整的理由和证据。
7. 使用现有 SSE 匹配器回放所有候选。
8. 只将实际命中的候选标记为已验证。
9. 用户选择需要的候选，可以修改名称、匹配规则和缺失策略。
10. 规则变化后必须重新验证。
11. 用户点击应用后才更新表单中的正式 SSE 配置。

## 8. 事件事实目录

### 8.1 提取范围

服务端从每个标准化 SSE 事件中提取以下有限信息：

- `event_name`。
- `data_json` 中满足受限 JSONPath 规则的标量字段。
- `data_text` 是否非空及裁剪后的结构摘要。
- 事件序号和客户端到达偏移。
- 内容是否非空，不向 AI 传递完整敏感正文。

### 8.2 事实聚合

相同的 `event_name + source + path + normalized_value` 聚合为一个事实：

```json
{
  "fact_id": "fact_6e15248c",
  "event_name": "message",
  "source": "data_json",
  "path": "$.data.event_type",
  "value_type": "string",
  "normalized_value": "answer",
  "matched_count": 12,
  "first_sequence": 3,
  "last_sequence": 16,
  "first_offset_ms": 2657,
  "last_offset_ms": 6731,
  "has_non_empty_content": true
}
```

### 8.3 值保留规则

- 事件类型、状态、阶段、动作等低敏感枚举值可以保留。
- 回答正文、用户输入、文件内容、令牌、Cookie、身份信息和业务数据必须脱敏。
- 长字符串只保留类型、长度和是否非空。
- 高基数随机值不得作为 `equals` 候选。
- 数字时间戳和序号不得自动作为固定匹配值。

### 8.4 事件目录接口要求

事件事实目录必须可以在 AI 不可用时直接返回前端，用于手动选择事件和排障。

## 9. 通用候选指标分类

分类用于推荐排序和界面解释，不要求每个接口都具备，也不写死具体事件值。

| 分类 | 标识 | 说明 |
|---|---|---|
| 首次有效输出 | `first_output` | 首次出现用户可感知或非空业务输出 |
| 阶段开始 | `milestone_start` | 某个可辨识业务阶段开始 |
| 阶段完成 | `milestone_end` | 某个可辨识业务阶段完成 |
| 整体完成 | `completion` | 整个流式请求完成或进入终态 |
| 首次外部调用 | `first_external_action` | 首次工具、插件、检索或外部服务调用 |
| 状态变化 | `state_transition` | 进入重要业务状态 |
| 自定义事件 | `custom_event` | 其他具有性能观测价值的真实事件 |

分类不得决定具体匹配规则，也不得成为必须生成的固定指标集合。

## 10. 结构型候选生成

### 10.1 目标

当 AI 不可用或输出无效时，系统仍然能够根据结构证据给出有限候选，但不编造业务语义。

### 10.2 可识别模式

- 首次携带非空内容的事件。
- 位于事件流末尾且只出现一次的稳定枚举事件。
- 名称具有开始与结束对应关系的事件，例如 `_start`/`_end`、`begin`/`complete`。
- 首次出现的外部动作类事件，例如名称或结构中明确包含 `tool`、`plugin`、`retrieval`。
- 从中间状态进入终态的明确状态字段。

### 10.3 降权或排除模式

- `heartbeat`、`ping`、`keepalive`。
- 日志、调试、链路追踪和内部序号事件。
- 每帧都变化的随机 ID、时间戳和计数器。
- 仅表示连接建立但没有业务意义的协议事件。
- 无法使用受限匹配器稳定表达的复杂结构。

### 10.4 结构型候选名称

无法确认业务含义时使用中性名称，例如：

- `首次非空内容到达时间`
- `事件 process_start 首次到达时间`
- `事件 completed 首次到达时间`

不得仅根据字段名把事件命名为用户未确认的业务动作。

## 11. AI 分析设计

### 11.1 AI 职责

- 判断事件事实可能代表的业务里程碑。
- 对候选指标进行性能观测价值排序。
- 生成用户可理解、可编辑的候选名称。
- 说明推荐理由和不确定性。
- 识别可能的开始与结束事件关系。

### 11.2 AI 禁止行为

- 不得要求固定生成任何指标。
- 不得要求至少生成两个指标。
- 不得发明样本中不存在的事件名、路径或期望值。
- 不得直接生成正式指标 ID。
- 不得把服务端载荷时间戳作为客户端耗时。
- 不得输出 Python、脚本或不受限表达式。
- 不得在证据不足时断言业务语义。

### 11.3 推荐提示词

```text
你是通用 SSE 性能指标发现分析器。

你的任务是分析真实采集并由程序聚合的 SSE 事件事实，推荐最有性能观测价值的候选指标。

必须遵守：
1. 不得假设接口属于聊天、LLM、工作流或任何特定业务。
2. 不得预设 call_llm_start、answer、query_end 或其他固定事件。
3. 只能引用输入中存在的 fact_id、事件名、JSONPath 和字段值。
4. 每个候选必须引用至少一个 fact_id 作为证据。
5. 优先考虑首次有效输出、关键阶段开始、关键阶段完成、整体完成和重要外部动作。
6. 降低心跳、日志、调试、确认和高基数随机字段的优先级。
7. 不确定业务语义时必须降低置信度并使用中性名称。
8. 可以返回零个到八个候选，不得为了满足数量而生成低质量指标。
9. 不生成正式指标 ID，不修改请求，不生成代码。
10. 置信度只表示基于当前样本的解释可信度，不代表跨请求稳定性。
```

### 11.4 AI 输入

```json
{
  "task": "discover_performance_metric_candidates",
  "context": {
    "target_name": "流式任务接口",
    "target_description": "可选的接口或步骤描述",
    "user_goal": null
  },
  "sample": {
    "event_count": 18,
    "duration_ms": 6832,
    "truncated": false
  },
  "facts": []
}
```

`user_goal` 是可选辅助信息，不填写时不得阻止通用发现。

### 11.5 AI 输出

```json
{
  "candidates": [
    {
      "name": "首次有效内容到达时间",
      "category": "first_output",
      "fact_id": "fact_6e15248c",
      "occurrence": "first",
      "confidence": 0.94,
      "reason": "该事件首次携带非空内容，并在后续持续产生内容",
      "uncertainty": null
    }
  ],
  "end_rule_candidate_fact_id": "fact_81a3a470",
  "summary": "从本次样本中发现两个高价值性能里程碑"
}
```

AI 输出不直接包含任意 JSONPath。服务端根据 `fact_id` 还原受限匹配规则，避免模型修改事实。

## 12. 候选评分与排序

### 12.1 评分维度

每个候选按以下维度计算推荐分：

- `evidence_score`：事实是否明确、是否实际命中。
- `stability_score`：匹配条件是否低基数、简单且可重复。
- `observability_score`：是否能代表可解释的请求阶段。
- `user_value_score`：是否可能反映用户可感知性能。
- `semantic_confidence`：AI 对业务语义的置信度。
- `noise_penalty`：心跳、日志、调试、高频噪声等扣分。

建议首期权重：

```text
recommendation_score =
  evidence_score * 0.30
  + stability_score * 0.25
  + observability_score * 0.20
  + user_value_score * 0.15
  + semantic_confidence * 0.10
  - noise_penalty
```

### 12.2 推荐等级

- `recommended`：分数不低于 0.75，默认勾选。
- `optional`：分数为 0.50 至 0.74，默认不勾选。
- `low_confidence`：分数低于 0.50，仅在“其他事件”中展示。

结构型候选没有可靠业务语义时，`semantic_confidence` 不得高于 0.50。

### 12.3 单样本限制

单次样本只能证明规则在当前样本中命中，不能证明长期稳定。界面统一使用“样本已验证”，不得使用“规则永久有效”等表述。

后续如支持多样本，可以增加跨样本命中率和稳定性评分，但不属于本次范围。

## 13. 候选数据契约

建议增加独立候选模型，不将 AI 元数据写入正式 `PerformanceSseMetric`：

```python
class PerformanceSseMetricCandidate(BaseModel):
    suggestion_key: str
    name: str
    category: Literal[
        "first_output",
        "milestone_start",
        "milestone_end",
        "completion",
        "first_external_action",
        "state_transition",
        "custom_event",
    ]
    match: PerformanceSseMatch
    occurrence: Literal["first"] = "first"
    recommended_missing_policy: Literal["record_null", "fail_request", "ignore"]
    source: Literal["ai", "structural", "merged"]
    recommendation_level: Literal["recommended", "optional", "low_confidence"]
    recommendation_score: float
    semantic_confidence: float
    reason: str
    uncertainty: str | None
    evidence_fact_ids: list[str]
    validation: PerformanceSseMetricValidation
```

`suggestion_key` 仅用于当前草稿交互，不作为正式指标 ID。

## 14. 正式指标 ID

### 14.1 生成原则

正式指标 ID 由服务端根据规范化匹配规则生成，不由 AI 提供：

```text
sse_<semantic_slug>_<match_hash>
```

示例：

```text
sse_first_output_a84f93
sse_completed_42c591
```

### 14.2 稳定性

- 修改显示名称不改变 ID。
- 修改匹配规则后重新生成 ID。
- 同一规范化匹配规则重复生成时得到相同 ID。
- ID 必须符合现有 `^[a-z][a-z0-9_]{0,63}$` 约束。
- 用户已有性能目标引用旧 ID 时，编辑匹配规则必须提示目标关联可能失效。

## 15. 回放验证

### 15.1 验证对象

- 每个候选指标独立验证。
- 结束规则独立验证。
- 不再使用固定 `REQUIRED_METRIC_IDS` 判断整体有效性。

### 15.2 验证结果

```json
{
  "valid": true,
  "matched_count": 12,
  "first_event_sequence": 3,
  "sample_elapsed_ms": 2657,
  "sample_event": {
    "event": "message",
    "event_type": "answer",
    "has_non_empty_content": true
  }
}
```

### 15.3 整体可应用条件

- 至少选择一个候选指标。
- 所有被选择的候选指标均通过回放。
- 若配置了结束规则，结束规则必须通过回放。
- 未选择或低置信度候选不影响整体应用。
- 用户修改匹配字段后，候选立即变为“待验证”。

## 16. 生成结果接口

建议将现有生成结果扩展为：

```json
{
  "sample_summary": {
    "event_count": 18,
    "duration_ms": 6832,
    "truncated": false
  },
  "event_facts": [],
  "candidates": [],
  "end_rule_candidate": null,
  "analysis": {
    "ai_status": "used",
    "generation_mode": "ai_and_structural",
    "summary": "发现 3 个候选指标"
  },
  "result_status": "ready",
  "messages": []
}
```

### 16.1 `ai_status`

- `used`：AI 结果已采用。
- `not_used`：AI 返回但未采用。
- `unavailable`：AI 调用不可用。
- `disabled`：本次未调用 AI。

### 16.2 `generation_mode`

- `ai_and_structural`。
- `ai_only`。
- `structural_only`。
- `event_catalog_only`。

### 16.3 `result_status`

- `ready`：存在至少一个已验证候选。
- `empty`：没有高质量候选，但事件目录可用。
- `partial`：部分候选无法验证。
- `failed`：样本采集或解析失败。

## 17. 用户交互设计

### 17.1 初始状态

页面显示：

```text
业务响应指标
运行真实接口，分析 SSE 流中值得观测的业务事件。

[运行样本并发现指标] [手动配置]
```

不得提前展示固定的 LLM 指标名称。

### 17.2 生成结果

```text
本次样本发现 9 类事件，推荐 3 个性能指标

☑ 首次有效内容到达时间                     推荐
  $.data.event_type = answer
  样本 2657 ms · 首次事件 #3 · 命中 12 次
  推荐原因：首次携带非空业务内容

☐ 事件 call_llm_start 首次到达时间          可选
  $.data.event_type = call_llm_start
  样本 2614 ms · 事件 #2 · 命中 1 次
  说明：可能表示某个处理阶段开始，业务含义需确认

☑ 整体处理完成时间                           推荐
  $.data.event_type = query_end
  样本 6832 ms · 事件 #18 · 命中 1 次
```

### 17.3 用户能力

- 勾选或取消候选指标。
- 修改显示名称。
- 修改匹配规则。
- 修改缺失策略。
- 展开查看样本证据。
- 查看未推荐的其他事件。
- 将任意事件事实添加为自定义指标。
- 重新运行样本。
- 重新验证当前草稿。
- 应用已选择且已验证的指标。

### 17.4 草稿恢复

弹窗不得成为生成结果的唯一状态载体。候选、选择状态、编辑内容和验证状态保存在表单级草稿中。

状态定义：

```text
idle
  -> generating
  -> generated_pending_apply
  -> edited_pending_validation
  -> verified_pending_apply
  -> applied
```

按钮规则：

| 状态 | 主按钮 | 次按钮 |
|---|---|---|
| `idle` | 运行样本并发现指标 | 手动配置 |
| `generated_pending_apply` | 查看生成结果 | 重新生成 |
| `edited_pending_validation` | 继续编辑 | 重新生成 |
| `verified_pending_apply` | 查看并应用 | 重新生成 |
| `applied` | 配置指标 | 重新生成 |

弹窗关闭规则：

- 右上角关闭、Esc 和遮罩关闭只关闭弹窗。
- 不清空草稿和样本证据。
- “取消”改为“暂存并关闭”。
- 页面显示“已生成，等待应用”或“已编辑，等待重新验证”。
- 只有“放弃草稿”才清除未应用结果。

### 17.5 请求变化处理

为生成时的请求参数计算请求指纹，至少包含：

- 目标接口或场景步骤。
- 环境。
- Method 和 URL。
- Path、Query、Header、Cookie、Body、Form 和 Multipart 参数。
- 最大流式等待时间。

请求指纹变化后：

- 保留候选草稿供用户查看。
- 将所有验证状态置为失效。
- 页面提示“请求配置已变化，请使用新请求重新验证”。
- 禁止直接应用旧验证结果。

首期只要求组件和表单生命周期内保留；可使用 `sessionStorage` 增强页面刷新恢复，但不新增服务端草稿表。

## 18. 用户提示策略

### 18.1 成功提示

当至少存在一个已验证候选时：

```text
已发现并验证 3 个候选指标
```

如果 AI 未采用但结构识别成功，仍显示成功提示，不弹出内部降级警告。

### 18.2 空结果提示

```text
本次样本未发现高可信度性能指标，可从事件目录中手动选择。
```

### 18.3 部分结果提示

```text
已验证 2 个候选，另有 1 个候选未命中。
```

未命中的候选显示在结果面板内，不逐条弹 Toast。

### 18.4 失败提示

仅以下情况使用错误提示：

- 接口或场景执行失败。
- 响应不是可解析的 SSE。
- 未捕获任何有效事件。
- 样本超出安全限制且无法形成事件目录。
- 服务端无法完成回放。

### 18.5 诊断详情

AI 状态属于诊断信息，默认折叠：

```text
识别详情
生成方式：结构识别
AI 辅助：未采用
事件事实：9 类
回放结果：3 个候选已验证
```

## 19. 结束规则

结束规则与业务指标分开推荐：

- 结束规则用于决定何时停止消费流。
- 业务指标用于记录耗时。
- 同一个事件可以同时成为完成指标和结束规则，但二者必须独立展示和确认。
- 没有可靠结束事件时允许 `end_rule = null`，由 EOF 或最大流式时间控制。
- 不得固定优先使用 `query_end`，只能根据当前样本事实推荐。

## 20. 兼容性

### 20.1 历史配置

- 已保存的 `call_llm_start` 和 `first_answer` 继续作为普通正式指标运行。
- 不迁移、不删除、不重命名历史指标 ID。
- 历史性能目标和报告保持原语义。
- 编辑历史配置时可以继续手动修改，也可以重新运行通用发现。

### 20.2 API 兼容

- `PerformanceSseConfig` 正式配置结构保持兼容。
- 生成接口可以扩展响应字段，但不得要求历史消费者理解候选元数据。
- 如现有响应结构无法兼容，应增加版本字段或新建发现接口，不复用含义已经变化的字段。

### 20.3 报告兼容

- 报告继续按正式指标 ID 聚合。
- 候选分类、置信度和推荐理由不进入正式运行结果。
- 正式指标保存后只保留运行所需字段，避免 AI 元数据污染运行配置。

## 21. 安全与隐私

- 完整 SSE 回答正文不得发送给 AI。
- Header、Cookie、Token、身份字段和业务正文必须脱敏。
- AI 只接收事件事实目录和必要上下文。
- `fact_id` 由服务端生成，AI 只能引用存在的 `fact_id`。
- 服务端根据 `fact_id` 还原匹配规则，拒绝 AI 构造的新路径和值。
- 样本不因生成指标而新增长期持久化。
- 前端样本证据继续使用裁剪和脱敏结构。

## 22. 可观测性

建议记录以下不含业务正文的生成指标：

- 样本事件数量。
- 事件事实数量。
- 结构型候选数量。
- AI 候选数量。
- 合并后候选数量。
- 已验证候选数量。
- 用户最终应用数量。
- `generation_mode`。
- `ai_status`。
- 生成和回放耗时。
- 空结果率和手动配置率。

不得将 AI 未采用直接记录为用户级功能失败。

## 23. 失败与降级策略

| 场景 | 系统行为 | 用户结果 |
|---|---|---|
| AI 成功且候选有效 | 合并结构候选并回放 | 展示已验证候选 |
| AI 输出引用不存在的事实 | 丢弃对应 AI 候选 | 保留结构候选 |
| AI 输出格式无效 | 记录诊断，使用结构识别 | 不弹整体失败警告 |
| AI 调用异常 | 使用结构识别 | 不弹整体失败警告 |
| 结构候选为空 | 返回事件目录 | 引导手动选择 |
| 所有候选回放失败 | 返回事件目录和失败原因 | 禁止应用 |
| SSE 样本为空 | 终止发现 | 显示采样失败 |
| 请求参数变化 | 保留草稿、验证失效 | 引导重新验证 |

## 24. 后端改造要求

### 24.1 删除固定假设

- 删除 AI Schema 的 `min_length=2` 限制，允许零至八个候选。
- 删除提示词中必须生成 `call_llm_start` 和 `first_answer` 的要求。
- 删除 `requested_metrics` 固定输入。
- 删除固定 `REQUIRED_METRIC_IDS` 整体验证。
- 删除固定两个指标的确定性兜底。
- 删除固定优先 `query_end` 的结束规则逻辑。

### 24.2 新增模块职责

- 事件事实提取器。
- 高基数字段过滤器。
- 结构型候选生成器。
- AI 候选解析和 `fact_id` 校验器。
- 候选合并与去重器。
- 推荐评分器。
- 正式指标 ID 生成器。

### 24.3 复用模块

- SSE 标准化解析器。
- 受限 JSONPath 校验。
- `event_matches` 匹配器。
- 样本回放验证。
- 正式 `PerformanceSseConfig` Schema。
- Locust SSE 指标运行逻辑。

## 25. 前端改造要求

- 将单个 `candidate_sse` 编辑模式改为候选列表选择模式。
- 区分候选状态、选择状态和验证状态。
- 保存未应用草稿并提供重新打开入口。
- 按最终结果显示成功、部分、空结果或失败。
- 不再逐条 Toast 展示 AI 内部警告。
- 增加事件目录和“添加为自定义指标”能力。
- 展示推荐等级、推荐理由、不确定性和样本证据。
- 对请求指纹变化执行验证失效。
- 应用时将选中的候选转换为现有 `PerformanceSseConfig`。

## 26. 测试策略

### 26.1 后端单元测试

- 从任意事件字段提取事实目录。
- 不同 JSON 层级能够生成正确路径。
- 高基数随机值不生成 `equals` 候选。
- 非空内容事件可以生成结构候选。
- 开始与结束命名对能够形成里程碑候选。
- 心跳和日志事件被降权或排除。
- AI 可以返回零个或一个候选。
- AI 引用不存在的 `fact_id` 时被拒绝。
- AI 不能修改事实对应的匹配规则。
- 相同匹配规则生成稳定正式指标 ID。
- 验证不依赖固定指标 ID。
- 无候选时返回事件目录而不是固定指标。

### 26.2 后端集成测试

- LLM 聊天 SSE 样本能够发现候选，但不依赖固定事件名。
- 任务进度 SSE 能够推荐阶段和完成指标。
- 文件处理 SSE 能够推荐完成事件。
- 只有心跳事件时返回空推荐。
- AI 异常时返回结构候选。
- AI 和结构候选相同规则时正确合并。
- 所有正式配置继续通过现有脚本生成和运行链路。

### 26.3 前端测试

- 未生成状态不显示固定指标名称。
- 生成一个候选时可以正常展示和应用。
- 生成零个候选时展示事件目录和手动选择入口。
- 关闭弹窗后可以重新打开未应用草稿。
- 编辑规则后关闭弹窗，编辑内容和待验证状态保留。
- 请求参数变化后旧验证结果失效。
- AI 未采用但结构候选成功时只显示成功提示。
- 未命中候选显示在结果面板，不逐条弹 Toast。
- 只转换用户选中的已验证候选。

### 26.4 回归测试

- 历史 HTTP 性能测试不受影响。
- 历史 SSE 配置可以读取、编辑、生成脚本和运行。
- 历史性能目标继续引用原指标 ID。
- 报告继续展示动态 SSE 指标。

## 27. 验收标准

### 27.1 通用性

- 系统代码和提示词中不存在必须生成 `call_llm_start`、`first_answer` 或 `query_end` 的逻辑。
- 任意合法 SSE 事件结构均可进入事件事实目录。
- AI 可以返回零至八个候选。
- 生成结果不依赖固定指标数量或固定指标 ID。

### 27.2 真实性

- 每个候选必须引用真实事件事实。
- 每个标记为“已验证”的候选必须在样本回放中至少命中一次。
- 界面展示首次事件序号、样本耗时和命中次数。
- 无证据的业务语义不得显示为确定结论。

### 27.3 用户体验

- AI 未采用但最终存在已验证候选时提示生成成功。
- 关闭弹窗后无需重新运行即可查看生成结果。
- 用户修改规则后必须重新验证才能应用。
- 请求变化后不得应用旧验证结果。
- 没有候选时提供事件目录和手动配置路径。

### 27.4 兼容性

- 历史固定指标继续正常运行。
- `PerformanceSseConfig` 正式运行契约保持兼容。
- Locust 脚本生成器不调用 AI。
- AI 元数据不进入正式运行配置和性能统计。

## 28. 实施顺序建议

1. 新增事件事实和候选 Schema。
2. 实现事实提取、过滤和结构型候选。
3. 重构 AI 提示词和输出契约。
4. 删除固定指标与固定结束规则要求。
5. 实现候选合并、评分、回放和稳定 ID。
6. 扩展生成 API 响应。
7. 重构前端候选选择和草稿状态。
8. 调整提示信息和诊断详情。
9. 增加通用样本测试和历史配置回归测试。
10. 灰度观察空结果率、应用率和手动配置率。

## 29. 设计决策总结

- SSE 正式运行模型继续使用现有声明式配置，不创建第二套运行引擎。
- 指标生成从固定目标匹配改为真实事件发现。
- AI 从配置生成者降级为受限事实上的语义分析器和排序器。
- 程序负责事实提取、规则生成、ID 生成和确定性验证。
- 用户负责最终选择和应用。
- AI 失败不再触发固定业务指标兜底。
- 生成结果以表单草稿存在，弹窗只负责展示和编辑。
- 用户提示按最终可用性决定，内部降级信息进入诊断详情。
