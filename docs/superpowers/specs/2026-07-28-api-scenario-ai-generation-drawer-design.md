# API 场景 AI 编排生成改造设计

- 日期：2026-07-28
- 状态：待实现
- 范围：API 自动化场景编辑器中的 AI 编排草稿生成

## 1. 背景

当前 AI 编排入口使用居中 Dialog。用户点击“生成编排草稿”后，Dialog 由 `aiBusy` 持续占用并显示“正在生成”，导致用户感觉页面被卡住，无法继续查看或编辑当前场景。

项目已经存在可复用的后台任务能力：

- `api_scenario_ai_plans` 持久化 AI 编排计划及生命周期状态。
- `TaskRunningIndicator` 轮询 `/tasks/running` 并展示顶部运行中任务。
- `api_scenario_ai_plan` 已作为任务来源类型被任务中心识别。
- AI Plan 已提供按 `plan_id` 恢复结果的查询接口。

本次改造不新增平行任务体系，目标是让 AI 编排遵循现有任务中心模式。

## 2. 目标

1. 将 AI 编排输入界面从居中弹窗改为右侧抽屉。
2. 用户提交生成后立即关闭抽屉，不在生成期间占用主编辑区。
3. 生成任务在后台继续执行，顶部统一展示任务状态。
4. 生成完成后不自动打开预览；用户主动点击顶部状态后查看结果。
5. 页面刷新、切换路由或重新进入场景后，可以恢复任务状态和生成结果。
6. 保留现有 AI Plan 的预览、校验、应用和版本校验能力。

## 3. 非目标

- 不改变 AI 编排提示词、模型选择或接口资产筛选规则。
- 不改变 AI Plan 应用到场景草稿的业务规则。
- 不自动将 AI 生成结果直接应用到场景。
- 不新增独立的“AI 编排任务表”或另一套全局通知组件。
- 不在生成过程中伪造百分比进度。

## 4. 交互设计

### 4.1 打开生成抽屉

入口保持在 API 场景编辑器中。点击后打开右侧抽屉，桌面端建议宽度为 420–480px，小屏占满可用宽度。

抽屉内容包括：

- 标题：`AI 编排接口场景`
- 状态标签：`生成草稿`
- 业务目标输入框
- 当前已导入接口资产说明
- 当前接口环境等已有生成约束
- 操作按钮：`取消`、`生成编排草稿`

抽屉打开时不使用全屏模糊遮罩，左侧场景画布保持可见，允许用户保留当前编辑上下文。

### 4.2 提交生成

用户点击 `生成编排草稿` 后：

1. 校验目标非空并执行现有场景保存逻辑。
2. 创建 AI 编排后台任务。
3. 在任务已被后端接受后立即关闭抽屉。
4. 触发既有 `AI_TASK_STARTED_EVENT`，让顶部任务指示器立即刷新。
5. 页面继续可编辑，不显示阻塞式 Dialog，不锁定整个编辑器。

提交按钮只在短暂的“提交中”阶段禁用，避免重复创建任务。任务进入后台后，抽屉关闭，前端局部 `aiBusy` 复位。

### 4.3 顶部任务状态

复用 `TaskRunningIndicator`，任务来源为 `api_scenario_ai_plan`。

运行中展示：

```text
生成中 · AI 编排接口场景
```

点击顶部指示器后，显示任务卡片，至少包含：

- 任务标题
- 当前状态
- 业务目标摘要
- 创建时间
- 所属项目
- 进入任务中心或场景页面的入口

不具备真实阶段数据时，只展示“生成中/已完成/失败”等后端状态，不展示虚假百分比。

### 4.4 生成完成

任务完成后：

- 顶部运行中数量更新。
- 可通过短时 toast 提示：`AI 编排草稿已生成`。
- 不自动打开抽屉，不打断用户当前编辑。
- 用户点击任务卡片中的 `查看生成草稿` 后，进入对应场景并打开 AI 编排结果抽屉。

结果抽屉复用现有计划预览内容：

- 场景名称
- 步骤数量
- 置信度
- 步骤列表
- 校验错误和警告
- `放弃计划`
- `应用到场景草稿`

只有用户主动点击 `应用到场景草稿` 且校验通过时，才修改当前场景。

### 4.5 失败和恢复

任务失败时：

- 顶部状态展示 `AI 编排失败`。
- 任务卡片展示后端返回的可读错误原因。
- 提供 `重新生成`，重新打开输入抽屉并保留上次业务目标（若本地仍可恢复）。

用户刷新页面或重新进入场景时：

- 任务状态由 `/tasks/running` 或任务中心数据恢复。
- 已生成但未应用的 Plan 由 `plan_id` 查询接口恢复。
- 不重复发起 AI 请求。

## 5. 前端设计

### 5.1 组件调整

将 `AiOrchestrationDialog` 改造为 `AiOrchestrationDrawer`，或抽取一个支持侧边定位的通用 AI 编排面板组件。

建议职责分离：

- `AiOrchestrationDrawer`：负责输入、生成结果展示和应用操作。
- `useApiScenarioEditor`：负责任务提交、Plan 查询、应用和错误处理。
- `TaskRunningIndicator`：负责顶部任务状态轮询和任务入口。

不建议让抽屉组件直接维护全局任务状态。

### 5.2 状态模型

前端至少区分以下状态：

```text
idle                 尚未提交
submitting           正在提交任务
background_generating 已提交，后台生成中
completed            已生成待查看
failed               生成失败
previewing           正在加载已生成 Plan
applying             正在应用 Plan
```

其中 `background_generating` 不应控制抽屉继续打开，也不应阻塞场景编辑器。

### 5.3 防重复提交

提交前应查询或利用后端返回的任务状态，避免同一场景重复创建活跃任务。

如果后端返回“已有任务生成中”，前端展示已有任务入口，而不是再次提交。

### 5.4 路由和深链接

任务详情至少需要携带：

- `projectId`
- `scenarioId`
- `planId`

可继续复用现有场景页面参数，并新增或复用一个用于定位生成结果的查询参数，例如：

```text
?scenarioId=<scenario-id>&aiPlanId=<plan-id>
```

页面加载后读取参数，查询 Plan 状态；仅当用户通过任务入口进入时才自动打开结果抽屉。

## 6. 后端设计

### 6.1 接口策略

优先改造现有 `POST /projects/{project_id}/api-scenarios/ai-plan`，不新增平行的 AI 编排接口。

当前接口同步返回完整 Plan。改造后应支持快速返回任务句柄：

```json
{
  "plan_id": "aiplan-xxxx",
  "lifecycle_status": "generating",
  "scenario_id": "scenario-xxxx"
}
```

推荐 HTTP 语义：

- 任务成功入队：`202 Accepted`
- 参数或资产校验失败：保持现有 `4xx`
- 任务无法创建：返回明确的 `5xx` 或业务错误码

现有 `GET /projects/{project_id}/api-scenarios/ai-plans/{plan_id}` 继续用于查询生成状态和恢复完整 Plan。

### 6.2 异步执行

创建接口完成以下短事务后立即返回：

1. 校验项目、场景和接口资产。
2. 创建 `api_scenario_ai_plans` 记录。
3. 设置 `lifecycle_status = generating`。
4. 保存脱敏后的目标和生成上下文。
5. 将 AI 生成工作提交给现有后台执行机制。

后台 worker 完成后：

- 成功：写入 `plan_json`、`validation_json`，设置 `lifecycle_status = completed`。
- 失败：设置 `lifecycle_status = failed`，写入错误摘要。
- 过期或超时：设置明确的超时状态或失败状态，避免永久处于 generating。

如果当前项目没有可复用的后台 worker，应优先复用现有任务执行入口；不得使用前端请求生命周期作为任务可靠性的唯一保障。

### 6.3 状态契约

建议统一生命周期状态：

```text
generating  后台生成中
completed   已生成可预览
failed      生成失败
expired     结果已过期
applied     已应用到场景草稿
```

`status = preview` 表示 Plan 的业务类型或可预览状态时，应与 `lifecycle_status` 分开使用，避免前端把“预览”误判为“生成完成”。

### 6.4 结果一致性

继续保留现有的：

- `expected_revision`
- 场景草稿哈希
- 接口资产指纹
- 应用前校验

生成期间用户可以继续编辑场景。用户应用 Plan 时，如果版本或接口资产已经变化，继续触发现有冲突确认流程，不覆盖用户新修改。

## 7. 任务中心集成

现有 `TaskRunningIndicator` 已支持 `api_scenario_ai_plan`，本次只需确认：

1. `lifecycle_status = generating` 能出现在运行中任务列表。
2. `completed/failed/expired` 能正确退出运行中列表并保留历史记录。
3. `detail_url` 能定位到对应项目和场景。
4. `summary` 或错误字段能显示可读信息。
5. `notifyAiTaskStarted()` 在任务创建成功后触发，而不是在同步 AI 请求即将开始时触发。

## 8. 验收标准

### 交互验收

- 点击 AI 编排入口打开右侧抽屉，不出现居中大弹窗。
- 点击生成后抽屉立即关闭。
- 生成期间场景画布、步骤配置和其他页面操作不被遮挡或禁用。
- 顶部能看到 AI 编排生成中状态。
- 点击顶部任务入口可以查看任务详情。
- 生成完成后不会自动打开任何预览面板。
- 用户主动点击查看后，结果在右侧抽屉中展示。

### 数据验收

- 任务创建后刷新页面，任务仍显示为生成中。
- 生成完成后刷新页面，可以恢复未应用的 Plan。
- 失败任务显示可读错误原因。
- 同一场景存在生成中任务时，重复提交不会创建重复任务。
- 场景版本变化时，应用结果仍执行版本校验。

### 自动化测试

前端至少覆盖：

- 抽屉打开、关闭和提交行为。
- 提交后抽屉关闭且不阻塞编辑器。
- 顶部任务入口出现和状态更新。
- 完成后主动打开结果抽屉。
- 失败状态和重试入口。

后端至少覆盖：

- AI Plan 创建接口返回任务句柄。
- 任务记录初始状态为 `generating`。
- 后台成功、失败和超时状态转换。
- Plan 查询接口在生成中、完成、失败时返回正确结构。
- 重复任务保护。
- 版本或资产指纹变化时应用失败或进入现有确认流程。

## 9. 实施顺序

1. 确认并复用现有任务执行器和任务状态契约。
2. 将 AI Plan 创建流程改为可快速返回任务句柄的后台任务。
3. 补齐前端 API 类型和任务状态恢复逻辑。
4. 将 `AiOrchestrationDialog` 改为右侧抽屉。
5. 接入提交后关闭、顶部状态和主动查看结果流程。
6. 添加前后端测试并执行针对性验证。
7. 最后进行手工验证：提交、切换页面、刷新、完成、失败、重试和应用。

## 10. 设计决策

最终采用：

```text
右侧抽屉承载输入和结果
顶部任务指示器承载后台状态
后端持久化并异步执行 AI Plan
生成完成不自动弹出结果
```

该方案在保持当前任务中心、Plan 持久化和版本校验能力的同时，消除生成期间的阻塞感，并为后续增加生成设置和结果详情保留空间。
