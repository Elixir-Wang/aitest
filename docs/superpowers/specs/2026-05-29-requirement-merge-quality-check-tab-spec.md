# 需求合并质量检测整改规范

## 背景

当前需求合并结果页把用户可见产物组织为“合并后的文档 / 段落映射 / 明显冲突”。这套结构偏向研发审计，存在两个问题：

1. “合并后的文档”已经在初始需求主内容区展示，再作为 artifact tab 会造成重复。
2. “段落映射”是质量保障证据的一部分，不应作为业务和测试人员需要单独理解的技术入口。

本次整改将用户视角调整为：

```text
主内容：合并需求稿
辅助页签：质量检测、待确认项
```

其中“质量检测”用于证明合并后没有丢失内容、没有过度摘要、没有破坏关键结构；“待确认项”用于承载来源之间的矛盾、口径不清、条件缺失等需要人工确认的问题。

## 目标

- 移除用户可见的“合并后的文档”artifact tab，合并稿只作为初始需求主内容展示。
- 将“段落映射”改造为“质量检测”，并把来源覆盖、内容保留、完整性检查、追溯摘要合并到同一质量页。
- 将“明显冲突”改名为“待确认项”，覆盖冲突、口径不清、规则互斥、条件缺失等需要人工判断的内容。
- 保留后端内部段落映射和结构化审计能力，但不把 `mapping_id`、`docmap`、fragment id 等调试字段暴露给业务和测试人员。
- 质量检测内容面向业务和测试人员，回答“这份合并稿能不能用于后续测试设计”。

## 非目标

- 不重做需求上传、标准文件转换、Source Block 抽取或合并智能体主流程。
- 不删除内部 mapping、source blocks、coverage table、quality JSON 等机器产物。
- 不把业务冲突、规则缺条件、字段定义冲突放进质量检测页详述。
- 不让质量检测替代待确认项的人工决策流程。
- 不在本次整改中实现更复杂的语义级字段完整性算法；先复用已有可计算指标，后续再增强。

## 用户可见结构

### 初始需求主内容

初始需求页的主 Markdown 区继续展示合并需求稿。

主内容负责：

- 展示最新合并稿或已确认版本内容。
- 提供编辑、需求分析、确认写入版本等操作。
- 展示质量结果摘要，例如通过、警告、未通过。

主内容不再作为 artifact tab 的一项出现。

### 质量检测

页签名称：`质量检测`

定位：合并质量保障结果。它只回答合并过程质量问题：

- 来源内容是否都被处理。
- 合并稿是否疑似缩水或只剩摘要。
- 表格、代码块、Mermaid、规则段落等关键结构是否保留。
- 高保真来源块是否得到保留。
- 来源内容是否可以追溯到合并稿中的业务章节。

质量检测不负责解释业务冲突谁对谁错。

### 待确认项

页签名称：`待确认项`

定位：人工确认工作台。它承载内容本身存在不确定性的问题：

- 来源之间口径不一致。
- 规则互斥或条件缺失。
- 字段定义、状态流转、异常处理存在差异。
- 智能体无法确定应采用哪一版。
- 需要业务或测试人员补充确认后才能重新合并或确认入库。

## 质量检测内容结构

### 1. 检测结论

展示本次合并质量门禁结果：

| 字段 | 说明 |
| --- | --- |
| 合并质量 | 通过、警告、未通过 |
| 是否可确认写入版本 | 是、否 |
| 阻断原因 | 仅展示质量门禁原因，例如未覆盖、内容缩水、结构丢失 |
| 检测时间 | 本次 merge run 的生成时间 |

质量结论文案应避免技术字段。例如：

```text
通过：未发现来源内容遗漏或关键结构丢失，可进入后续测试设计。
警告：合并稿可阅读，但存在部分来源覆盖或结构保留风险，建议人工复核。
未通过：存在来源内容未覆盖或合并稿疑似缩水，不能确认写入版本。
```

### 2. 来源覆盖

展示来源文件和来源块是否都进入处理链路。

指标包括：

- 来源文件数。
- 来源块总数。
- 已合入数量。
- 重复引用数量。
- 进入待确认项数量。
- 未覆盖数量。

未覆盖内容必须显示业务可读摘要：

```text
- 账号状态限制：未进入合并稿，也未进入待确认项。
- 登录失败提示规则：未找到合并后章节位置。
```

来源覆盖来自内部 `coverage_items` 和 `source_blocks`，但前端展示不得出现 `mapping_id`、`docmap`、fragment id。

### 3. 内容保留

检查合并稿是否保留关键结构和高保真内容。

第一版复用现有可计算指标：

| 检查项 | 数据来源 | 说明 |
| --- | --- | --- |
| Markdown 表格 | 来源 Markdown 与合并稿结构计数 | 表格行数量是否异常下降 |
| Mermaid 流程图 | fenced block language | 流程图是否缺失 |
| 代码块 / JSON 示例 | fenced block count | 示例、配置、接口片段是否缺失 |
| 高保真来源块 | `must_preserve_original` | 必须保留原文的块是否被保留或进入待确认项 |

后续可增强字段、枚举、状态、规则类段落的语义保留检测，但不阻塞本次整改。

### 4. 合并完整性

检查合并稿是否疑似被压缩成摘要。

第一版复用现有有效内容量比对：

- 来源有效内容条数。
- 合并稿有效内容条数。
- 内容保留比例。
- 是否低于质量门禁阈值。

示例：

```text
来源有效内容 128 条，合并稿有效内容 83 条，保留比例 65%。未发现明显摘要化。
```

当低于阈值时，质量检测应阻断确认写入版本：

```text
来源有效内容 128 条，合并稿有效内容 24 条，保留比例 19%。合并稿疑似只生成摘要，不能确认写入版本。
```

### 5. 来源追溯摘要

来源追溯摘要是“段落映射”的业务化表达，不再展示完整技术映射表。

展示方式：

```text
- 账号登录规则：已合入「登录认证 / 账号登录」。
- 密码错误锁定规则：已合入「登录认证 / 安全限制」。
- 登录提示文案差异：进入「待确认项」。
- 租户切换规则：未覆盖，需要重新合并或人工补充。
```

追溯摘要只展示来源标题、合并后业务位置和处理结果，不展示内部 ID。

## 待确认项内容结构

待确认项从原“明显冲突”扩展而来，但命名和文案面向业务和测试人员。

内容包括：

- 待确认项统计。
- 每个待确认项的标题。
- 问题类型：口径不一致、规则互斥、条件缺失、字段差异、状态流转差异。
- 涉及来源。
- 差异摘录。
- 需要确认的问题。
- 当前处理状态。

无待确认项时显示：

```text
本次未发现需要人工确认的差异。
```

如果质量检测存在阻断原因，但没有待确认项，阻断原因应出现在质量检测页，不应硬塞到待确认项页。

## 后端设计

### Artifact 输出

后端继续保存机器可追溯产物：

```text
previews/{run_id}.md
mappings/{run_id}.md
conflicts/{run_id}.md
artifacts/{run_id}-source-blocks.json
artifacts/{run_id}-fragments.json
artifacts/{run_id}-decisions.json
```

新增或调整用户可见 artifact：

```text
quality/{run_id}.md
confirmations/{run_id}.md
```

用户可见 `artifact_tabs` 调整为：

```json
[
  {
    "key": "quality",
    "label": "质量检测",
    "path": "quality/{run_id}.md",
    "content": "..."
  },
  {
    "key": "confirmations",
    "label": "待确认项",
    "path": "confirmations/{run_id}.md",
    "content": "..."
  }
]
```

兼容阶段可保留读取旧 `mapping/conflicts` 文件的能力，但新 merge run 不再把 `merged/mapping/conflicts` 作为 public tabs 返回。

### 质量检测渲染

新增后端渲染函数：

```text
build_quality_markdown(
  coverage_items,
  source_files,
  source_blocks,
  preview_markdown,
  quality_result,
  blocking_issues,
  merge_summary
)
```

职责：

- 汇总检测结论。
- 汇总来源覆盖。
- 汇总内容保留。
- 汇总合并完整性。
- 生成来源追溯摘要。

该函数应确定性渲染 Markdown，不由智能体自由生成质量检测文档。

### 待确认项渲染

将原 `build_conflicts_markdown()` 改造或包装为：

```text
build_confirmation_markdown(conflicts)
```

职责：

- 使用“待确认项”作为文档标题。
- 将 conflict 文案业务化。
- 无待确认项时只说明无人工确认差异。
- 不承载质量门禁阻断原因，除非该阻断原因本身来自待确认项。

### 质量门禁

继续复用现有 `evaluate_merge_quality()` 结果：

- `passed`：可确认写入版本。
- `warning`：可确认，但提示建议人工复核。
- `failed`：禁止确认写入版本。

质量门禁判断范围：

- 来源内容未覆盖。
- 合并稿疑似摘要化。
- 关键 Markdown 结构保留不足。
- 高保真来源块未保留。
- 合并稿污染源文件名、`docmap` 或内部来源结构。

待确认项数量可以影响是否允许确认，但待确认项详情展示在“待确认项”页。

## 前端设计

### 类型调整

`MergeArtifactTab.key` 从：

```text
merged | mapping | conflicts
```

调整为：

```text
quality | confirmations
```

兼容旧数据时允许读取旧 key，但新接口响应以新 key 为准。

### 初始需求页

初始需求页展示结构：

```text
[合并需求稿主内容]

[质量检测] [待确认项]
```

交互规则：

- 默认展示合并稿主内容。
- `质量检测` 和 `待确认项` 作为辅助 tab 或辅助区展示。
- 质量结果 `failed` 时禁用“确认写入版本”。
- 禁用原因指向“质量检测”，例如“质量检测未通过，请查看未覆盖来源内容”。
- 有待确认项时提示用户先处理待确认项。

### 文案调整

统一替换用户可见文案：

| 旧文案 | 新文案 |
| --- | --- |
| 合并后的文档 | 不再作为 tab 展示 |
| 段落映射 | 质量检测 |
| 明显冲突 | 待确认项 |
| 段落映射存在未覆盖来源内容 | 存在来源内容未进入合并稿 |
| 智能体未返回段落映射 | 无法证明所有来源内容已被处理 |

## 数据兼容

历史 merge run 可能仍只有旧产物：

```text
previews/{run_id}.md
mappings/{run_id}.md
conflicts/{run_id}.md
```

兼容策略：

- 读取历史产物时，可将旧 `mapping.md` 作为“质量检测”的兼容内容展示。
- 读取历史 `conflicts.md` 时，前端 label 显示为“待确认项”。
- 新生成产物必须使用 `quality` 和 `confirmations`。
- 不迁移历史文件，避免批量数据改写。

## 测试策略

### 后端单元测试

覆盖以下场景：

- `write_merge_artifacts` 新生成 public tabs 为 `quality / confirmations`。
- `build_quality_markdown` 包含检测结论、来源覆盖、内容保留、合并完整性、来源追溯摘要。
- 未覆盖来源块出现在质量检测中，并导致 `quality_result=failed`。
- 内容异常过短时质量检测展示有效内容条数和阻断原因。
- 表格、Mermaid、代码块保留不足时质量检测展示结构保留问题。
- 无冲突时待确认项显示“本次未发现需要人工确认的差异”。
- 有冲突时待确认项包含差异摘录和人工确认提示。

### 前端验证

覆盖以下场景：

- 初始需求主内容不再出现“合并后的文档”tab。
- artifact tab 只显示“质量检测”和“待确认项”。
- `quality_result=failed` 时确认按钮禁用，并能看到质量检测原因。
- 旧数据返回 `mapping/conflicts` 时仍可显示为“质量检测/待确认项”。

### 回归验证命令

建议执行：

```powershell
rtk .\.venv\Scripts\python.exe -m pytest tests/test_requirement_merge_service.py -q
rtk .\.venv\Scripts\python.exe -m pytest tests/test_document_service.py -q -k merge
rtk npm --prefix apps/frontend run typecheck
```

## 验收标准

- 用户在初始需求页只看到一个合并稿主内容，不再看到重复的“合并后的文档”tab。
- 用户可见辅助入口为“质量检测”和“待确认项”。
- “质量检测”能说明是否存在内容遗漏、结构丢失、合并稿缩水和来源追溯问题。
- “待确认项”只承载需要人工确认的业务差异，不混入纯质量门禁问题。
- 新生成 merge run 的 public tabs 不再包含 `merged`、`mapping`、`conflicts`。
- 内部审计产物仍能追踪来源块和覆盖关系。
