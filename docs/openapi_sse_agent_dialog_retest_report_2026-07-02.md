# OpenAPI SSE Agent Dialog 复测报告

**接口**: `POST https://saibotan-pre.100credit.cn/openapi/sse/agent-dialog/lightweight-beta/dialog`

**复测日期**: 2026-07-02

**测试工具**: Windows PowerShell + `curl 8.21.0`

**测试环境**: `pre`

## 1. 复测目标

- 按原测试报告场景重新验证接口行为
- 确认 SSE 流式响应是否仍有明确结束标记
- 确认鉴权、必填、请求方法、请求体格式等关键约束是否稳定
- 识别本次复测与上次测试相比的新风险

## 2. 复测范围

本次复测覆盖 23 个场景：

- 正常请求
- 特殊字符输入
- 空问题、缺少问题、空格问题、长文本问题
- username / robot key / robot token 缺失、为空、null、错误
- segment_code / message_source 缺失或非法
- 非法 JSON
- GET / OPTIONS 方法
- `Accept` / `Content-Type` 异常

## 3. 复测结论

### 3.1 总体结论

- 接口仍可正常建立 SSE 流，正常业务流均返回 `HTTP 200` 和 `text/event-stream`
- 成功业务流均能收到最后结束标记 `finish: "y"`
- 鉴权与核心必填字段校验仍有效
- 非法 JSON 仍返回 `HTTP 500`
- `GET` / `OPTIONS` 仍返回 `HTTP 405`
- 本次复测出现多次 `系统繁忙(201)，请稍后重试。`，但业务码仍为 `000000` 且 SSE 正常结束

### 3.2 本次新增关注点

`系统繁忙(201)` 被包在成功 SSE 流内返回：

- HTTP 状态为 `200`
- SSE 业务码为 `000000`
- 最后一条事件为 `finish: "y"`
- 但最终回答内容为 `系统繁忙(201)，请稍后重试。`

这意味着调用方不能只根据 `HTTP 200`、`code=000000`、`finish=y` 判断回答可用，还需要检查最终回答内容或后端是否有更细的下游错误字段。

## 5. 关键场景说明

### 5.1 正常请求

`TC01` 和 `TC02` 均返回完整回答：

- HTTP: `200`
- Content-Type: `text/event-stream`
- 业务码: `000000`
- 最后一条事件: `finish: "y"`
- curl 退出提示: `curl: (56) Connection closed abruptly`

说明 SSE 流本身完整结束，但 curl 仍认为连接收尾方式异常。

### 5.2 question 缺失或为空

`TC03`、`TC04`、`TC19` 均能进入正常业务流。

本次表现：

- 空字符串、缺少字段会返回默认问候语
- 空格问题返回成功流，但最终内容为 `系统繁忙(201)`

### 5.3 鉴权与核心必填

`username`、`robot_key`、`robot_token` 缺失、为空或 null 时，返回 `400001`。

`robot_token` 错误时，返回 `400002`。

这些场景 HTTP 仍为 `200`，错误通过 SSE `data.code` 表达。

### 5.4 非法 JSON

非法 JSON 返回：

- HTTP: `500`
- Content-Type: `text/plain; charset=utf-8`
- 未进入 SSE 流

### 5.5 方法限制

`GET` 和 `OPTIONS` 均返回 `405`，未进入 SSE 流。

## 6. 风险点

| 风险 | 说明 | 建议 |
|---|---|---|
| 业务失败不一定体现在 HTTP 状态码 | 鉴权错误仍是 `HTTP 200` | 客户端必须解析 SSE `code/message` |
| 下游繁忙也可能包装在成功流中 | `code=000000` 且 `finish=y` 时仍可能返回 `系统繁忙(201)` | 客户端需识别最终回答内容，或服务端增加明确错误字段 |
| 非法 JSON 返回 500 | 请求体格式错误未被转成 4xx | 调用方先做 JSON 格式校验 |
| `message_source` / `segment_code` 非强校验 | 缺失或非法仍进入业务流 | 产品/后端确认这两个字段是否应强校验 |
| 浏览器直连存在风险 | `OPTIONS` 返回 405 | 如前端直接调用，需补 CORS 方案 |

## 7. 接入建议

- 客户端判断一次调用是否成功时，应同时检查：
  - HTTP 状态
  - SSE `data.code`
  - 最后一条事件 `finish`
  - 最终回答内容是否为系统繁忙/下游错误
- 不建议只用 `HTTP 200` 或 `finish=y` 判断业务成功
- 对外 SDK 可封装统一解析逻辑，将 `400001`、`400002`、`系统繁忙(201)` 转成明确异常
- 若该接口要给浏览器前端直接调用，必须补 CORS/预检验证

## 8. 最终结论

本次复测结果与原测试结论总体一致：

- SSE 协议链路可用
- 核心鉴权校验有效
- 方法限制明确
- 非法 JSON 未被友好处理

但本次新增发现：

- 多个成功流返回 `系统繁忙(201)`，且仍表现为 `code=000000`、`finish=y`

因此，接口可继续接入验证，但生产级客户端需要补充“成功流内业务降级/繁忙提示”的识别逻辑。
