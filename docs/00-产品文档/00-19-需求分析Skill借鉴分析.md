## 值得借鉴的核心理念

### 1. 核心原则：需求是假设

**Skill的观点：**
> Requirements are hypotheses about what will solve a problem. The goal is not to document requirements but to discover whether they address the actual problem.

**借鉴到PRD：**
```markdown
## 需求分析核心原则

需求不是事实，而是关于"什么能解决问题"的假设。需求分析的目标不是记录需求，而是验证需求是否真正解决了实际问题。

### 需求验证三问
1. 这个需求解决什么问题？（问题识别）
2. 为什么这个需求能解决这个问题？（因果关系）
3. 如何验证需求确实解决了问题？（验证方法）

### 需求分类
| 类型 | 说明 | 处理方式 |
| --- | --- | --- |
| 已验证需求 | 有证据支持的需求 | 直接进入需求文档 |
| 假设需求 | 未验证的需求 | 标记为"待验证"，补充验证计划 |
| 伪需求 | 实际是解决方案的需求 | 追溯真实问题，重新表达 |
```

### 2. 状态机模型

**Skill的状态：**
- RA0: 没有问题陈述
- RA1: 解决方案优先思维
- RA2: 模糊需求
- RA3: 隐藏约束
- RA4: 范围蔓延预防
- RA5: 需求已验证

**借鉴到PRD：**
```markdown
## 需求分析状态机

### 状态定义

| 状态 | 说明 | 症状 | 下一步 |
| --- | --- | --- | --- |
| 需求缺失 | 没有明确的需求来源 | 只有想法，没有需求文档 | 补充需求来源 |
| 解决方案混淆 | 需求描述中混入实现细节 | "需要用React实现"、"需要用Redis缓存" | 提取真实需求 |
| 需求模糊 | 需求不可测试 | "系统应该快"、"用户体验好" | 具体化需求 |
| 约束缺失 | 缺少明确的约束条件 | 没有性能指标、没有兼容性要求 | 补充约束清单 |
| 范围不清 | 没有明确的边界 | 所有功能都是P0、没有分期计划 | 划分优先级 |
| 需求已确认 | 需求可测试、有约束、有边界 | 通过质量门禁 | 进入知识库生成 |

### 状态流转规则
- 必须按顺序通过每个状态
- 不能跳过状态（如需求模糊时不能直接进入需求已确认）
- 每个状态有明确的退出条件
```

### 3. 关键问题清单

**Skill的关键问题：**
- What happens if this doesn't exist? Who suffers?
- What are people doing today instead?
- How would you know if this requirement is met?
- What's definitely true about this context?

**借鉴到PRD：**
```markdown
## 需求分析关键问题清单

### 问题发现阶段
- [ ] 这个需求解决什么问题？
- [ ] 谁有这个问题？（具体的用户角色）
- [ ] 如果没有这个功能会发生什么？
- [ ] 用户现在如何解决这个问题？
- [ ] 为什么现有方案不够好？
- [ ] 是什么触发了这个需求？

### 需求澄清阶段
- [ ] 这个需求必须实现什么？
- [ ] 如何验证需求已满足？
- [ ] 最小可用版本是什么？
- [ ] 什么样的实现会让你失望？
- [ ] 这个需求能用其他方式满足吗？

### 约束发现阶段
- [ ] 实际的时间预算是多少？
- [ ] 需要哪些技能？
- [ ] 必须集成哪些系统？
- [ ] 有哪些假设尚未验证？
- [ ] 什么会导致项目失败？

### 范围定义阶段
- [ ] V1包含什么？后续版本包含什么？
- [ ] 如果必须削减，会削减什么？
- [ ] 什么触发重新考虑延期项？
- [ ] 什么明确不在范围内？
```

### 4. 反模式识别

**Skill的反模式：**
- The Solution Specification（解决方案规范）
- The Stakeholder Fiction（利益相关者虚构）
- The Infinite Backlog（无限待办）
- The Premature Precision（过早精确）
- The Constraint Blindness（约束盲区）
- The Feature Transplant（功能移植）

**借鉴到PRD：**
```markdown
## 需求分析反模式

### 反模式1：解决方案伪装成需求

**症状：**
- 需求描述包含技术实现："需要用PostgreSQL存储"
- 无法在不提及技术的情况下解释需求
- 回答"是什么"时用"如何实现"

**示例：**
❌ 错误："系统需要使用Redis缓存"
✅ 正确："系统需要在1秒内返回查询结果"

**修正方法：**
1. 对每个需求问："这个需求能用其他方式满足吗？"
2. 如果答案是"是"，说明你描述的是实现，不是需求
3. 重新表达为结果导向的需求

### 反模式2：假想用户需求

**症状：**
- 测试工程师假想用户需求："用户会想要..."
- 没有证据支持的需求
- 复制其他产品的功能而不理解原因

**示例：**
❌ 错误："用户会想要暗黑模式"（没有证据）
✅ 正确："5个用户反馈长时间使用时眼睛疲劳，需要暗黑模式"

**修正方法：**
1. 如果你是用户，诚实表达你的需求
2. 如果为他人构建，与他们交谈或使用类似证据
3. 不要发明用户

### 反模式3：无限需求列表

**症状：**
- 需求不断增长，没有优先级
- 所有功能都同等重要
- 无法区分核心和锦上添花

**示例：**
❌ 错误：50个P0需求
✅ 正确：3个P0需求，10个P1需求，37个P2需求

**修正方法：**
1. 强制排序：如果只能实现一个功能，是什么？
2. 然后两个？这揭示了真实优先级
3. 使用MoSCoW方法：Must/Should/Could/Won't

### 反模式4：过早精确化

**症状：**
- 在验证核心需求前设计细节
- 设计通知偏好页面，但还没验证用户是否需要通知

**示例：**
❌ 错误：详细设计报告导出的10种格式，但还没确认用户是否需要导出
✅ 正确：先验证导出需求，再设计格式

**修正方法：**
1. 识别哪些需求现在需要精确，哪些可以延后
2. 对不确定的区域标记"在X验证后再确定"

### 反模式5：约束盲区

**症状：**
- 没有列出真实约束
- 实现中途才发现约束："哦，我每周只有10小时"

**示例：**
❌ 错误：没有明确性能要求，实现后发现性能不满足
✅ 正确：需求阶段明确"页面加载时间<2秒"

**修正方法：**
1. 在需求分析前明确约束清单
2. 区分真实约束和假设

### 反模式6：功能移植

**症状：**
- 从现有产品复制功能，不理解为什么存在
- 不确定功能是否解决你的问题

**示例：**
❌ 错误："Jira有看板，所以我们也需要看板"
✅ 正确："我们需要可视化任务状态，看板是一种方式"

**修正方法：**
1. 对每个"借鉴"的功能，说明它在你的场景中解决什么问题
2. 如果说不出来，删除它
```

### 5. 健康检查问题

**Skill的健康检查：**
- Am I describing a problem or a solution?
- Could I explain this to someone unfamiliar?
- How would I test if this requirement is satisfied?
- What assumptions am I making?

**借鉴到PRD：**
```markdown
## 需求分析健康检查

在需求分析过程中，定期自问：

### 问题 vs 解决方案
- [ ] 我在描述问题还是解决方案？
- [ ] 这个需求能用其他方式满足吗？

### 可理解性
- [ ] 我能向不熟悉的人解释这个需求并让他们理解吗？
- [ ] 需求文档中有没有只有我才懂的术语？

### 可测试性
- [ ] 我如何测试这个需求是否满足？
- [ ] 我能写出具体的测试用例吗？

### 假设识别
- [ ] 我做了哪些未验证的假设？
- [ ] 哪些假设如果错误会导致项目失败？

### 范围控制
- [ ] 这个范围在我的实际约束下可实现吗？
- [ ] 什么明确不在范围内？

### 动机检查
- [ ] 我在构建我需要的还是我知道如何构建的？
- [ ] 如果这个项目失败，最可能的原因是什么？
```

## 建议的PRD优化

### 优化1：在00-03文档中增加"需求分析状态机"

在需求分析章节前增加：

```markdown
## 6.0 需求分析状态机

需求分析不是一次性活动，而是一个渐进式的状态流转过程。

### 状态定义

| 状态 | 说明 | 典型症状 | 关键问题 | 退出条件 |
| --- | --- | --- | --- | --- |
| S0-需求缺失 | 没有明确的需求来源 | 只有想法，没有需求文档 | 这个想法解决什么问题？ | 有需求文档或探索文档 |
| S1-解决方案混淆 | 需求中混入实现细节 | "需要用Redis"、"需要用React" | 如果这个技术不存在，你需要什么？ | 需求不包含技术实现 |
| S2-需求模糊 | 需求不可测试 | "系统应该快"、"用户体验好" | 如何验证这个需求已满足？ | 可测试性评分>=80分 |
| S3-约束缺失 | 缺少明确的约束条件 | 没有性能指标、兼容性要求 | 什么是确定的约束？ | 约束清单完整 |
| S4-范围不清 | 没有明确的边界 | 所有功能都是P0 | 如果只能实现3个功能，是哪3个？ | 有明确的V1边界 |
| S5-需求已确认 | 需求可测试、有约束、有边界 | 通过质量门禁 | - | 可进入知识库生成 |

### 状态流转规则

1. **顺序流转**：必须按S0→S1→S2→S3→S4→S5顺序
2. **不可跳跃**：不能跳过中间状态
3. **可回退**：发现问题可回退到前面状态
4. **门禁检查**：每个状态有明确的退出条件

### 状态诊断

系统在需求分析时自动诊断当前状态：

```python
def diagnose_requirement_state(requirement_doc):
    if not requirement_doc.has_source():
        return "S0-需求缺失"
    if requirement_doc.contains_implementation():
        return "S1-解决方案混淆"
    if requirement_doc.testability_score < 80:
        return "S2-需求模糊"
    if not requirement_doc.has_constraints():
        return "S3-约束缺失"
    if not requirement_doc.has_scope_boundary():
        return "S4-范围不清"
    return "S5-需求已确认"
```

## 总结

这个需求分析skill提供了非常好的**诊断式思维框架**，与我们当前PRD的**结构化检查清单**形成互补：

**Skill的优势：**
- 问题导向，避免解决方案思维
- 状态机模型，清晰的流转路径
- 反模式识别，避免常见错误
- 假设验证，区分事实和假设

**当前PRD的优势：**
- 测试视角完整，覆盖功能和非功能
- 结构化程度高，可操作性强
- 专业性强，测试维度全面
- 质量门禁，确保需求质量

**融合后的价值：**
✅ 既有诊断式的问题发现能力
✅ 又有结构化的检查和验证能力
✅ 既避免了常见错误
✅ 又确保了测试覆盖

建议优先实施"需求分析状态机"和"反模式识别"，这两个是最容易落地且价值最大的部分。
