# 新增性能压测智能分析报告

## 背景

当前性能测试已经支持单接口 Locust 脚本生成、运行控制、实时统计、结果文件下载、AI 诊断、白名单配置修复和自动复测。现有 AI 分析主要服务于“发现失败原因并修复重跑”，报告仍以 Locust 原始 HTML/CSV 和抽屉中的诊断文本为主，无法稳定回答以下问题：

- 本次压测是否满足性能目标，结论依据是什么。
- 最大稳定吞吐量和性能退化拐点在哪里。
- 延迟、吞吐、错误与资源指标之间是否存在可验证的关联。
- 与历史基线相比发生了什么变化。
- 研发、技术负责人和业务负责人分别应该看到哪些结论。
- 优化建议如何转化为可跟踪、可复测的行动。

本变更在现有 `performance_report_analysis`、`performance_analysis_sessions`、证据包和修复复测链路上增加结构化指标快照、数据质量判定、证据化智能报告、角色化阅读视图、历史对比和报告导出。系统使用确定性代码计算数值和图表数据，AI 只负责受约束的归因、建议和叙事，不允许模型自由计算或改写指标。

## 目标

- 为已结束的 Locust 性能运行生成可追溯、可重复的结构化分析快照。
- 性能运行进入终态后先创建报告分析；只有报告诊断确认存在白名单可修复项时，才允许进入 AI 修复。
- 根据明确的性能目标输出 `pass`、`conditional_pass`、`fail` 或 `indeterminate` 结论。
- 计算稳态窗口、延迟分位数、吞吐量、错误率、容量余量和可识别的性能拐点。
- 将所有 AI 诊断绑定到稳定证据引用，并区分 observed、derived 和 inferred。
- 提供研发、技术负责人和业务负责人三种报告视角，但共享同一份事实快照。
- 提供完整报告页以及 HTML、PDF 导出，保留现有 Locust 原始报告下载。
- 支持选择同一性能测试的历史运行作为基线，展示同口径对比。
- 支持围绕报告追问；回答必须引用报告证据，不得修改运行、配置或脚本。
- 复用现有白名单修复、审批、预检和自动复测能力形成闭环。
- 复用并扩展现有 `agents/performance_testing/diagnosis`，首版不新增重复读取原始数据的报告智能体。

## 非目标

- 第一阶段不接入 JMeter、k6、Gatling 或外部压测平台。
- 第一阶段不实现跨服务的完整 APM 拓扑归因；未接入服务端观测数据时必须明确证据不足。
- 不让模型直接读取大文件后自行计算 P95、P99、TPS、错误率或容量结论。
- 不让模型生成可执行 HTML、JavaScript、SQL、Locust 脚本或任意配置修改。
- 第一阶段不新增独立 `report_narration` 智能体；角色化报告由受控模板编排同一份结构化诊断。
- 不自动发布报告到外部系统，不自动通知项目外人员。
- 不根据相关性直接宣称因果关系，不在缺少证据时强制输出根因。
- 不替换现有 Locust 原始报告和 AI 修复复测流程。

## 预期收益

- 把离散的压测结果转化为可以直接用于发布评审和容量决策的报告。
- 通过统一口径和版本化快照提升重复分析的一致性。
- 让诊断结论能够从报告追溯到原始运行证据，降低 AI 幻觉风险。
- 将发现问题、提出优化、审批修复和复测对比连接为完整工作流。
- 为以后接入 Prometheus、APM 和更多压测工具保留稳定的数据契约。
